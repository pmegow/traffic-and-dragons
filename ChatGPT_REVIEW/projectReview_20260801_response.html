Finding-by-finding assessment

1 · Cache/version release mismatch Confirmed

Verified: the last APP_VERSION/CACHE bump is commit 719cd4b (v1.518 / tnd-v3-20260801h, Aug 1 22:51). Two later content commits — 038a57f and ff69782 (HEAD) — both modify capability_bible.js, which is precached in the service-worker app shell (sw.js:15). Neither bumps either marker. class_bible.js is unaffected (it rides the network-first regex, sw.js:96) — the review correctly singled out capability_bible.js.

This is the review's best finding: real, current, and it violates the project's own hard rule ("bump APP_VERSION on every commit that changes game code — no exceptions"). Installed clients would keep serving the pre-rebalance Necromancer benches indefinitely. The reviewer's deeper point also lands: our existing guard (.claude/hooks/stop-check.js) checks version drift against memory notes, not "shell asset changed without a marker bump" — so the rule has no mechanical teeth today, and a content-only commit is exactly the shape that slips past human discipline. The suggested pre-commit/CI check is the right fix; a generated shell fingerprint is worth evaluating but is a larger change to a deliberately simple deploy story.

Proposed disposition: bump both markers in the next commit before any deploy; queue a TODO row for a mechanical shell-asset-vs-marker check. (Not done in this session per instruction.)

2 · Browser-side secrets, no CSP Confirmed · Accepted risk

Verified: _headers sets only Cache-Control rules — no Content-Security-Policy anywhere. Provider keys, the fal.ai key, and the server session token are long-lived localStorage values. Inline onclick= handlers are pervasive (HTML-by-string-concatenation is a documented project convention).

Factually correct, and the threat model is stated fairly: any same-origin script injection escalates to credential theft. Context the reviewer couldn't have: this is a deliberate consequence of the no-server, bring-your-own-key architecture, and the long-term remediation it proposes — proxying provider calls through a trusted server under a subscription/session model — is already the stated plan (the PROVIDERS table is explicitly documented as the intended server-side routing table). The near-term "strict CSP + migrate inline handlers" suggestion is honest but underestimates the lift: with hundreds of concatenated inline handlers, a meaningful CSP (no unsafe-inline) is a broad refactor, not a header. A CSP that allowlists unsafe-inline would be security theater.

The practical takeaway we accept: finding 3 is the cheap, real mitigation — closing the actual injection sinks matters more right now than a CSP that can't yet be made strict. Session-only key storage as an opt-in is a reasonable middle step worth considering.

Proposed disposition: fold into the existing server-proxy roadmap; consider opt-in session-only key storage; treat CSP as part of the (already-noted) eventual architecture evolution, not a quick win.

3 · Remaining innerHTML injection sinks Confirmed

Verified: ① storage-adapter.js:661 — the legacy fallback assigns synced data.narrativeHtml straight into the story pane via innerHTML (fires only for pre-transcript server blobs; the upload side already sends "" per audit #18). ② char-creation.js:148 — err.message from the portrait-generation catch is rendered via innerHTML; similar err.message-into-innerHTML status lines exist on the neighboring portrait paths.

Both claims are accurate. Severity calibration: the narrativeHtml path requires the attacker to control your own server blob (i.e., your account), and the error path requires a hostile or compromised provider response — neither is a drive-by. But combined with finding 2 (keys in localStorage), the review's "high-impact when it does fire" framing is fair. The remedy is cheap and the direction is one the project already committed to: the transcript is the canonical narrative record, so the legacy HTML fallback is a removable vestige (old blobs degrade to the "Previously:" recap path, which is plain-text). Error messages should render via textContent — that is also simply our own no-silent-failures style done safely. The suggestion to add regression tests with script-like payloads matches the house sabotage-testing doctrine and should be part of the fix.

Proposed disposition: queue as a small hardening TODO — remove the narrativeHtml fallback, sweep err.message render sites to textContent, add a hostile-payload regression test. Drift-surface note: touches the reload/replay path, so it takes the standard Fable-tier review before landing.

4 · Local bible-server write hardening Confirmed

Verified: dev/bible-server.js:24-27 sets Access-Control-Allow-Origin: * (needed today because the editor runs from file://, Origin null); it binds 127.0.0.1 only (line 64) and serves exactly two routes. No write token exists. Its own header comment concedes the shape-vs-intent point the review makes.

Accurate, and the review deserves credit for stating its own mitigating facts (loopback binding, validation). The residual risk is real: while the server is running, any webpage open in any browser can fire a cross-origin POST /install at localhost, and validation ensures the payload is a well-formed bible, not your bible. The exposure window is small (dev-only, run on demand, single-user machine) — P2 is the right priority, not P1. The per-run random token is the correct minimal fix and costs a few lines on each side; it also preserves the file:// editor workflow, which the "same local origin" half of the suggestion would complicate. Take the token, skip the origin change.

Proposed disposition: queue a small TODO — per-run token printed at server start, required on POST /install, entered once in the editor. CORS * can then stay for the file:// reality.

5 · Test-manifest divergence, no CI gate Confirmed

Verified: test.html loads 16 engine scripts; dev/load-engine.js loads 18 — the browser page omits clock.js, table-talk.js, and sound.js, exactly as claimed. The only GitHub workflow is server-health.yml; the 951-assertion suite runs via local hooks only.

Fully accurate, and this finding produced a bonus: while verifying it we found that our own CLAUDE.md load-order table is stale — it documents a 25-script order while index.html actually loads 30 (wasm-probe.js, clock.js, table-talk.js, sound.js, plus reordering). The review effectively caught doc drift our process missed. Both recommendations are sound and cheap: a single shared manifest consumed by dev/load-engine.js and test.html kills the divergence class permanently (very much in the house style — same move as tag_table.js and buildFileMenus), and a GitHub Actions job running node dev/run-tests.js makes the suite unbypassable.

Proposed disposition: queue both (shared manifest + Actions workflow); separately update the CLAUDE.md files/load-order tables to match reality.

6 · Global-script architecture & payload Accurate · Counterpoint

Verified: 30 <script src> tags in index.html; root-level game JS totals ~1.5 MiB (the review's 1.47 MiB figure is consistent with the shell subset it measured). Load order is strict and manual; state is global — all as described.

The diagnosis is accurate and the incremental framing ("do this gradually, not a rewrite") is appreciated. Two-part response:

  • Lazy-loading heavy optional surfaces: agreed. Dynamic script injection after first interactivity is fully compatible with the no-build philosophy, and TTS is the obvious first candidate (the Piper wasm runtime is already deferred; the pattern can extend).
  • Native ES modules: declined on a constraint the reviewer couldn't see. Opening index.html directly from file:// is a documented, supported workflow (dev loop, and the cloud-sync CORS layer explicitly accommodates the null origin). Module scripts are blocked by CORS on file:// origins, so an ES-module migration would quietly kill that path. A small application namespace for new seams — the review's own alternative — is the workable half of the suggestion.

Proposed disposition: adopt lazy-loading incrementally where a surface is genuinely optional; no ES-module migration while file:// remains supported.

On the "recommended order"

The review's sequencing is agreed with one emphasis: item 1 is not merely first, it is a deploy blocker — the working tree cannot ship until the markers bump, because the newest bible content is invisible to every installed client until they do. Items 2–4 are well-prioritized (cheap real fixes before expensive architectural ones). Item 5 is correctly last and partially declined as above.

  • stop-check.js gap — the existing hook checks version-vs-memory drift, not shell-asset-vs-marker drift; the class of miss in finding 1 is currently unguarded.

Bottom line

This is a review worth taking seriously: zero hallucinated claims, reproduced verification numbers, correct severity ordering, and one finding (cache/version) that is genuinely urgent. Its two P1 security items are accurate statements of a trade-off the project made knowingly, with the cheap half (the innerHTML sinks) being immediately actionable and the expensive half (proxy/CSP) already on the long-term roadmap. The single disputed recommendation — ES modules — fails only on the file:// constraint. The reviewer's closing observation is accepted as written: the project turns field failures into safeguards, and findings 1 and 5 are precisely the two places where that discipline exists as a rule but not yet as a mechanism.

Nothing in this response modifies code or acts on any finding. All dispositions above are proposals pending the owner's decision; accepted items would land as TODO.md rows per house process.
