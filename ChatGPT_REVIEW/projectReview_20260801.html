Traffic and Dragons — Engineering Review

Overall: this is a thoughtful, unusually well-defended solo-built game engine. It has excellent operational memory, strong regression discipline, and real attention to mobile failure cases. The primary risks are deployment correctness, browser-side secret exposure, and the accumulating cost of a global-script architecture.

Verification performed: 951 engine assertions passed; JavaScript syntax checks passed; a 12-response parser replay completed with zero handler errors.

What is done especially well

  • The tag system is excellent. One ordered registry drives parsing, stripping, and prompt documentation, avoiding the common parser/prompt drift failure.
  • Save-data resilience is unusually strong: compressed transcripts, corruption rescue, migration logic, quota-aware storage, and loud user-facing failure handling are all present.
  • Cloud sync is designed defensively: debouncing, request timeouts, conflict detection, and a deliberate refusal to overwrite newer server state.
  • The project takes player-facing observability seriously. Breadcrumb/error reporting is a strong answer to the invisible mobile-console problem.
  • Provider, TTS, capability, and campaign-generator abstractions are generally data-driven rather than scattered conditionals.
  • The test culture is a major win. The suite covers hostile/malformed model outputs, migrations, storage failure, sync conflicts, and audio edge cases—not merely happy paths.

Findings

PriorityFilesProblem and why it mattersSuggested solution
P1 capability_bible.js, globals.js, sw.js The newest commit changes capability_bible.js, which is in the cached live app shell, but does not change APP_VERSION or the service-worker cache name. Because the worker is cache-first, an installed client can continue serving old mechanics indefinitely: its service worker sees no changed script and therefore no reason to install a new shell. Before deployment, bump both markers. Add a pre-commit/CI check that fails when any app-shell asset changes without matching APP_VERSION and cache changes. A generated shell fingerprint would eliminate this manual release hazard.
P1 state.js, ui-boot.js, ui-modals.js, _headers LLM, image-provider, and sync credentials are long-lived values in localStorage. There is no CSP. Any same-origin script injection is therefore a credential compromise, not only a visual bug. Long-term, proxy provider calls through a trusted server/session model so browser storage never contains durable provider keys. Near-term, add a strict CSP and migrate inline handlers to event listeners; make persistent key storage opt-in and prefer session-only storage by default.
P1 storage-adapter.js, char-creation.js Normal narration is safely escaped, but two paths still inject untrusted strings with innerHTML: legacy synced narrativeHtml and provider error messages. In combination with stored API keys, this is a high-impact XSS path. The legacy narrative fallback is particularly unnecessary now that transcript replay is canonical. Remove the HTML fallback and migrate old saves to transcript/plain-text replay. Render error messages with textContent. If HTML must survive, use a proven sanitizer and add regression tests containing script-like payloads.
P2 dev/bible-server.js The local authoring server accepts POST /install from every origin and writes validated content into the real bible. Binding to loopback blocks remote hosts, but any webpage opened while the server is running can attempt browser-mediated writes to localhost. Validation protects file shape, not author intent. Serve the editor from the same local origin and require a per-run random authorization token for write requests. Restrict CORS to that origin; do not use * on a write-capable localhost service.
P2 test.html, dev/load-engine.js, .github/workflows/server-health.yml The browser test page claims to mirror the engine list but omits clock.js, table-talk.js, and sound.js; the canonical Node loader includes them. The only GitHub workflow monitors server uptime—tests are local-hook only and can be bypassed. Make one shared manifest the source for both Node and browser test loading, then add a GitHub workflow that runs node dev/run-tests.js. Add a browser smoke test that loads the full production script list.
P3 index.html, dev/load-engine.js The live shell eagerly loads 30 scripts totaling about 1.47 MiB of JavaScript, and runtime state lives in globals with a strict manual load order. The service worker helps repeat loads, but first-launch parsing and main-thread work will increasingly hurt lower-end phones. It also makes refactoring and partial test environments fragile. Keep the no-build philosophy, but introduce native ES modules or a small application namespace for new seams. Lazy-load dev-only and optional surfaces, especially heavy TTS/editor code, after gameplay is interactive. Do this incrementally rather than attempting a rewrite.

Recommended order

  1. Fix the current cache/version release mismatch before deploying the latest mechanics.
  2. Remove unsafe HTML restoration and error rendering.
  3. Put an automated test gate in GitHub Actions and unify test/runtime manifests.
  4. Harden the local bible authoring server.
  5. Plan a gradual module/lazy-load migration around the heaviest surfaces.

The project’s strongest quality is that it already learns from field failures and turns them into safeguards. Applying that same discipline to release invalidation and browser trust boundaries would meaningfully raise its production maturity.
