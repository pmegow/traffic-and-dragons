Module → Blueprint

How “make a blueprint for Tomb of Annihilation” became tomb_of_annihilation.blueprint — written 2026-07-05, and the reusable recipe for the next module.

0 · The one-sentence version

A blueprint is not a summary of a module. It is the minimum set of anchors that keeps the GM canonical while it improvises everything else — a spine of acts, a cast with secrets, a handful of fixed places, and rules that guard the module's soul. Everything that didn't anchor something got cut.

1 · Learn the format from the engine, not from memory

First move was not writing content. It was discovering what a blueprint actually is to the code that consumes it:

  • Read the reference artifact: rise_of_the_runelords.blueprint — the shipped fixture. It answers every shape question by example: top-level keys, act/arc structure, how NPC notes are voiced, how long a location description runs.
  • Read the choke points: normalizeBlueprint() and validateBlueprint() in game.js are the real spec — what fields get defaulted, what fails validation. applyBlueprint() answers the more important question: what does each section become in-game?
  • Query the vocabularies live: tone ids and prose-voice ids aren't guessable — one node command listed TONES (high/gritty/swords/horror/politic/custom) and AUTHORS. Arc types came from the fixture: combat / investigation / exploration / social.
Why this matters: every section of a blueprint has a runtime destiny, and knowing it changes how you write. NPC notes become the GM's private knowledge base (memory.npcs[].knowledge) — so write secrets, not marketing copy. Location descriptions become permanent canonical text injected every time the party is there — so write to constrain drift, not just to evoke. Rules go into the cached stable half of every single prompt — so every rule costs attention on every turn, and must earn it.

2 · Recall the module and find its load-bearing skeleton

Tomb of Annihilation is ~256 pages: a city gazetteer, a hexcrawl the size of a country, two dungeon complexes, and a hundred named NPCs. The blueprint has room for a premise, a handful of acts, and about a dozen cast members. The compression question is: what is the story of this module when you can only keep the spine?

ToA's spine is unusually clean — it's already a three-act structure wearing a sandbox costume:

Module chunkBecameReasoning
Ch. 1 — Port NyanzaruAct 1 · Port of Last HopeThe setup act: patron, stakes, guide, provisioning. Four arcs = the four things every table actually does there (meet Syndra, navigate the princes, pick a guide, first expedition).
Ch. 2 — the hexcrawlCompressed into ONE arc ("The River of Teeth")The engine has no hex grid; the jungle's job in T&D is texture and attrition, which a rule handles better than geography ("Chult itself is an antagonist"). The crawl's destinations that matter (Kir Sabal, Orolunga, Firefinger) survived as locations + arcs instead.
Ch. 3 — Omu + Ch. 4 — FaneAct 2 · The Forgotten City, parallel: trueOmu genuinely is open-order: shrines, the Fane, the Red Wizards can be tackled in any sequence. The parallel flag is the engine's native way to say that — the GM weaves hooks, the player picks.
Ch. 5 — the TombAct 3 · The Tomb of the Nine GodsLinear descent, so a serial act. Three arcs split it at its natural joints: the trap gauntlet, the Sewn Sisters (the one social beat in the dungeon), the Soulmonger finale.

Turning points got special care because the engine uses them as act-transition triggers ([ACT_COMPLETE:]): each one is written as a concrete, recognisable event ("the nine cubes unlock the tomb — and you now know you're in a race"), not a vibe.

What got cut, and the cut rule: Fort Beluarian, Nangalore, Hrakhamar, the Aldani, Needle's Bones, dozens of hexes. The rule: an arc must be an objective a player can complete, not a place that exists. Places with no objective became location seeds (if plot-critical), flavour in other entries (Firefinger rode along inside Azaka's notes AND a location), or nothing. The GM re-invents connective tissue better than a blueprint can prescribe it.

3 · Casting: who earns an NPC slot

Selection test — an NPC earned a seed if they hit at least two of three: plot-load-bearing (the story breaks without them), recurring (multi-act presence), or carrying a secret that changes play when it surfaces. That produced 11 from a module with a hundred names.

  • Secrets go IN the notes. The blueprint is a GM-side document — Azaka's entry says weretiger, Eku's says couatl, Artus's says Ring of Winter. The GM needs the secret on turn 1 to foreshadow it; the player discovers it in play. (This is also why the designer got collapsible cards with a “spoiler cover” default — same doc, two audiences.)
  • Notes are written as play instructions, not encyclopedia entries. "Can be bargained with — his hatred of Acererak's works runs deep — but never trusted" tells the GM how to run Ras Nsi, which is worth more than his history.
  • The guide choice was preserved as a choice — both Azaka and Eku seeded, because "pick a guide, each with their own price" is Act 1's best decision point.
  • Roles stayed coarse (ally/enemy/neutral) — Artus Cimber is neutral on purpose: the entry explicitly frames him as a wildcard, and pinning him as ally would flatten the module's best swing character.

4 · Locations: anchors against drift

Eight locations, chosen because each is somewhere the story must pass through, written as canonical descriptions the engine will inject permanently (the [LOCATION_DESC:] mechanism — written once, never overwritten, re-served every visit). Two crafting rules:

  • Each description carries one fact the GM must not lose: Omu's nine shrines and the temple beneath the palace; the Tomb's six levels and "a cradle no light should ever have touched." These are drift-anchors disguised as prose.
  • Evocative but bounded — a description that over-specifies chokes the GM; one that under-specifies lets Port Nyanzaru become a generic fantasy port. The target register: postcard plus load-bearing facts.

5 · Rules: guard the module's soul, one failure mode each

Rules are the most expensive real estate in the format — injected into every prompt, competing for attention with everything else. So each of the six exists to prevent a specific, predictable failure:

RuleFailure it guards against
"Adapted from ToA — stay true, adapt freely"Canon drift in both directions: inventing a different plot, or railroading against the player.
Death curse as a HUMAN clockThe engine has no doom-counter mechanic; without this the curse evaporates. With it, urgency arrives through Syndra visibly dying and funerals in port — narrative pressure the GM can actually apply.
Jungle as antagonistThe deleted hexcrawl's job, reassigned: travel must cost something even without hexes.
Chultans vibrant, never primitiveThe genre's colonial cliché — a real risk with a pulp prose voice at the wheel. The rule pins the module's own framing.
Trickster gods have personalitiesShrines degenerating into generic puzzle rooms.
The tomb kills fairly — telegraph everythingArbitrary deaths. Acererak works as an author only if the player can lose to their own choices, not to dice noise.
The lesson learned in review (2026-07-05): the trickster-gods rule originally referenced the nine gods without naming them — "(I'jin's caprice, Obo'laka's caution, Papazotl's pride...)". The user caught it: a rule that points at data the document doesn't contain makes the GM improvise exactly the canon the blueprint exists to pin. Fixed by putting the full roster — nine names, animal forms, natures — into the rule itself. New checklist step: audit every name-drop; a blueprint must contain what it references. (Known open instance: the six unnamed merchant princes.)

6 · Tone and voice: mechanical choices, not decoration

"tone": "swords" — ToA blends pulp adventure with tomb horror, but the dominant register is sword-and-sorcery: physical danger, wonder, hostile wilderness. The tone id gates content-DNA in the prompt, so it had to be one of the six real ids from TONES, not a vibe word.

"proseAuthor": "howard" — Robert E. Howard is the closest voice in AUTHORS to what ToA reads like at the table: lush menace, kinetic action, landscape as a character. The blueprint pins it (like Runelords pins Abercrombie); the player can override in Dev Mode.

7 · Validate through the real engine, then keep validating

The file was never trusted by inspection. Verification ran the actual game code headlessly:

node: load globals→data→helpers→state→storage-adapter→memory→api→game
      bp = JSON.parse(tomb_of_annihilation.blueprint)
      normalizeBlueprint(bp)      → must be a NO-OP (file already canonical)
      validateBlueprint(bp)       → null (clean)
      tone id real? voice id real? arc types ⊆ known set?
      top-level / act / npc key shapes === Runelords fixture shapes?

When the schema grew two days later (creatures, arc + act rewards), verification grew with it — all the way into the prompt: applyBlueprint(bp) → worldState.bestiary seeded → buildSysPrompt() stable half contains the BESTIARY block with correct formatting. The blueprint is done when the GM's actual prompt contains what the module needs, not when the JSON looks right.

8 · What the schema couldn't hold (v1, 2026-07-04) — and then could (v1.176+)

The first pass had no home for two module-critical things, and the gap surfaced as designer feedback within a day:

  • Creatures. ToA's monsters are half its identity. v1.176 added creatures[] → the ToA file gained six (King of Feathers, the daylight dead, zombie tyrannosaurus, pterafolk, yuan-ti malisons, grung), each written monster-manual style: what it IS, how it behaves, how it dies. These inject into the stable prompt as a bestiary the GM must stay canonical to.
  • Rewards. Arc rewards (v1.176) and act rewards (v1.178) — completion pays out in the same response as the [ARC_COMPLETE:]/[ACT_COMPLETE:] emission, including props a later arc needs (the puzzle-cube pattern is literally ToA's plot).

Moral: the module conversion and the schema evolve together. When a module has something important with no schema home, that's a schema feature request, not something to cram into a rule.

9 · The reusable checklist

  • Read the current reference blueprint + normalizeBlueprint/validateBlueprint/applyBlueprint — the code is the spec, and each section's runtime destiny dictates its writing style.
  • List valid TONES ids and AUTHORS ids live; pick one of each for the module's register.
  • Find the module's act structure (usually 3). Turning points = concrete recognisable events, they drive [ACT_COMPLETE:].
  • Arcs = completable objectives, never places. Flag genuinely open-order acts parallel. Type each arc (combat/investigation/exploration/social).
  • Cut ruthlessly: anything that anchors nothing becomes GM improvisation, which is a feature.
  • Cast by the two-of-three test (load-bearing / recurring / secret-that-changes-play). Secrets go IN the notes; notes are run-instructions.
  • Locations: only must-pass-through places; each description carries its load-bearing facts.
  • Creatures: the module's signature monsters, written as nature + behaviour + how it dies.
  • Rewards on arcs and acts — especially props later content depends on.
  • Rules: one per predictable failure mode, each earning its per-turn prompt cost. No lore-dumps as rules.
  • Name-drop audit: everything a rule, note, or description references by name must be defined somewhere in the document.
  • Validate headlessly through the real engine: parse → normalize no-op → validate clean → shape-diff vs the reference fixture → (for prompt-injected sections) applyBlueprint → buildSysPrompt and read what the GM will actually see.
