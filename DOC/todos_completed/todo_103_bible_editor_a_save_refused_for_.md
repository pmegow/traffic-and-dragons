## Status / record

✅ **SHIPPED v1.481 (2026-07-28).** **① The save was CORRECT to refuse.** The FSA API blocks `createWritable()` when the file changed on disk after the handle read it — here because the session's own commits rewrote class_bible.js while the editor tab held an older view. The browser was refusing to let a stale editor clobber a newer file, which is exactly right; the raw wording just explained none of it, and the old handler then fell back to a download as if the write had merely failed. Now that case is detected (`InvalidStateError` / the message probe) and stated in the user's terms — what happened, why the browser refused, and the only correct recovery — with NO misleading download fallback. **② `↻ Reload from disk`** (user request): re-reads the open file through the existing handle, confirming first if the tab has unsaved edits. It is the named recovery for ①, and the general answer to a file that moved underneath a long editor session. Explains itself when there is no handle rather than throwing. **③ `⌫ Clear merged (N)`**: additions whose name now RESOLVES in the shipped bible are dead weight — the define-form flow exists only to author MISSING capabilities — but nothing ever removed them, so the count reported 4 forever (3 had shipped at v1.468). The button appears only when N>0, names them in its tooltip, confirms, and **keeps additions not yet in the bible**. Deliberately NOT an auto-prune: silently deleting authored data is the worse failure. 894 green. Live-verified against the user's exact four staged entries restored through a real draft: 4 → 1 (fog bank/flash/leap cleared, poisoner kept), tooltip correct, button hides, **the cleanup survives a page reload** (the debounced draft write was checked explicitly — an unpersisted clear would have reproduced the original "it's still there" complaint), no-handle reload explains itself, zero console errors. 



**v1.485 — THE SAVE ACTUALLY WORKS NOW (user: "I have not yet been able to save from the bible editor. It's always blocked somehow").** v1.481 EXPLAINED the refusal but gave no way THROUGH it, and this session then rewrote class_bible.js on ~10 commits, re-staling the handle within minutes of every recovery — explaining a wall repeatedly is not fixing it. **`saveBible` now re-reads the file through the handle BEFORE writing.** Two jobs in one read: it refreshes the cached snapshot the browser was rejecting (so the common case just works), and it compares the file's mtime against the one observed at load, so a real disk change is detected UP FRONT where it can be explained and **chosen about** (overwrite with your version · cancel and reload) instead of surfacing as an opaque `InvalidStateError` after the fact. mtime is captured on every load path (open/reconnect/reload) and re-baselined after a successful write. **`diskChangedSinceLoad` is extracted between markers and pinned by a new SAVE STALENESS CONTRACT** — and writing that test CHANGED THE CODE: the comparison is `!==`, not `>`, because a sync client or `git checkout` can restore an **older** timestamp and `>` would sail past it and clobber. Three clauses, all sabotage-proven. **Also fixed a silent-data-loss path found while writing the recovery advice:** `openBible` replaced the tab's contents with NO guard, so opening a file with unsaved edits destroyed them wordlessly (the same class the reconnect path already guarded) — it now confirms and points at Download copy first; the contract pins the guard. If a save still fails after the re-read the handle is genuinely beyond use (the file was REPLACED rather than edited in place), and the message now says so and names the one thing that always works: re-open the file, minting a fresh handle inside the user's own click. 895 green. ⚠ **HONEST LIMIT:** the FSA round-trip cannot be driven from the harness (the picker is an OS dialog needing a real user gesture) — the logic is pinned and the mechanism sound, but **end-to-end confirmation is the user's next save**.
