## Task

**Re-evaluate TTS providers — hosted (Inworld / Cartesia) + local (Kokoro desktop; Piper / Kitten phone) — pricing is just better.** Inworld's voice/TTS pricing beats Cartesia's per-*character* billing, which is the documented TTS cost pain (see #12: shorter prose to cut the Cartesia bill; a `402` = character-quota exhausted). Swap surface is small and already abstracted: `tts.js` routes Cartesia ↔ native browser voice through one path (`speak()`, key in `KEY_K`, native fallback + red-error indicator per #19), so adding a provider is another adapter in the same shape, not a rewrite. **Three contenders, two categories:** ① **Cartesia** + ② **Inworld** are hosted APIs (keyed, per-character billing, ongoing cost, network latency) — the straight cost swap; ③ **Kokoro** is a different animal — open-weight (~82M param, Apache-licensed) local/self-hosted TTS at **$0/character marginal cost**. Kokoro trades the billing line for a hosting + latency + quality tradeoff and **does NOT fit the "route TTS through the T&D server as a keyed proxy under the subscription model" shape** — it'd be a self-host/on-device adapter, not a proxied-key one, so weigh it as an infra decision, not just a price line. **When building:** ① confirm CURRENT Inworld + Cartesia TTS pricing + free tiers (pricing moves — verify at build time); ② A/B voice quality/latency across all three on real narration (cost only wins if the voice holds up for car-audio, the primary use case — Kokoro especially must clear that bar to justify the self-host burden); ③ mirror the existing fallback discipline (key-missing / request-failed → native voice + reason indicator); ④ keep it provider-agnostic like the LLM `PROVIDERS` table so TTS providers become a swappable list, not a hardcode.
