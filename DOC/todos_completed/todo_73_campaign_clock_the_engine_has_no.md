**Effort:** M · **Tier:** Fable

## Task

**Campaign clock — the engine has no concept of a DAY, so any in-fiction deadline is pure hallucination.** TLDR: the Runelords campaign has a solstice countdown the story treats as load-bearing, and the GM invents a different number every time it is asked, because nothing anywhere stores one. Evidence (2026-07-19, live Table Talk): asked "how many days to the solstice", the GM answered **11**, then **8**, then **94** — three confident answers, no stored fact behind any of them — and it emitted `[CALENDAR:11 days to winter solstice]` and `[DAYS_TO_SOLSTICE:94]`, **invented tags for a system that does not exist** (grep for solstice/CALENDAR/DAYS_TO across tag_table/state/api/globals returns zero hits). So the GM believes it is recording the countdown; nothing is listening. The only clock today is free-text `[TIME:]` ("dusk", "midday") with no advancement — CLAUDE.md §7 already notes this. **Design questions for the fresh session:** what advances a day (GM tag? travel? rest? an explicit `[DAY_PASSES:n]`?); where it lives (`worldState.world` beside time/weather is the obvious home); whether countdowns are FIRST-CLASS (a named deadline with a target day, so "days remaining" is COMPUTED not remembered) or just a day counter the GM does arithmetic against — computed is far safer given the evidence; how travel interacts (the trigger case was a 3-day ride, a day on site, a 3-day ride back); what the GM is shown each turn (one "Day 94 · 11 days to winter solstice" line in the volatile half would do it); and whether existing saves get a starting day or opt in. ⛨ Drift surface — new tag + buildSysPrompt injection + migration; the anti-hallucination win IS the point, so the injected line must be authoritative and the GM must never be asked to remember a number it can compute.
