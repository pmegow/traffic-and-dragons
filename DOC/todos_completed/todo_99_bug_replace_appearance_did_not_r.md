# TODO #99 — BUG: "Replace appearance" did not replace the appearance.

*Full record extracted verbatim from TODO.md (Feature backlog, completed row) on 2026-09-01; the tracker row keeps the TLDR and the verdict. Table pipe escapes (`\|`) are unescaped here; `<br>` breaks became paragraphs.*

**Effort:** S · **Tier:** Any

## Task

**BUG: "Replace appearance" did not replace the appearance.** Reported 2026-07-27 from the "appearance read from the portrait" panel. **Two distinct defects behind one symptom.** **① Display (every subject):** the write landed but nothing repainted the sheet under the portrait modal, so the old text stayed on screen until the sheet was closed and reopened — for the PLAYER the data had in fact persisted the whole time, which is why it read as "doesn't seem to" rather than a hard failure. **② DATA LOSS (sheet-less party members):** `showNpcSheet` builds `npcSubject` as a THROWAWAY object literal when the NPC has no `charSheet`, and the handler wrote `c.appear = desc` straight onto it — the description went into an object discarded on close, `saveAll()` then saved state nothing had changed, and a success toast claimed otherwise. Reachable in normal play: a `[PARTY_MEMBER:]` join creates an NPC with no sheet (exactly why the ✦ Generate Character Sheet button exists), and the avatar/portrait button renders for any party member. **Fix (v1.460):** a caller-supplied `setAppearance` seam, the same shape as the existing `getPortrait`/`setPortrait` pair. The default writer targets the player and repaints `#cs-modal` (a separate element from `#portrait-modal`, so the portrait modal stays open). `showNpcSheet` supplies one that writes `wsNpc.charSheet.appear` and repaints the NPC sheet; with no charSheet it REFUSES with a toast pointing at Generate — without a sheet nothing would ever READ an appearance anyway (the sheet renders it from charSheet, and `doRender` pulls party descriptions from charSheet), so a "successful" write would be a second silent lie. A refusal deliberately leaves the generated text on screen rather than discarding work that cost a vision call.

## Status / record

**v1.461 follow-up — repaint on CLOSE, not per write (user's call, and the better seam).** User confirmed the data was updating and pinpointed the remaining symptom: "the text didn't update in the already opened sheet… I think we just need to rerender the character sheet when the edit portrait UI closes." Correct — and measurement showed why v1.460's per-write repaint was the wrong seam: the portrait modal renders at **z-index 400** over the sheet's **300** (verified live via `elementFromPoint`), so a mid-flow rebuild is invisible to the user, and it only covered the appearance handler while portrait and framing edits still relied on the avatar-only `refreshFn`. Now `pmClose()` does `modal.remove()` then, if anything was actually written, `refreshSheet()`; `modalShell`'s `onClose` routes through `pmClose` so the × button and an outside-click repaint too, not just the three internal close paths; a `_pmDirty` flag keeps a look-and-leave close from rebuilding the sheet and resetting its scroll; and `showNpcSheet` supplies its own `refreshSheet` instead of the writer tearing down its parent modal mid-flow. **Verified live through the REAL buttons** (not stubs): open sheet showing old text → Describe → Replace → close → sheet current with no reopen, old text gone; same for an outside-click close; a clean close rebuilds nothing (0 calls). Contract extended to pin the mechanism (pmClose repaint, onClose routing, all six dirty-marking write paths) and **sabotage-verified** — removing the repaint trips it by name. Note for future work: **any sheet-visible field edited from a modal that overlays the sheet needs this repaint-on-close treatment**; the sheet is a static render.
