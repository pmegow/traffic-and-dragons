# TODO #105 — Locations are frozen in their first-visit state — a place the party materially changed is still served to the GM as intact.

*Full record extracted verbatim from TODO.md (Feature backlog, completed row) on 2026-09-01; the tracker row keeps the TLDR and the verdict. Table pipe escapes (`\|`) are unescaped here; `<br>` breaks became paragraphs.*

**Effort:** M · **Tier:** Fable

## Task

**Locations are frozen in their first-visit state — a place the party materially changed is still served to the GM as intact.** TLDR: the party destroyed a large part of the sea cave, and ~700 turns later a new quest re-offered it as though nothing had happened, because nothing in the engine ever tells the GM what a location looks like *now*. **Promoted from [DOC/BUGS.md](DOC/BUGS.md) B17 (field report 2026-07-23, v1.427, Rise of the Runelords t1059) — already root-caused there; the full seven-leg investigation stays in the bug row, this row owns the build.** **The mechanism:** `[LOCATION_DESC:]` is write-once by design (anti-drift, CLAUDE.md §9) and `buildGeoBlock` describes the CURRENT node only — so there is NO channel at all that serves a remote location's history to the GM. The field built for exactly this is dead code: `fileLocation(loc,note,turn)` writes `memory.locations[].notes[]`, but its only caller passes a hardcoded empty string (tag_table.js:211) and nothing reads it for injection. Map nodes have no changed/damaged field; `[LOCATION_ITEM:]` covers named items only. The recency windows had scrolled past (STORY SO FAR = last 8 chapters, RECENT DECISIONS = last 5), and RAG's location bonus (`if(q.loc&&en.e.l===q.loc)sc+=2`, memory.js:543) only fires when the party is physically AT the location. **The structural trap:** the prompt is frozen BEFORE generation, but the GM decides to reference the cave INSIDE its own output — so every mention-triggered mechanism (the `memoryNpcDetail` last-6-messages pattern) keys off already-said text and cannot help. A fix must be ALWAYS-PRESENT (compact roll-up) or next-turn-reactive, never predictive. **Fix sketch (direction only, not ratified):** a durable per-node state-change log distinct from the immutable description — `stateNotes[]` on the map node (capped 3-5, lore/futureEvents cap discipline), written by a new dedicated tag (`[LOCATION_STATE:note]`, sibling of `[LOCATION_ITEM:]`), surfaced as a compact always-present one-line-per-changed-location roll-up near memoryTOC's VISITED lines. **⚠ Drift surface — Fable-tier by decree, design review BEFORE any code.** The write-once rule exists for a measured reason and must not be reopened. Silent-failure classes a careless fix invites: unbounded notes → volatile-half bloat; a mutate-instead-of-append tag reopens description drift; wiring through RAG's location bonus inherits the exact gate that caused the bug; any leak into the STABLE half kills prompt caching campaign-wide.
