TLDR

When the game hits a runtime error on a device where you can't see the console — your phone, the car — it now emails you the details instead of dying silently. A new file, error-report.js, catches errors from eight places in the app (including the Piper narration-death forensics), packages them with the app version, campaign, turn, and device info, and POSTs them to a tiny Google Apps Script webhook that forwards the report to pmegow@gmail.com. Flood control means a cascading failure sends one email per 30 seconds, not fifty.

Current state: the game side is fully built, tested, and pushed — but switched off, because the webhook half is a ~10-minute Google-account step only you can do. Until that URL is pasted into ERROR_WEBHOOK_URL, nothing about the game's behavior changes. And per last night's conversation: the whole thing sits in one clean-revert commit, so "keep, adjust, or discard" is still an open question — the open decision points are at the bottom.

Why this exists

Two incidents in one evening made the case. The Piper narration deaths surface as a toast on the phone — 8 seconds in a moving car, then the forensics are gone. And the desktop "input cut off" report couldn't be diagnosed because the evidence lived in a console nobody was looking at. The pattern: the app already detects its failures loudly (the no-silent-failures rule), but on mobile the loudness goes nowhere. This feature gives every existing loud-failure path a destination that survives the moment.

How a report travels

Error → inbox, step by step

  1. Something breaks. An uncaught exception, a failed GM turn, a summarize failure, a narration death detected at boot — any of the wired sites below.
  2. The catch site calls reportError(context, message, detail) — every call is typeof-guarded, so even a missing/stale error-report.js can never itself throw.
  3. The flood gate decides. No webhook URL → do nothing (one console note). Already sent 10 this session → stop (boot-loop guard). Sent something in the last 30s → count it and wait — the count rides the next email as "N earlier errors suppressed."
  4. The payload is built: context, message, detail (stack trace, capped 4KB), app version, campaign + turn, page URL, device user-agent, online/offline flag, timestamp.
  5. One fetch POST to the webhook. Deliberately a "simple request" — plain body, no custom headers — because Google Apps Script can't answer CORS preflight. A simple request skips preflight entirely, and delivery success/failure is still readable and console-logged.
  6. The Apps Script receives the JSON and calls MailApp.sendEmail() — subject line like [T&D v1.352] narration-death: ⚠ Last narration died at sentence 1/35…, body with every field labeled.

Flood control — why a cascade can't melt the inbox

  • 30-second debounce. First error sends; everything inside the next 30s is counted, not sent. The next accepted email carries suppressed: N — so a cascade reads as one email saying "and N more followed," which is usually the more useful signal anyway.
  • 10 emails per page load, hard stop. A boot-loop that errors on every reload gets 10 chances per session, then silence (with a console warning). Google's MailApp quota (~100/day) is the outer wall.
  • Reentrancy latch. If the reporter itself throws, it cannot recurse through window.onerror back into itself — verified by a test that makes the transport explode.
  • 4KB detail cap keeps a pathological stack trace from becoming a megabyte email.

What it deliberately does NOT do

  • No behavior change when unconfigured. Empty ERROR_WEBHOOK_URL = every call is a cheap no-op (one console note the first time). That's how it shipped.
  • No UI. No toasts about reports, no settings modal. The existing error surfaces (toasts, system messages) are untouched; this only adds a destination.
  • No new dependencies. ES5, no libraries, one file loaded second (right after globals.js) so the catch-all hooks exist before any other file can fail. Added to the SW app shell and the engine-test loader; 5 new suite tests (619 green) pin the debounce, cap, payload shape, truncation, and the can't-recurse guarantee.

User-initiated reports (#16b) — "not all bugs are crashes"

The second species: nonsense action suggestions, hallucinations, drift, broken screens — things only a human notices. File ▸ ⚠ Report bug (game screen): the menu closes, the game screen is screenshotted, and a modal opens with the thumbnail, an editable text box, and a Send button.

  • The screenshot is a DOM re-render, not a real screen grab — browsers don't let a page screenshot itself without a permission picker (which doesn't exist on iOS at all). The vendored html-to-image library inlines the page into an SVG; we rasterize it to JPEG ourselves, because the library's own rasterizer awaits img.decode() + requestAnimationFrame and hangs in embedded Chromium (found live during the build). 8-second timeout; any capture failure degrades to a text-only report with a console note — never a blocked report. Known limit: iOS WebKit taints the canvas for this SVG type, so iPhone reports are text-only by design.
  • Auto-attached context: a state digest (name/class/HP/gold/location/turn), the last 5 exchanges, the newest GM response with its state tags intact (was the tag missing, or the prose wrong? — half of every drift diagnosis), and the suggestion buttons on screen.
  • The hint table: the report text is scanned for topic keywords — mentioning quests, rendering, the model, voice, combat, memory, or sync attaches that subsystem's settings (one table, ER_REPORT_HINTS, one entry per topic). API keys and tokens are never gathered; the sync hint sends a connected boolean, never the token.
  • No crash debounce — the player pressed the button, they meant it. Just an in-flight latch, and send failures show inline in the modal with the typed text preserved.
