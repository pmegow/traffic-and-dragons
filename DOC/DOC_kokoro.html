Kokoro on the Voice Server — the M2 quality upgrade

Spec R1, 2026-07-24 · TODO #91 · gated on the D4 benchmark (ratified 2026-07-24) · builds on the live M1 tnd-tts app (DOC/DOC_server_tts.html) · engine v1.439

⛔ M2.0 RESULT — D4 GATE FAILED (measured on the live box, 2026-07-24). Kokoro does not ship. Not close, and not for the reason the spec expected: RAM was a red herring, CPU is the wall. Numbers in "M2.0 — benchmark results" below. Headline: Kokoro q8 runs at RTF ≈ 2.1 at full burst (the bar is ≤1.0), then collapses to RTF 22–34 once sustained load exhausts the shared-CPU burst balance — one 7-second line took 3 minutes 56 seconds. Piper on the same box does RTF 0.16. Verdict: M2 is blocked on economics, not on code — every decision below (K1–K3, K6) stays valid and rebuildable the day the CPU math changes, but nothing should be built against it now. The pragmatic quality upgrade is already in hand — see "The alternative that needs no new engine" at the foot of this page.
Why this exists. M1 proved the pipe: server-side Piper, same 19 voices, B9 dead. Kokoro-82M (Apache-2.0, StyleTTS2-derived) is the quality jump behind the SAME endpoint: markedly better prosody than Piper mediums, ~24–50 voice packs, and voice blending (style vectors are small tensors — a weighted average of two packs is a new voice), which is the real prize for per-character casting. Self-hosted on our own box, so the ownership decision that killed Cartesia/LiveKit stays intact. D4 (ratified): M2 ships only after a Fly CPU benchmark shows ≥1× realtime on the chosen instance; "near real-time on common CPUs" is the ecosystem's claim, not a measurement of a shared-cpu-1x — the gate exists because nobody has run it there.

K2 — Routing: the voice id IS the engine selector

Kokoro ids are namespaced kk_* (e.g. kk_af_bella, kk_bm_george). The server routes on the prefix: kk_ → kokoro, else → piper. The M1 engine param stays accepted for compatibility but is redundant — one source of truth, no way for the param and the id to disagree. Allowlist discipline identical to M1: a curated KOKORO_VOICES list mirrored client/server; unknown ids 400 before any download. 
POST /api/tts   (unchanged shape)
  { text, voiceId: "kk_af_bella", rate }         → 200 audio/wav (24000 Hz mono PCM16)
  { text, voiceId: "kk_mix:af_bella@0.6+af_sky@0.4", rate }   → blended style vector (M2.5 — syntax
                                                    reserved and parsed server-side from day one;
                                                    the picker UI for it ships later)

Client decode is already rate-agnostic — _wavToAudioBuffer builds the buffer at the WAV's own fmt.sampleRate and WebAudio resamples, so 24kHz needs zero client decode changes (verified against the v1.439 source).

K3 — The real client design work: tier-aware voice resolution

The wrinkle M1 never had: every M1 voice exists on BOTH tiers (same 19 Piper ids locally and server-side). A kk_ voice exists ONLY on the server. Three shipped code paths break if this isn't specified:
  • The ladder handoff. A server read failing mid-read unshifts its remainder onto local Piper with the passage voiceId — a kk_ id local Piper cannot load.
  • resolvePiperVoice's snap guard. A campaign narrator pinned to kk_af_bella would be "unknown" to the curated Piper set and silently snapped to the Piper default — eating the player's choice on every resolution.
  • characterVoiceId / speaker maps. Same membership test, same wrong snap.

Spec: introduce ONE classification helper and thread it through the four touchpoints — no scattered prefix checks (the abstraction rule):

voiceTier(id)  →  "kokoro" (kk_ prefix) | "piper" (curated set) | null (unknown)

narratorVoice(tier)   — the narrator for a GIVEN tier: the campaign/device pin when its
                        tier matches, else that tier's default (Piper: libritts_r;
                        Kokoro: a curated default pack). The pin STORES whatever the
                        player picked; resolution is per-tier, the pin is never rewritten.

characterVoiceId(char, tier) — the character's own voice when voiceTier(it)===tier,
                        else narratorVoice(tier). A kk_-bound character on a piper
                        read speaks in the piper narrator voice — graceful, loud once.
  • _speakServer asks for tier "kokoro"-or-"piper" ids untouched (the server speaks both); its HANDOFF unshift converts the remainder's voice via narratorVoice("piper") when the passage voice is kk_ — the existing degrade toast already tells the player.
  • _speakPiper's per-unit map lookup runs through characterVoiceId(char,"piper") — a stored kk_ assignment can never reach predict().
  • The sheet Voice dropdown gains a "Server voices (cloud)" optgroup, shown only when the server tier is configured; picking one while unconnected is allowed (it's a preference) with the sub-line noting it speaks only on server reads.
  • Blueprint narratorVoice validation (TTS.voiceKnown) accepts both namespaces; the E20 no-clobber rule unchanged.

K4 — The D4 benchmark, concretely (the gate)

Run BEFORE any M2 code is written. A bench script in the server repo (tts/bench-kokoro.mjs, dev tool, not routed) executed on the live box via fly ssh console — the same shared-cpu-1x that will serve it, not a laptop.
  • Corpus: 30 units at real narration lengths — 10 short (~40 chars), 10 median (~120), 10 long (~220, the MAX_UNIT ceiling) — from an actual transcript, not lorem ipsum.
  • Matrix: quantizations q8, fp16, fp32 × cold-load time × sustained RTF (30 units back-to-back, report median + p95) × RSS before/after.
  • Pass (D4): sustained median RTF ≥ 1.0× at a quant whose output passes an ear check (spot-listen the 30 WAVs — q8 artifacts are the known risk); p95 unit latency ≤ the client's 10s mid-read timeout with margin; RSS verdict feeds K5.
  • Comparison row: the same corpus through the resident Piper daemon (M1 measured ~0.16 RTF — 6× realtime) so the cost of quality is a number, not a vibe.

M2.0 — benchmark results (the gate, run 2026-07-24)

Script: tts/bench-kokoro.mjs (server repo) · executed on the live tnd-tts machine via fly ssh console · kokoro-js + onnx-community/Kokoro-82M-v1.0-ONNX, dtype q8, voice af_bella · corpus = 30 real narration units (10 short ≈37ch / 10 median ≈102ch / 10 long ≈213ch)

Run A — 1GB (the shipped config): OOM before a single synthesis

  • Model loaded (cached on the volume) in 18.0 s, RSS 75 → 273 MB.
  • Process was killed during its first warm-up synthesis. Machine memory at the time: 985 MB total, three warm Piper daemons resident (the live session's), ~119 MB free.
  • Conclusion: Kokoro cannot coexist with the Piper daemons the app must keep warm on a 1GB box.

Mechanism — shared-CPU burst exhaustion (strong hypothesis, evidence-backed)

Units 1–8 consumed ≈48 s of continuous 100% CPU, then throughput fell off a cliff in a single step (2.1 → 22.65) and kept degrading — the signature of a shared-cpu-1x burst balance running out and the machine being throttled to its baseline share. It is a step, not a ramp, so it is not a memory leak or GC drift; loadavg stayed ~1.0–1.36 throughout (busy, not blocked). Piper never trips this because each unit costs ~0.16× realtime — it sips the balance and lets it refill between reads. Confirming test if ever needed: idle the box 10 minutes and re-run — if units 1–8 are fast again, burst is proven.

The comparison that settles it

Engine (same box, same corpus class)RTFMeaning
Piper medium (shipped, M1 production logs)0.166× faster than realtime — 200 ms for a 3 s line
Kokoro q8, best case (full burst)2.113× Piper's cost; already 2× over the D4 bar
Kokoro q8, sustained (throttled)22–34unusable — exceeds the client's 10 s unit timeout on every unit

Even the best Kokoro number fails D4, and the client's 25 s lookahead cannot hide RTF > 1 — the buffer drains monotonically once synthesis is slower than playback. Quantization down to q4 would need to buy a 2×+ speedup just to reach parity with the bar, before the throttle question is even asked.

K5 — Box sizing (decided BY the benchmark, not before)

Resolved by measurement: no RAM tier fixes this. 2 GB makes Kokoro run; it does not make it fast. Reaching RTF < 1 with margin needs dedicated cores (performance tier, no burst throttling) and probably multi-threaded ORT — a materially different cost class that K5 says requires explicit user ratification, and which buys an engine still ~13× Piper's cost per second of audio.

K6 — Catalog & casting

  • English packs only for v1 (~24–26 en_US/en_GB voices). Curate exactly like the Piper 19: the official pre-rendered samples through a voice_picker.html-style pass; user picks the keepers; ships as KOKORO_VOICES (client display + server allowlist). Gender tags from day one — the #9⑨ lesson, don't re-create the missing-attribute gap.
  • Model + packs live on the /data volume (D5's 3GB has room: model ≤330MB even at fp32; style vectors are KBs). Download-on-first-use like M1, .part+rename discipline.
  • Blending is M2.5: the server parses kk_mix: from day one (cheap — it's a weighted vector average), but the mixer UI (sliders on the sheet voice control) ships as its own small pass after single-pack casting is field-proven.

The alternative that needs no new engine (recommended next move)

Piper's own "high" voices are a quality upgrade already sitting in the shipped catalog — en_US-libritts-high (904 speakers, and already downloaded on the server volume), en_US-lessac-high, en_US-ryan-high, en_GB-cori-high. Same engine, same daemon machinery, same endpoint, no new dependency, no box change, no client work beyond a narrator/character voice pick the UI already supports.

The honest caveat: a "high" model is a bigger network than a medium, so it costs more CPU per second of audio — unmeasured. But the headroom is enormous: Piper medium runs at RTF 0.16, so a high model could be 6× slower and still clear the D4 bar, where Kokoro needed to get 2× faster just to reach it.

Proposed M2′ (small, cheap, decisive): point the same harness at the piper daemon — medium vs high on the identical 30-unit corpus — and get the RTF and quality delta. If high lands anywhere under ~0.6, it ships as a voice-catalog preference with zero architecture change, and #91 closes as "quality upgrade delivered by a different route."
