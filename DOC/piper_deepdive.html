Piper narration kills the iOS tab — a from-the-outside deep dive

Bug B9 · assembled 2026-07-23 · engine v1.428 · Piper runtime r9 · method: a 14-agent research fleet (12 web-research scouts across the Piper / onnxruntime-web / WebKit / Web-Audio stack + 1 code-mapper of our own integration + 1 synthesis organizer). This document is the research writeup and the applied gap audit of our integration.

Why this document exists

We have "found the solution" to B9 several times and the field has said no every time. The pattern is a fix built on a variable measured from inside our own assumptions. This pass deliberately went outside: learn what the world actually knows about running Piper/ONNX inference in an iOS browser, then hold our integration up against it atomically. The result is convergent and, for the first time, points at a part of the system we have never touched — because our one mitigation cannot reach it.

The bug, in facts we have already proven

Narration dies mid-passage on iPhone Safari (iOS 18). The tab is killed by the OS with no pagehide / unload / visibilitychange — a WebContent-process jetsam. Twenty-five field breadcrumbs across ten versions establish, and this document treats as settled:

FACT A — Death tracks cumulative synth COUNT (pc ≈ 90–132), not wall-clock, turns, uptime, or voice switches.
FACT B — ORT/WASM linear memory at death spans 248–624 MB and is NOT the predictor. Tabs die at 248 MB and at 624 MB alike.
FACT C — Moving synthesis into a disposable iframe realm that is periodically torn down did not help. Deaths are identical realm-vs-in-page.
FACT D — The espeak-ng phonemizer is flat at ~16 MB all session.
FACT E / F — ORT session options (enableMemPattern etc.) and input-shape bucketing both had no effect.

Forced conclusion: something accumulates once per synth() that is not ORT linear memory, and eventually crosses an iOS process-kill threshold. The whole investigation is: what?

Part 1 — What is actually known about this stack

1.1 Our synthesis unit, precisely

One synth = text → espeak-ng-wasm phonemize → VITS ONNX graph via onnxruntime-web (WASM/CPU EP) → one Float32 PCM output → WAV-encoded ArrayBuffer → Blob → decode to AudioBuffer → AudioBufferSourceNode → scheduled on a single shared AudioContext. This is the same shape as every community port (diffusionstudio/vits-web, mintplex, thewh1teagle/piper-onnx). high confidence

The split that matters: a single GM response is broken by splitSentences(…commaSplit) into multiple speakable units, each its own predict() + its own AudioBuffer + AudioBufferSourceNode. So pc = 90–132 is a floor on the number of Web-Audio buffer creations, not a 1:1. The real per-response audio-object churn is higher. tts.js:1511, 1559–1646

The architectural fault line: synthesis (ORT + espeak + all wasm) runs inside a hidden same-origin iframe realm (piper-host.html). The entire playback layer — AudioContext, decode, createBufferSource, scheduling, _sources[] — runs in the main page. The disposable-realm respawn only ever tears down synthesis. It has never been able to touch playback. tts.js:414, 1627–1646 · piper-host.html:108–113

1.2 Why ORT/WASM linear memory is correctly excluded

  • WebAssembly.Memory only grows, never shrinks (spec-level, engine-agnostic including JSC), and ORT's BFCArena extends in power-of-two chunks and never returns pages by default — but all of that lives inside the single linear-memory buffer whose byteLength we already measured and found non-predictive. The mechanism is real but already captured by the ruled-out metric. MDN Memory.grow · emscripten #19470 · onnxruntime bfc_arena.h
  • Every publicly documented ORT-web leak is per-session, not per-run: #18165 (~300 MB at session creation, never released, closed not-planned), #21673 (leak persists after session.release(), memlab-confirmed, unfixed). A cached-session build like ours would show these as a one-time jump, not linear-with-count growth — the wrong signature for FACT A. onnxruntime #18165, #21673
  • The two most plausible arena-growth triggers were already falsified on-device (FACTS E, F) — jointly excluding shape-varying execution-plan-cache growth as the cause. high confidence

1.3 iOS jetsam — what actually judges the kill

  • Jetsam is a kernel decision on the WebContent process's TOTAL resident footprint — malloc zones, the JS VM Gigacage, IOSurfaces/GPU-process buffers, JIT code pages, and native Core Audio buffers. A WASM-heap byteLength reading is only one slice. This is exactly why a single-allocator number can be non-predictive while the real footprint climbs. high confidence docs.webkit.org MemoryInspection · catchmetrics.io WebKit RAM deep-dive
  • A jetsam kill fires no JS event (WebKit #199854) and there is no JS-reachable early-warning API on iOS — measureUserAgentSpecificMemory and performance.memory are both Chromium-only. The page cannot detect approach or self-throttle. Only "reduce total accumulated footprint" works — never "catch and recover." WebKit #199854 · MDN · caniuse
  • The device ceiling is variable and system-load dependent (~200–450 MB on older iPhones to 1 GB+ on newer), and the kill tracks resident footprint at check time, not growth rate — consistent with death-tracks-count and the 248–624 MB spread. medium confidence

1.4 Why the disposable-realm teardown was structurally unable to help (FACT C, explained)

  • iOS Safari shares ONE WebContent process between a page and its same-origin iframes by default (site isolation is opt-in / newer). Our synthesis iframe is same-origin, so it was never a separate process — there was no process footprint to reclaim by destroying it. docs.webkit.org SiteIsolation
  • Tearing down a same-realm iframe reclaims only GC-reachable JS/wasm objects inside that realm. It cannot free process-scoped native resources — OS threads, JIT code pages, Gigacage reservations, or native Web Audio objects. If the accumulator is any of those, realm teardown is a no-op by construction — matching the observed result.
  • Independently, the respawn cannot touch the playback layer regardless of process model: the AudioContext and every buffer/source object live in the main page, not the iframe. Even a perfect realm teardown leaves the entire Web-Audio object graph intact. tts.js:414, 1627–1646, 1782–1852

This is the pivot of the whole investigation. FACT C was read all session as "memory isn't the cause." The sharper reading: the one thing we can reclaim (the iframe's wasm) is not where the accumulation lives. We have been draining the wrong tank.

1.5 The live suspect space — non-linear-memory native accumulators with WebKit precedent

Web Audio native object/thread leaks. WebKit has shipped count-gated kills where a JS-collectible audio object pins a native resource GC can't reclaim, invisible to heap/WASM instrumentation: #198964 OfflineAudioContext pinned a thread, crash at ~2028 instances, ~40 KB each; #224279 crash at ~26–60 instances on iOS 14 via an AudioDestinationNode circular ref. Same fingerprint as ours: fixed count, trivial measured memory. Both were fixed on old iOS — so this is precedent, not proof, for iOS 18. high confidence (as a class)

Gigacage fragmentation. WASM linear memory, typed arrays and SharedArrayBuffer share one protected virtual region that fragments by allocation-event count, not resident bytes; iOS is the documented worst case. Every synth allocates fresh ORT I/O typed arrays + a WAV ArrayBuffer into this cage. medium WebKit #269937, #272171, #221530

JIT executable-code pool + OMG tier-up. Repeated session.run() re-exercises the same large wasm functions; JSC retains compiled code + metadata in a process-scoped pool evicted only on best-effort pressure. The closest external analog — onnxruntime #26827 — is a still-open, explicitly count-proportional iOS/WebKit kill after repeated ORT calls, worked around by pinning ort-web to v1.20.x. Caveat: #26827 is JSEP/WebGPU-EP-specific and WebKit 26.x, not our wasm/cpu EP on iOS 18 — mechanism-class evidence, not a direct hit. medium

decodeAudioData daemon-side retention is a known iOS class our code was explicitly engineered around (the manual WAV→PCM parse is the primary path specifically to avoid it); the decodeAudioData fallback is annotated in-code as carrying iOS memory risk. tts.js:1446–1452, 1618 · standardized-audio-context #718

Part 2 — Ranked hypotheses for the accumulator

H1
A native Web-Audio resource in the MAIN-PAGE playback layer is retained by WebKit despite our correct JS-side disconnect + dereference, accumulating once per speakable unit. confidence: medium — the prime suspect

Mechanism

Each unit creates an AudioBuffer and an AudioBufferSourceNode, played on the shared AudioContext. WebKit's precedent bugs (#198964, #224279) show that clean-looking JS — proper stop()/disconnect(), one reused context — can still leave a native audio object or thread un-reclaimed, invisible to any JS-heap or WASM-byteLength metric. At ~90–132 responses (more actual buffers, since commaSplit yields several units each) the count crosses the device's native-resource ceiling.

Why it fits all the evidence

  • Count-not-bytes (FACTS A+B): native audio resources accrue per playback object, uncorrelated with ORT byteLength — the fatal region is the native audio/process pool, not the wasm heap. 248 MB and 624 MB deaths reconcile trivially.
  • Realm-teardown-didn't-help (FACT C), decisively: the playback layer lives in the main page, never inside the disposable iframe, so respawn cannot touch it; and the precedent leaks are native/process-scoped, surviving any same-origin realm teardown anyway.
  • Session-option & padding nulls (FACTS E,F): those are synthesis-layer levers — expected to do nothing to a playback-layer leak.

How to test it cheaply

On-device A/B: run the full synth pipeline but bypass playback entirely — synthesize each unit, then discard the WAV right after blob.arrayBuffer() (short-circuit at tts.js:1613): no _wavToAudioBuffer, no createBufferSource, no scheduling. Drive 200+ synths. Survives past 132 → the accumulator is in the main-page playback layer.

H2
JS-VM Gigacage fragmentation driven by per-synth typed-array churn (ORT I/O tensors + WAV ArrayBuffers) — a process-scoped WebKit region that degrades by allocation-event count. confidence: medium

Mechanism

Every predict() builds fresh int64/float32 input tensors + a Float32 output + a fresh WAV ArrayBuffer; these live in the shared Gigacage alongside wasm memory and SAB. Repeated grow/allocate/free fragments the fixed cage so that at some allocation-event count a request can't be satisfied and total footprint/pressure crosses jetsam — independent of any single pool's instantaneous resident size.

Why it fits

WebKit documents cage exhaustion as allocation-pattern-driven, not resident-byte-driven (#269937) — the native shape is "events, not bytes," matching FACTS A+B. And the cage is process-scoped: destroying the same-origin child realm does not defragment the parent's cage, and the parent page's own WAV/AudioBuffer typed arrays keep churning it regardless (FACT C). iOS is the documented worst case.

How to test

Reuse a single pre-allocated fixed-size I/O buffer across all synths (WebKit's own suggested workaround) and see if the death count moves. Cheaper still: check the deployed iOS WebKit version against the April-2024 #272171 fix landing.

H3
JSC JIT executable-code accumulation — OMG tier-up recompiling hot wasm inference functions into a process-scoped pool not synchronously reclaimed. confidence: low

Why it's ranked low: destroying the iframe should eventually free its JIT code, yet the observed respawn at 624 MB still didn't help — which argues the accumulator is in the parent page or a non-JIT native pool. The count-proportional analog (#26827) is JSEP/WebGPU-specific, not our wasm/cpu EP. Test: pin ort-web to v1.20.x on-device; if the death count shifts, a version-introduced wasm/JIT regression is implicated.

H4
The phonemizer broken-latch trips on real narration, after which every synth builds a fresh ~16 MB Emscripten module for the rest of the page's life. confidence: low

Why low: this lives in the synthesis realm — the iframe respawn should reclaim it, so if the latch were the whole story, FACT C would not hold. Test costs nothing: read the existing crumb's pn field (_phonInstances) across a fatal window. pn>1 = the latch fired. The field has said pn:1 on every crumb so far, i.e. it has never fired in play.

Part 3 — Applied gap audit of our integration

Where our code diverges from best practice or leaves a per-synth resource un-freed. Severity is about the B9 kill specifically. Verified against source line-by-line.

severity: high  G1 — The safety valve is wired to the wrong sensor

The one cross-turn mitigation, the iframe respawn, fires only when ORT wasm memory crosses PIPER_RESPAWN_MB = 400 — i.e. keyed to the proven non-causal metric. A 248 MB death fires below the threshold, so the realm never respawns; a 624 MB death respawns and it doesn't help. We gated our only reclaim on the one number we proved doesn't predict the kill. tts.js:1069 (const), tts.js:1860 (mb < PIPER_RESPAWN_MB → skip)

severity: high  G2 — The most-precedented leak site is the one place we can't reach

The entire playback layer lives in the main page while synthesis is isolated in the disposable iframe. The disposable-realm architecture cannot reclaim native Web-Audio objects (the class with the strongest WebKit precedent for count-gated kills), and no amount of respawn tuning changes that. tts.js:414, 1627–1646 · piper-host.html:108–113

severity: high  G3 — The in-page fallback has no reclaim path at all

Whenever the iframe fails to spawn/init on iOS, we fall back to the in-page engine, whose only mitigation is a 30-synth session recycle the code itself documents does not reclaim the wasm arena/shape cache. It is annotated in-code as "memory will ratchet, B9". If iOS is silently on this path for a stretch, that's a known-unbounded growth path with no cap. tts.js:1233, 1709–1731 · vits-web.js:309–316, 327–330

severity: medium  G4 — ORT tensors are never explicitly disposed

Input/output Tensor objects are built fresh every predict() and never .dispose()'d; release relies on JS GC of the wrapper. For the wasm/cpu EP this may be unnecessary, but it is unverified against the prebuilt ort.wasm binary — a per-run resource whose freeing is assumed, not confirmed. vendor/piper/vits/vits-web.js:223–231 · onnxruntime Tensor.dispose docs

severity: medium  G5 — The decodeAudioData fallback has no telemetry

The decodeAudioData fallback (used per-unit whenever the manual PCM16 parse fails) is annotated in-code as carrying iOS daemon-side retention risk — the exact leak the manual path exists to avoid. There is no counter on how often it fires, so a silent per-unit native-retention path could be active undetected. tts.js:1618, 1446–1452 · standardized-audio-context #718

severity: medium  G6 — The phonemizer broken-latch has no reset

One callMain failure permanently reverts to per-synth ~16 MB Emscripten-module creation. Reproducible on long synthetic input; behavior on real narration unconfirmed. Instrumented (pn crumb) but not guarded. tts.js:768–782 · vits-web.js:259–297

severity: low  G7 — releaseVoiceIfUnused uses the Safari-broken vendored remove()

releaseVoiceIfUnused() calls the vendored mod.remove() — the Chrome-only FileSystemFileHandle.remove() in a catch that reports success regardless — while still deleting the in-memory LRU bookkeeping. An OPFS voice-model leak on iOS. Disk, not RAM, so not the jetsam mechanism, but a confirmed resource-not-freed divergence (and it uses the vendored path instead of our own working _piperRemoveVoiceFiles primitive). tts.js:2331–2347 vs 1362–1394

Part 4 — The verdict and the one experiment to run next

Verdict

The convergent read of the external evidence and our own code is that we have spent six versions draining a tank the leak isn't in. The strongest, best-precedented, evidence-consistent cause is a native accumulator in the main-page playback layer (H1) — precisely the region our disposable-realm mitigation is architecturally incapable of reclaiming, which is why the realm work never moved the needle (FACT C) and why the fatal byte-count wanders (FACT B).

But we do not get to declare victory — that is the exact mistake this document exists to break. The next move is not another fix. It is the one cheap test that splits the search space along the axis FACT C already implicated.

⭐ Cheapest next experiment — bypass playback, keep synthesizing

Run the full synthesis pipeline on-device but bypass the playback layer entirely: synthesize each unit as normal (iframe ORT path unchanged), then short-circuit right after blob.arrayBuffer() at tts.js:1613 — skip _wavToAudioBuffer/decodeAudioData, skip createBufferSource/connect/start, skip _sources[]. Drive 200+ synths and watch for the kill. A few lines, no new instrumentation.

OutcomeWhat it provesNext
Tab survives past ~132The accumulator is in the main-page Web-Audio playback layer (H1). This also independently explains FACT C — the realm never contained the leaking objects. Fix targets native audio-object lifecycle: recycle the AudioContext itself every N units, buffer=null on ended, pooled buffers, count the decodeAudioData fallback.
Tab still dies at ~same count, no audio ever playedThe entire playback layer is exonerated; the accumulator is inside the synthesis/wasm chain. Narrow to H2 (single reused I/O typed-array buffer) vs H3 (pin ort-web v1.20.x).

This is the highest-value test because it costs almost nothing, needs no memory API iOS doesn't expose, and cleanly separates "per-synth audio playback" from "per-synth wasm inference" — the split nothing in 25 crumbs has ever made. Note it aligns with, and sharpens, the handoff's existing "narration OFF" idea: narration-off proves per-synth vs per-turn; playback-bypass proves playback vs synthesis while keeping the synth load identical.

Guardrail for whoever acts on this: H1 is the prime suspect, not a confirmed cause. Do not build a playback-recycler before the bypass test returns. The single most important number this whole document produces is the survival count of that one experiment. Ship the experiment, not the fix.
