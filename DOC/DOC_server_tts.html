Server-Side TTS — the B9 architectural close

R1, mandated GO 2026-07-24 · design for a fresh build session · engine v1.434 · see DOC/BUGS.md ▸ B9 for the three-week diagnosis this answers

Why this exists. B9's root cause is closed: iOS kills the WebContent process after a cumulative budget of heavy synthesis work per page load (the energy assassin) — ~100 game synths / ~2 minutes of sustained wasm inference, deterministically, regardless of memory. No client-side arrangement of the work survives it; the v1.434 governor keeps tabs alive by degrading to the native voice, which is a tourniquet. The fix is to move the work off the phone entirely: synthesize on the Fly server (self-hosted — the ownership/cost objection that killed Cartesia/LiveKit does not apply to our own box), stream small WAVs to the client, keep the existing playback/queue machinery untouched. Client CPU ≈ zero → nothing for the assassin to kill → B9 dead on every device, Car Mode included. The TTS_PROVIDERS table was explicitly preserved for exactly this return.

Milestones

M1Server Piper. Same 19 curated .onnx voices hosted server-side — identical audio, zero catalog change, zero speaker-map change. Proves the pipe, kills B9.
M2Kokoro option. Same endpoint, engine param. Kokoro-82M (Apache-2.0): markedly higher quality, dozens of voice packs, voice blending → per-character voices better than today. Requires one CPU benchmark on Fly before commitment + a new voice-picking pass (voice_picker.html precedent).

Endpoint contract (server repo — lives OUTSIDE this tree)

POST /api/tts
  body: { text: string,           // ONE speakable unit (the client's existing splitSentences unit)
          voiceId: string,        // e.g. "en_US-libritts_r-medium" (M1: the curated Piper ids)
          rate: number,           // 0.5-2.0, default 1.0
          engine?: "piper"|"kokoro" }   // M2; default piper
  → 200 audio/wav (22050 Hz mono PCM16) — the exact format _wavToAudioBuffer already parses
  → 4xx/5xx JSON {error} — client falls down the ladder for THAT unit
Auth: same session token as /api/state (Authorization header). See D1.
  • Per-unit request/response, not streaming (v1). Units are 1–10s of audio; the client's 25s lookahead + per-unit queue absorb 200–500ms round trips invisibly. Chunked streaming is a later optimization, not a requirement.
  • Server implementation: warm piper daemon per active voice (spawn-per-request pays ~1s model load per unit — too slow), LRU of 2–3 warm voices, idle-killed after ~10min. Voices downloaded to the Fly volume on first use (HuggingFace), never baked into the image (19×60MB).
  • Cache: optional LRU disk cache keyed (text,voiceId,rate) — replays/re-speaks hit it; low priority.

Client changes (this repo, tts.js — off the drift surface)

  • New TTS_PROVIDERS.server entry: available() = online + server connected (+ a health probe memo). _speakServer() = the existing _speakPiper unit loop with predict() replaced by fetch(/api/tts) — same splitter, same speaker maps, same _wavToAudioBuffer, same scheduling, same pause tiers. Most of the loop is reused.
  • The ladder (per unit, loud): server → local Piper (governed, v1.434) → native. Connectivity drop mid-read degrades that unit and retries server next read. The governor keeps protecting the local tier; it never touches the server tier (no client work to budget).
  • Voice ids unchanged in M1 → resolvePiperVoice/characterVoiceId/blueprint narrator plumbing untouched. M2 introduces a namespaced catalog (kk_*).
  • Per-unit timeout (~4s) → ladder-fallback for that unit; never a stalled read.

Decisions to ratify before build

D1Auth. Recommend: require the existing GitHub session token; not-connected players simply use the local ladder (offline play unchanged). Alternative (open endpoint + rate limit) invites abuse of our CPU.
D2Topology. Recommend: second small Fly app (tnd-tts) in the same server repo, so narration bursts never delay game-state saves. Alternative: same app first, split when measured.
D3Fallback UX. When the server tier degrades mid-session, toast once per session or per read? Recommend once per session (the B10/governor toast pattern).
D4M2 gate. Kokoro ships only after a Fly CPU benchmark shows ≥1× realtime on the chosen instance; otherwise it waits for a bigger box or stays optional.
D5Voice storage quota. Fly volume size for models (19 Piper ≈ 1.2GB + Kokoro ≈ 350MB). Recommend 3GB volume.

Sizing reality check

Piper medium runs 2–5× realtime on shared x86. A 30-unit read ≈ 60–90s of audio ≈ 15–40s of server CPU, spread across the read's duration by the per-unit request pattern. Concurrency = simultaneous narrating players ≈ 1–2 today. A shared-cpu-1x handles M1; Kokoro (~4–5× Piper's cost) is what D4's benchmark is for.
What this does NOT change: the local Piper engine, the governor, the native fallback, the voice-slot UI, OPFS caching — all stay, as the offline tier. The drift surface is untouched (output rendering only). The v1.434 governor remains correct and necessary for the offline tier forever.
