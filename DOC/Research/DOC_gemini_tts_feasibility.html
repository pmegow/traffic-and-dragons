Gemini TTS — feasibility

Can the savings from a cheaper GM model pay for a premium voice? Costed against our own measured prose volume, not vendor examples. Research only — no code was written.

Commissioned off one observation: opus-5 costs 16–18× gemini-3.7-flash-low per 50 turns and is not 16–18× better, so the difference could buy something else. This page tests whether "something else" can be Gemini's TTS.

Bottom line. viable probe run The arithmetic works, but by a thinner margin than first estimated. Moving the default from sonnet-5 to gemini-3.7-flash-low frees $2.14 per 50 turns; premium Gemini voice on that same run costs a measured $1.75. The voiced experience lands $0.39 cheaper than today's silent-tier default — still cheaper, with a far better voice, but not the $0.93 the estimate promised.

Car Mode is answered: time to first audio is 840 ms streaming — against a current server tier whose cold chain has hit 10.17 s. Non-streaming took 31 s for the same clip, so streaming is not optional.

The remaining caveat is that all three TTS models are preview, with restrictive rate limits and no stability promise.

What Gemini TTS actually is

verified against Google's own docs, not blog aggregators

  • Three models: gemini-3.1-flash-tts-preview, gemini-2.5-flash-preview-tts, gemini-2.5-pro-preview-tts. All are preview: "may change before becoming stable and have more restrictive rate limits."
  • Streaming: 3.1 and later only. "Streaming is supported for Text-to-Speech (TTS) models starting with version 3.1." This is the single most decision-relevant fact on the page — see Car Mode below.
  • 30 prebuilt named voices (Kore, Puck, Zephyr, Enceladus…), each with a described character — Bright, Upbeat, Breathy.
  • Multi-speaker up to 2 per call, via multi_speaker_voice_config.
  • Natural-language style control. "Say in a spooky whisper", per-speaker emotional direction, and inline modifiers like [whispers] / [laughs].
  • 32k token context per TTS session; automatic input-language detection across a wide language set.

The style control is the genuinely interesting part for this product, and it is not a gimmick here: we already have a validated voice-attribution layer (#96 [SAY:], field-confirmed by the owner) that knows which character is speaking. Feeding that layer's output into per-utterance emotional direction is the natural next move, and no other tier we have can do it — Piper renders a flat read.

The 25 tokens/second figure is the trap. It appears in Google's own worked example and across every pricing aggregator, and it is what the first cost model used. The billed reality on 3.1-flash was 1,522 audio tokens for 47.56 seconds — 32.0 tok/s, about 28% higher. Combined with speech being slower than 150 wpm, the estimate was 45% light. This is the entire justification for probing before committing.

Voice. Two samples were produced for the same passage — Algenib (Gravelly) and Gacrux (Mature) — specifically to judge whether the model changes register for Sylvie's quoted whisper. That is the capability Piper structurally cannot provide, and it is the part no spreadsheet can settle.

Multi-actor scenes

the owner's question · probed on a real 5-speaker scene

Yes — but not the way the API advertises. The multi_speaker_voice_config object caps at two speakers, which is useless for a party scene. The path that works is the one this codebase already uses for Piper: synthesize per unit, each with its own voice, via the existing voices map. No new architecture — the stored sp speaker map written by the #96 [SAY:] layer already carries exactly the data needed.

Probe: Runelords t1774 — 5 speakers (Ammut, Morwen, Frizwick, Daeris, Wyla Ashvane) plus narrator, 1,433 speakable characters. The real splitSentences comma-split produced 42 units, matching the stored sp.n exactly.

Economically, multi-actor is free. Audio tokens bill by duration, and the duration of a scene does not change because six voices spoke it instead of one. The only additional cost is the per-call style direction re-sent with each group — 689 input tokens across 17 calls, which at $1/1M is $0.0007. Rounding error. A fully cast scene costs the same as a monotone one.

Operationally, rate limits are the constraint, not cost. Running the 17 groups at concurrency 3 produced 3 failures that only cleared on sequential retry with backoff. This is the preview-tier rate limit predicted in the risks section, now observed. It is manageable — playback is naturally paced, so synthesis only needs to stay one or two units ahead, and the existing ladder already degrades to Piper on failure — but a naive "fire all units at once" implementation will fail in the field. Piper never had this constraint because it runs locally.

Unverified: the voice bank is documented by characteristic ("Warm", "Clear", "Gravelly"), never by gender. The gender-matched cast used here is assigned from commonly-reported voice genders and needs a human ear to confirm before it becomes a shipped mapping.

The decision this actually forces

the swap that pays for itself

opus-5's savings were already banked when it was unlisted at v1.643, so "spend the opus savings" is not quite the live trade. The live trade is the default:

Today: sonnet-5 default, silent tier (self-hosted Piper, ~$0 marginal) = $2.64 / 50 turns.

Proposed: gemini-3.7-flash-low default + Gemini 3.1 streaming voice = $0.50 + $1.75 = $2.25 / 50 turns.

Net: $0.39 cheaper (measured), with a dramatically better voice added rather than removed. The margin is real but thin enough that it should be treated as "voice for free," not "voice plus savings."

The honest counterweight: today's TTS marginal cost is approximately zero, because we self-host Piper. This introduces a real per-use COGS line where none existed. The trade is only favourable because the GM-side saving is larger than the voice-side cost — it is not free money, it is a good exchange rate.

And note the second-order effect, which is the same one the owner identified for Car Mode usability: prose length is now a cost multiplier on both sides of a turn. opus-5's 1,544 chars/turn costs 2.1× gemini-low's to speak and ~17× to generate. Terser prose is cheaper twice and easier to follow while driving. Three independent arguments now point the same way.

Architecture — smaller than expected

this may need no client change at all

The obvious shape is a fourth TTS_PROVIDERS entry. That is probably the wrong one. The server tier already exists and already proxies: the client POSTs /api/tts to the tnd-tts Fly app, which today runs Piper daemons server-side. Swapping that backend to Gemini means:

  • The client ladder stays byte-identical — server → piper → native, unchanged.
  • The whole degradation story is inherited free: the 60s retry memo, per-item downgrade-to-native, the once-per-session degrade toast.
  • Piper remains the $0 offline floor, exactly as the #90/#41 design requires. This is additive, never a replacement.
  • Zero exposure to the client-side drift surface. The change lives in the server repo (tts/), deployed with flyctl.

The 2-speaker cap is a non-issue for the same reason: our queue already synthesizes per unit with a per-unit voiceId (the voices map), so each utterance is a single-speaker call carrying its own cast voice. The real work is a curated voice bank mapping the 30 prebuilt Gemini voices into the #174 casting flow (sheet gender → pronouns → starred bench). That is data, not architecture.

Risks and open unknowns

what would have to be settled first

  • blocker-ish Preview status. All three models are preview, with "more restrictive rate limits" and no stability guarantee. This project has already been bitten by retired Gemini IDs returning 404. A shipped tier on a preview model needs the ladder as a genuine safety net, plus acceptance that it can break on Google's schedule.
  • resolved Time to first audio — 840 ms streaming. Comfortably inside Car Mode needs and far better than the current server chain's 10.17s cold worst case. Non-streaming was 31s, so the tier must be built on streaming.
  • resolved The rate assumptions — measured at 2.412 tok/char (13.27 chars/s, 32.0 tok/s). Every cost figure above is now measurement-backed, and 45% higher than the estimate.
  • decided elsewhere Who pays. On a player's own key this repeats precisely the objection that killed LiveKit — per-use cost riding the player's key. It only makes sense server-proxied under the subscription model (BYOK-elimination ruling, 2026-08-16), which is also the architecture recommended above.
  • probe Free tier. 3.1-flash and 2.5-flash both list a free tier. Its limits are unstated here and worth probing — it may cover development and early play entirely.
  • Rate limits vs burst shape. A game turn produces a burst of short units, not one long clip. Preview rate limits are per-minute; the queue may need pacing that Piper never required.

Where it stands

probe complete · still no engine code written

The numbers are settled and they support building it: $0.39 cheaper than today with a far better voice, 840 ms to first audio, and a style-control capability the current stack structurally cannot match. What is not settled is whether the voice is good enough to justify introducing a COGS line where the marginal cost is currently zero — that is an owner listening call on the two samples, not an engineering one.

If it proceeds, the build order suggested by the architecture section is: ① a Gemini backend inside the existing tnd-tts app behind the current /api/tts contract, so the client never learns a new tier; ② a curated voice bank mapping prebuilt voices into #174 casting; ③ wiring #96 [SAY:] attribution into per-utterance style direction, which is the actual product win. Piper stays the offline floor throughout.

Two things to carry into that work: the preview-model risk is unmitigated (the ladder is the safety net), and per-minute rate limits against a game turn's burst of short units are still unprobed — a load shape Piper never had to care about.
