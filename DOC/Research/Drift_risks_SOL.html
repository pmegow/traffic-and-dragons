Where Traffic & Dragons can still drift

Sol analysis · 2026-08-08 · includes Rise_of_the_Runelords_Ammut_t1549.tnd from Downloads · no source or save repairs performed

Verdict

A focused hardening pass is warranted. The anti-drift architecture is not broadly failing: the latest save has correct structured split-party state, working provenance receipts, no reproduced NPC-key fragmentation, and no missing-health defect. The dangerous residue is narrower: temporary prose is being promoted to permanent NPC truth; bookkeeping text can select story memory; corrections can lose their authoritative replacement; and several mutation paths are not closed-loop.

The save also contains one already-real timeline corruption: the interim clock repair was effectively applied twice. That is not a normal gameplay regression, but it proves repair operations and load invariants are not safe enough for a mature campaign.

1. Method and burden of proof

I treated drift as a divergence between what happened in the fiction and what the engine later presents as current canon, whether through state, memory, prompt assembly, retrieval, sync, or UI projection. A code smell alone did not qualify.

Angle A · MechanismThe exact writer, reader, selector, or lifecycle edge had to be identifiable in current code.
Angle B · Failure evidenceThe latest save had to expose it, or an exact headless failure probe had to reproduce the dangerous condition.
Angle C · Counter-caseI looked for guards, precedence rules, expiry, or scope restrictions that could make the apparent issue benign. Those mitigations are stated with each finding.

Only candidates that survived all three angles are in the register. The report distinguishes active live contradictions, reproduced latent defects, and known accepted limitations.

R1. NPC knowledge has no temporal type

HighConfirmedLive prompt

Mechanism. The summary schema offers one free-text knowledgeGained field. applySummaryExtract permanently appends it to memory.npcs[name].knowledge[]. memoryNpcDetail later renders every entry under the standing label Knows:. There is no fact kind, observation turn, validity window, or distinction between “learned a secret” and “is standing at this door right now.”

Angle A · Codememory.js:976 accepts the untyped string; memory.js:753 joins the array oldest-first and truncates after 2,000 characters. The nominal cap sheds only one element per write, so a pre-existing overfill never converges.
Angle B · SaveMorwen's injected knowledge says she “is now stationed outside the sealed door” and “remained outside,” although she is with Ammut heading to Savah. Daeris says “Present at the carved door”; Frizwick says she “is holding the chokepoint,” although both are split at the ironworks.
Angle C · Counter-caseThe structured splitLoc, lastSeenAt, party sheet, and later geography block are correct. They reduce the probability of failure, but they do not remove the contradictory canon from the prompt.

Amplifier. Frizwick has 18 knowledge entries despite the cap of 12. Her joined text is 2,375 characters, so the renderer keeps the oldest 2,000 and cuts off the newest tail. The combination is backwards for drift resistance: stale positional claims survive while newer facts disappear.

Structured truth: Frizwick → Magnimar | Bridge District Ironworks
Injected “Knows”: “...is holding the chokepoint at the carved door”; “Present in the workshop...”

Structured truth: Morwen → with Ammut, en route to Savah
Injected “Knows”: “Is now stationed outside the sealed door...”
RankSolutionAssessment
1Typed temporal factsReplace bare strings with records such as {id,text,kind,observedTurn,standing}. Only standing/durable facts enter Knows:; scene position and one-turn actions go to stamped history/RAG. Most complete fix and the cleanest future contract.
2Structured-state conflict gateBefore prompt rendering, suppress a position/action claim when it conflicts with current splitLoc, current node, death, or other authoritative state. Render newest-first within budget. Smaller but requires a conservative classifier.
3Hygiene hardeningTeach extraction not to file transient posture/location; on load re-slice every knowledge array to 12; archive overflow; render the newest facts instead of the oldest. Useful immediately, but still relies on model classification.

R2. Bookkeeping text activates off-scene NPC memory

HighConfirmedLive prompt

Mechanism. api.js:882–885 finds “hot” NPCs by concatenating the last six raw sessionLog messages and searching names. Those user messages include prepended engine notes. The summarizer already has stripEngineNotes, but the hot-NPC selector does not use it.

Angle A · CodeAny name appearing only in a split, condition, presence, merge, relationship, or other audit note qualifies for full ACTIVE NPC DETAILS. Channel origin is discarded.
Angle B · SaveAcross the latest six messages, Frizwick appears twice and Daeris once, exclusively inside the split-audit note. Neither appears in story prose. Reconstructed buildSysPrompt still emits full details for both.
Angle C · Counter-caseThe later SPLIT THREADS block explicitly says they are at the ironworks and must never be narrated here. Position and wording favor that block, but the prompt now contains two incompatible authoritative-looking sections.

This is a feedback loop: a presence-protection audit names an absent person; that bookkeeping mention activates old narrative memory for the same person; the old memory contains stale presence claims.

RankSolutionAssessment
1Story-only hot setBuild the set from cleaned player actions plus GM transcript entity stamps, not raw API history. Include current co-located party and current-node NPCs explicitly; exclude split members unless the player's story action names them.
2Strip notes before scanApply the existing bracket-aware stripEngineNotes to user halves before hot-name detection and accept names only when they also occur in story prose. Minimal and directly closes the live case.
3Preserve message provenanceStore story text and engine notes as separate typed fields/spans so every downstream consumer can opt into the correct channel. Broadest architectural protection, but larger migration cost.

R3. Clock repair is not idempotent, and impossible clocks load normally

HighConfirmedCurrent save

Mechanism. The interim repair for TODO #142 was a raw console edit: worldState.clock.min-=1160. It had no expected current value, repair identifier, one-shot guard, or invariant check. Normal clock code only increments clock.min; load migration verifies shape, not chronology.

Angle A · Codeclock.js describes the scalar as monotonic and writes only +=. migrateWorldState accepts a numeric scalar and schedule array without checking transcript stamps or schedule births.
Angle B · SaveGM stamps go from ck=8820 at t1525 to ck=6500 at t1526: −2320 minutes, exactly twice the intended −1160 repair. Turn numbers do not regress. Current schedule births 6915 and 7490 are both greater than now 6680.
Angle C · Counter-caseNo normal gameplay path reproduces the decrement. This is specifically a repair/migration weakness, not evidence that the shipped clock still runs backward during ordinary turns.

The Sable schedule was created with a 1,440-minute duration. Because its birth is now 810 minutes ahead of the clock while dueMin stayed absolute, its current remaining time is 2,250 minutes: the deadline gained 13.5 hours.

RankSolutionAssessment
1Idempotent repair transactionA named repair carries repairId, expected-before value, intended-after value, and postconditions. Refuse if already applied or if the scalar does not match the expected anomaly. Save the repair receipt atomically.
2Load-time timeline validatorWarn and quarantine when transcript .ck regresses, schedule.born > clock.min, due < born, or a repair discontinuity lacks a receipt. Offer an export-first guided repair; never silently guess.
3Clock event ledgerStore advances/corrections as append-only events and derive the scalar. Corrections become reversible and auditable. Strongest long-term model, but much larger than the immediate safety need.

Do not auto-fix this save from this report. The intended corrected scalar and schedule semantics should be adjudicated once, from the t1523–t1526 evidence, then applied through an idempotent repair.

R4. State-tag application is not closed-loop

HighReproduced

Mechanism. Known tags do not share one typed resolution contract. Some exact-match, some substring-match, some choose the first candidate, some silently return, and several emit a mutation receipt without verifying that a mutation occurred.

Angle A · CodeSequential ARC_COMPLETE validates its title only for parallel acts; combatFoeByName returns the first containment match; many companion handlers continue silently; player spell and skill misses do nothing.
Angle B · Probes[ARC_COMPLETE:Totally Wrong] completed “True Arc.” [ENEMY_HP:Goblin|-3] damaged Goblin Scout among Scout + Shaman. [COMPANION_HP:Frizwik|-4], unknown spell, and unknown skill produced no mutation and no warning.
Angle C · Counter-caseMany high-risk handlers are already strict and loud, and companion spell use does warn. The defect is inconsistency, not a universally tolerant parser. That makes a shared boundary more valuable than scattered patches.

The live tag receipt adds a fourth shape: t1530 records ITEM_LOST with mutation text -none. The inventory contained no item named “none”; removeInventoryItem returned false, but the handler ignored the result and still reported success.

RankSolutionAssessment
1Typed tag schema + uniform resolverEach tag declares payload fields, target domain, exactness, ambiguity policy, and result status: applied / unchanged / invalid / ambiguous. Fail closed on wrong or ambiguous targets and surface the reason.
2Strict family fixesValidate sequential arc titles; make named combat targeting exact or uniquely resolvable; warn on every companion/spell/skill miss; honor inventory helper return values. Smaller, but risks future asymmetry.
3Post-parse receipt verifierCompare every recognized tag instance with an applied mutation or sanctioned no-op. Queue one repair note/toast for unmatched tags. Good backstop, but it detects after the primary resolver has already guessed.

Comparison: independently reproduced, then matched to the already-open tolerant-parser sweep in TODO #136. No duplicate tracker row was created.

R5. A correction can erase both versions from episodic recall

MediumConfirmed mechanismLive exposure

Mechanism. When raw GM output contains [RETCON:], logTranscript marks the correcting GM entry and the preceding GM entry rc=1. RAG excludes every rc entry. The separate filter for a preceding player message beginning GM: would also suppress the correction.

Angle A · Codestate.js:162–183 marks both; memory.js:630–641 excludes both correction-marked and OOC-meta responses. No first-class correction record is created.
Angle B · Save + probet1547's wrong street interrogation and t1548's corrected Wyla exchange are both rc=1. Wyla's knowledge does not yet say the watchers are hers. An A/B retrieval probe returns nothing with both marked and returns the canonical correction when it is eligible.
Angle C · Counter-caseThe correction remains in the current session tail and the next summary may file it. Therefore this is a delayed, probabilistic hole after the tail rolls, not a claim that t1549 has already forgotten the correction.
RankSolutionAssessment
1First-class canonical correctionLink the superseded turn to a correction record. Exclude the old entry; index the cleaned correction as authoritative and explicitly allow it through the GM: meta filter.
2Pin until acknowledgedInject a compact “correction in force” record until a summarizer result explicitly captures the replacement. Then archive the pin. Preserves truth without trusting one extraction pass.
3Post-summary coverage checkAfter summarizing a window containing RETCON, verify a replacement fact or correction record exists; if not, retain the exchange in the session tail and warn. Useful backstop, still model-dependent.

R6. Audit latches burn before delivery or compliance

MediumReproduced

Mechanism. Many note builders stamp cooldowns or clear one-shot state while buildEngineNotes is composing apiTxt. That happens before callGM. A network failure, provider error, tab loss, or same-turn retry therefore sees the latch as already consumed. Successful delivery is also treated as compliance even when the GM emits none of the requested tags.

Angle A · CodesendAction builds notes at game.js:1551–1559, before awaiting the provider. Split, presence, condition, mood, reciprocity and other builders mutate stamps on fire; the catch path does not roll them back.
Angle B · Probe/saveA due split produced an audit and wrote audited:20; rebuilding on the same unchanged turn returned no audit. In t1549, the t1547 split audit requested rejoin or reaffirm for Frizwick/Daeris; the GM emitted neither, but the audit stamp still suppresses the check for its cooldown.
Angle C · Counter-caseThe latest split records happen to be correct, so the ignored audit caused no current error. Cooldowns deliberately limit prompt pressure, and the burned-nudge tradeoff is acknowledged in code. The risk matters when the audited record is actually stale.
RankSolutionAssessment
1Two-phase note deliveryBuilders are pure and return text plus a proposed latch update. Commit the cooldown only after a response is received; for required-fork notes, commit only after an expected tag or explicit sanctioned no-change outcome.
2Persistent pending note IDsKeep a note pending across retries and turns until satisfied or expired. Re-send with bounded cadence. Best compliance loop, but requires per-note acknowledgement rules.
3Rollback on pre-commit failureSnapshot note-owned fields before building and restore them when the turn fails before commitGmTurn. Closes transport failures, but not successful noncompliance.

R7. Cloud conflict detection is too coarse for same-turn truth

MediumConfirmed design limit

Mechanism. Normal sync posts use baseTurn=_lastAckTurn, and the server rejects only when its stored turn is ahead. Whole-state edits that do not advance the turn can share the same CAS value. The campaign-manager push path intentionally omits baseTurn.

Angle A · Codestorage-adapter.js:384–470 guards by turn. pushCampaignState at 834–841 has no CAS. syncCharSheet, reroll replacement, and several UI/state changes can save without advancing the story turn.
Angle B · Failure constructionTwo devices load t1549. Device A applies a same-turn sheet correction and uploads. Device B, still at t1549, uploads its stale whole blob: the turn guard sees no ahead turn and can accept the overwrite. Manual rescue push is an even wider overwrite path.
Angle C · Counter-caseOrdinary story turns advance and genuine server-ahead conflicts pause loudly. Portraits have their own version. No evidence attributes the t1549 campaign mess to concurrency, so this remains a latent hardening risk.
RankSolutionAssessment
1Server revision / ETag CASEvery accepted write increments a per-campaign revision independent of story turn. Clients send If-Match or baseRev; any unseen write conflicts, including same-turn edits.
2Monotonic state revision in the blobIncrement stateRev at every authoritative mutation/save and guard on it. Easier to layer onto the current protocol, though multi-device offline forks still require human choice.
3Narrow protectionsPreflight manual pushes with server revision + explicit overwrite confirmation; version same-turn domains separately; gate play until first reconcile. Reduces exposure but leaves whole-state merging unresolved.

Comparison: this is already documented in TODO #5 as accepted v1 coarseness and TODO #7 for manual push semantics.

R8. NPC_FORGET is broad and unrecoverable

MediumReproduced

Mechanism. The handler lowercases the requested phrase and deletes every knowledge or event line containing that substring. It does not require a unique match, does not preview the affected facts, and does not archive them. Its sibling NPC_SUPERSEDE archives retired knowledge.

Angle A · Codetag_table.js:598 filters both arrays by indexOf(fgWhat)<0. The mutation summary reports only a count; the deleted content is gone.
Angle B · Probe[NPC_FORGET:Sage|red key] removed two separate knowledge lines and one historical event: “opens the vault,” “stolen yesterday,” and “saw the red key at dawn.”
Angle C · Counter-caseThe tag is intentionally destructive because it models Oubliate. That justifies removal from injected memory, not irreversible storage deletion or ambiguous multi-match behavior.
RankSolutionAssessment
1Forget by fact IDGive stored facts stable IDs and have the effect target one exact record. Move it to a non-injected forget archive/tombstone so the fiction forgets while operators retain recovery and provenance.
2Unique full-match ruleRequire exact text or exactly one unique normalized match. Multiple/no matches warn and do nothing. Archive the removed record. Good bridge before fact IDs exist.
3Preview/confirm queueQueue proposed matches and require a follow-up exact tag/confirmation. Safest for broad natural-language requests, but adds a turn of latency to the spell effect.

5. Protections that are working

  • Split state and projections: Frizwick and Daeris have stamped/audited splitLoc records, the prompt has a strict split block, and the UI hides remote vitals. Morwen's present state is correct.
  • Provenance: transcript .ck, .ta, .v, tagLog mutation receipts, split stamps, and session history made the clock and prompt failures provable rather than speculative.
  • Identity: alias resolution, human-confirmed merges, and the deterministic variant scanner show no current duplicate cluster in this save.
  • Memory bounds and recovery: future-event expiry, near-duplicate dedupe, summary retries, superseded-fact archive, and RAG contamination filters close several older failure classes. The findings above are boundary gaps in those systems, not absence of systems.
  • Sync: server-ahead turn conflicts pause loudly; automatic retries are bounded; campaign identity is positively checked; portraits have an independent revision.

6. Recommended hardening sequence

  1. Stop serving contradictory NPC truth: R2 story-only hot selection first (small, directly removes the latest prompt conflict), then R1 cap convergence/newest rendering as immediate hygiene. Design typed temporal facts before changing the memory tier.
  2. Repair the campaign clock safely: build the R3 invariant/repair instrument, export first, adjudicate one intended timeline, and apply one idempotent repair. Do not repeat the console decrement.
  3. Close the parser loop: take TODO #136 as one resolver/result-contract pass, with R8 handled as its destructive subcase. Write failure-first tests for wrong arc title, ambiguous foe, typo companion, missing inventory, and broad forget.
  4. Make corrections durable: implement R5's first-class correction record so the replacement survives beyond the rolling tail.
  5. Make audits transactional: R6 two-phase note delivery, beginning with split/presence/condition notes because they directly guard canon.
  6. Generalize sync revision: R7 becomes important before networked multiplayer or more same-turn editing surfaces ship.

Informed conclusion

The campaign did not become messy because one subsystem collapsed. The evidence points to contradiction multiplication: a transient scene statement was promoted to durable NPC knowledge; an engine audit re-selected that off-scene NPC; the prompt then contained both the stale prose claim and the correct structured location; RETCON and audit lifecycle rules can remove or delay the channels that would heal the disagreement. Separately, an unguarded manual clock correction was repeated and damaged every absolute deadline.

The right hardening pass is therefore not “add more reminders.” It is to enforce provenance and closure at boundaries: story vs bookkeeping, standing fact vs scene event, proposed tag vs applied mutation, correction vs superseded history, request built vs request committed, and story turn vs state revision.

Per-finding validity and solution risks

R1 · Temporal NPC memory

Valid — confirmed, and it is half of a larger defect. My audit found the same store failing in the opposite direction: the write-side cap evicts the oldest facts to the void (83 facts destroyed between t1265 and t1549, proven longitudinally; the #128 merges re-slice a united history to 12 archive-less), while Sol's render truncation cuts the newest tail of over-cap NPCs. An over-cap NPC like Frizwick is squeezed from both ends at once. These are not two findings; they are the write half and the read half of one defect — an untyped, unmanaged knowledge lifecycle — and the hardening pass should treat R1 plus my Finding 1 as a single work item.

Solution risks. Ranked #1 (typed temporal facts) is the right end state but is a memory-schema migration on the drift surface: every existing save carries bare strings, the summarize extractor's JSON contract changes (a model-facing change that needs a money-turn validation, the gpt-4o precedent), and the kind-classifier is model judgment — a standing fact misfiled as a scene event silently falls out of Knows: forever. Pair it with archive-on-eviction (my Finding 1, remedy 1) so a misclassification is recoverable rather than fatal. Ranked #3 contains a trap as written: "on load re-slice every knowledge array to 12" would destroy six of Frizwick's facts on the next load with no archive — the exact silent-loss class both audits are trying to close. Any convergence slice must archive what it sheds, and must decide which end honestly (newest-first retention inverts the current bias; that is a choice, not a given).

R2 · Bookkeeping activates off-scene NPCs

Valid — the audit's best original finding. Confirmed live: stripEngineNotes exists (memory.js:1008) and is applied only on the summarize path (:1059), never before the hot-NPC scan (api.js:885). The feedback-loop framing is exactly right, and it is an amplifier for R1: the presence-protection audit names the absent companion, which activates the detail block carrying her stale posture claims — the protection machinery feeding the contradiction it exists to prevent. Neither my audit nor any tracker row had this.

Solution risks. I would invert Sol's ranking for sequencing: #2 (strip notes before the scan) is nearly one line, classifier-free, and provably closes the live case — ship it first. #1 (story-only hot set) is the designed end state but reworks an audit-#13-vintage behavior with its own regression surface, and its "exclude split members unless named" clause needs one carve-out stated explicitly: a player's typed action about a split member ("what is Frizwick doing?") is story text and must still activate detail, or the SPLIT THREADS design loses the context it needs to advance remote threads. #3 (typed provenance spans) is correct architecture and the natural home is the eventual multiplayer/server-canonical migration, not this pass.

R3 · Clock repair non-idempotent

Valid — conceded above; Sol out-dug me here. Two additions. First, the likely double-application vector is cross-device: the repair line was published for the desktop console with "syncs to phone" framing, and a repair run on two devices (or re-run after a sync race restored the pre-repair blob) lands twice — which means Sol's #1 is right that the repair receipt must live in the synced save (worldState), not in device-local storage; a local receipt would not have prevented this. Second, the adjudication when it happens: intended state is one −1160, so the current scalar is 1,160 low (true min ≈ 7,840 at export), and both schedule anchors then sit legitimately in the past with the Sable window at ~18 hours rather than the inflated 2,250 minutes. I endorse the do-not-auto-fix callout without reservation; the #142 skip-and-demand teeth were the right fix for the cause, and this row is the missing fix for the repair tooling.

Solution risks. #2's load-time validator should treat a .ck regression as quarantine-and-ask, never heal-in-place — the transcript is decree-immutable and a "healer" that rewrites stamps would be a worse defect than the one it fixes. #3 (event ledger) I agree is oversized for the need; it is also the only option that would have made the double-repair self-evident, so it deserves a line in the multiplayer-era design notes even if unbuilt now.

R4 · Open-loop tag application

Valid, and correctly filed against the existing #136 rather than duplicated — good tracker discipline. The genuinely new contribution beyond #136's four classes is the t1530 ITEM_LOST "-none" receipt (verified): a mutation reported that did not occur, a fifth shape #136's row text does not currently list. That deserves to be added to #136 so the sweep covers receipt-honesty, not just miss-honesty.

Solution risks. The #1 uniform resolver is the right architecture — but "fail closed on wrong or ambiguous targets" must remain a per-tag declared policy, not a blanket rule. The bare [ENEMY_HP:] routing (single → engaged → first-living + warn) was a deliberate ratified ruling that the mutation always lands, because the GM does not retry and unbooked damage desyncs the fight; failing closed there reverses a design decision that was made with eyes open. Sol's schema technically supports per-tag policy — the risk is uniformity zeal at implementation time, so the contract should require each tag's ambiguity policy to be an explicit declared field, defaulting to strict only for new tags. #3's receipt verifier is cheaper than it looks: the tagLog provenance ring already records tags and muts lines per response, so the verifier is a diff over an existing structure.

R5 · RETCON suppresses its own correction

Valid — mechanism and live instance both verified (t1547 and t1548 both carry rc=1; the t1547 player half opens "GM:", so the meta filter would independently suppress it — a doubly-closed door). Sol's honest bounding (delayed, probabilistic, the summarize pass may still carry the fix) is the correct severity read. Worth stating plainly: the designed carrier for the correction is the summarize extraction, so this finding reduces to "the correction's survival depends on one unverified model pass" — which is why Sol's #3 (post-summary coverage check) is really the verification layer for the existing design rather than a third alternative; it composes with either #1 or #2 rather than competing with them.

Solution risks. #1 (first-class correction record) touches logTranscript, RAG scoring, and a new store in one change — proper Fable-tier surface, medium not small. #2's pin needs a bounded shelf: "until a summarizer result explicitly captures the replacement" is a condition that can simply never fire (extraction paraphrases; exact-match acknowledgment will miss), and an unexpiring pin becomes permanent prompt noise — the class the one-shot-shelf pattern exists to prevent. Give the pin a turn-capped shelf with a loud expiry.

R6 · Audit latches burn before delivery

Valid — mechanism confirmed in the builders themselves (e.g. buildRelationshipAudit stamps lastRelAudit during composition; sendAction composes notes before callGM; the catch path restores nothing).
