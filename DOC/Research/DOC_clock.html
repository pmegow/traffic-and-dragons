Campaign Clock

Design spec for TODO #73 — the engine's in-fiction time system: a monotonic clock the GM advances each turn, and a scheduler whose countdowns are computed, never remembered.

Status: design converged 2026-07-20 (user + Claude designed independently, then compared). v1 built same day. Drift surface → Fable pre-review pending (logged in todo_checkWithFable.md).

The problem it fixes

The engine has no concept of a day. The only clock is free-text [TIME:] ("dusk", "midday") with no advancement. So any in-fiction deadline is pure hallucination.

Live evidence (2026-07-19, Table Talk): asked "how many days to the winter solstice", the GM answered 11, then 8, then 94 — three confident answers, nothing stored behind any of them — and emitted [CALENDAR:11 days to winter solstice] and [DAYS_TO_SOLSTICE:94], inventing tags for a system that does not exist. The GM believed it was recording a countdown; nothing was listening.

The root cause is not that the GM is bad at counting. It is that the GM is asked to remember and re-state a number. The fix removes that request entirely: the engine stores an anchor, and every countdown is recomputed from it. A number the GM never re-states cannot drift.

The four pillars

PillarDesign
CounterONE scalar — total minutes since epoch (clock.min). The human day/hour/minute view is derived, never stored. A single monotonic integer cannot carry-desync from itself, and "add 90 minutes" is a bare +90. (User's first instinct was three stored fields m/h/d; same capability, but the scalar removes the carry-bug surface and those three become the display.)
AdvanceThe GM estimates how long each turn took and the ENGINE adds it. The GM does zero arithmetic — it emits a duration in natural units (2h, 11d), which is judgment, the thing models are good at. Every add, carry, and countdown is deterministic JavaScript. This is why "LLMs are bad at math" is the reason for the design, not a constraint worked around.
RestRoutes through the same advance tag — a rest is just a big advance (6–12h per the narrative), not a second mechanism.
SchedulerStores an absolute due-time; the "time remaining" is recomputed every turn (due − now). The GM sets a deadline ONCE and can never drift because it never re-states the number.

Data model

worldState.clock = {
  min: 0,              // total MINUTES since epoch (campaign start = 0). Monotonic.
  schedule: [          // absolute-time deadlines; countdowns are computed, never stored
    { id, label, dueMin, born }   // fires when clock.min >= dueMin
  ]
}

Epoch = 0 = campaign start, resettable via the Sync modal (fast-follow). The v1 clock measures elapsed campaign time — 4 whole days + 14h 30m renders as "Day 5, 14h 30m elapsed" (day labels are 1-based since v1.498) — which is the honest primitive. Mapping elapsed time onto an in-world wall-clock date ("3rd of Frostfall") is the calendar fast-follow.

Tags

TagEffect
[TIME_ADVANCE:N]Advance the clock. Unit-suffixed: 2h, 30m, 1d 6h, or bare = minutes. Clamped to ≥ 1 min. Monotonic — never runs backward. Emitted every turn. Missing → default +1 min (fail-safe-small) + a compliance watch (HP-under-emission class).
[SCHEDULE:label|when]Schedule a future event at now + when (duration form: 11d, 10m). Stores the absolute dueMin. Duplicate label refreshes rather than twinning.
[SCHEDULE_RESOLVED:label]The event happened / was handled — remove it.
[SCHEDULE_CANCEL:label]The event is no longer going to happen — remove it (distinct from resolved for clarity in logs).

The GM gets a duration reference table in the prompt so estimates stay consistent: combat round ≈ 1 min · conversation 1–5 min · searching a room 10–30 min · an errand 30–60 min · travel = hours (judge by distance) · a rest 6–12h. This is the "will take tweaking" knob.

Firing & jump-safety load-bearing

Firing = surface to the GM; the GM mutates. When now ≥ dueMin, the engine does not silently change state. It surfaces the event under "HAPPENING NOW" in the prompt; the GM narrates it and emits any consequent tag itself ([CONDITION_REMOVED:paralysis]). This preserves the engine's core contract — the GM is the only mutator; the engine tracks time and re-injects authoritative state. A due event surfaces for ~2 turns then auto-retires with a warn (the #29 futureEvents-hygiene lesson), so it can't nag forever.

The ≥ is not incidental — it is jump-safety. Firing is THRESHOLD-triggered (now ≥ due), NEVER exact-minute (now == due). An event due in 1 hour that the party sleeps past with a 6-hour rest (clock jumps 300 → 660, due = 360) MUST fire on waking — and it does, because 660 ≥ 360. The gap is never "checked"; the standing condition is. One comparison per pending event catches everything, robust to a jump of any size, and fires ALL events crossed in one jump (rest 6h over events at +1h/+2h/+5h → all surface, oldest-due first).

Do NOT "optimize" this into a per-minute scan or an exact match — an exact-minute check would silently skip every jumped-over event and pass casual testing. Test the failure case: schedule at +60 min, advance +360 min in one tag, assert it fires.

Narration nuance: the block distinguishes JUST-became-due ("a messenger arrives") from ELAPSED-during-a-jump ("you wake to find a messenger has waited since dawn") — same firing mechanism, the GM is told which flavor so a slept-past event reads as already-happened, not happening-now.

Injection — one shared builder

buildClockBlock() is a single pure builder injected into the volatile half every turn (never the cached stable half — a per-turn counter in the stable block would kill every prompt-cache hit, the UA5 failure). It computes all countdowns from data:

CAMPAIGN CLOCK: Day 5, 14h 30m elapsed (day labels 1-based since v1.498).
UPCOMING (computed from the clock — never invent or restate these numbers):
  • Winter solstice — in 7 days
  • Paralysis on Ammut wears off — in 6 minutes
HAPPENING NOW:
  • (nothing due)

Same re-inject-from-data pattern as the quest block, character sheet, and [LOCATION_DESC:]. Both buildSysPrompt and Table Talk's ttStateBlock call it — which is how #73 makes the solstice question answerable in Table Talk (#76) with (near-)zero change: TT gets the computed countdown by calling the shared builder, honoring the coupling promised when #76 shipped.

Deliberate v1 boundary (flag for the user). The user ratified "clock is authoritative for time-of-day". v1 does NOT deliver that yet — it keeps the v1 clock as an elapsed-time counter and leaves free-text [TIME:] / world.time ("dusk") untouched as narrative flavor. There is no conflict for the #73 fix, because scheduling runs on clock.min, not world.time. Retiring [TIME:] and deriving wall-clock time-of-day belongs with the calendar (both are the display / date-projection layer, and both touch the Sync modal), so they land together in the fast-follow rather than half-wiring the Sync modal now. This keeps v1 tightly scoped to the actual bug on a drift surface.

The named in-world calendar fast-follow

With minutes-since-epoch, a named calendar is a pure read-only projection over the same scalar: an epoch anchor ("begins 1st of Frostfall, Year 823") + month names + fixed month lengths → any clock.min maps to an in-world date via deterministic modular arithmetic in the engine (the model does none of it).

Not just flavor. It upgrades the scheduler: a deadline as 21st of Deepfrost is an absolute anchor — self-correcting, never re-stated — versus +11d, which is relative to when it was set and fragile if set twice. Fixed-date deadlines (solstices, festivals, "the tax is due on the 1st") become first-class. The delightfully-ridiculous month names ride on top for free.

⚠ Keep the calendar SIMPLE — fixed month lengths, no leap logic. It's a fantasy world; we make the rules, and simple rules stay deterministic and testable.
