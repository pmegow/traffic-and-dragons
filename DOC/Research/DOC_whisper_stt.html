Whisper STT — where transcription should run, and why the car is failing

TODO #113 exploration + TODO #77 (input proofreading) design pairing · 2026-08-03 · findings only, no code shipped. Grounded in stt.js at v1.535 and the field report "practically unusable in the car."

TLDR: The car problem is mostly not a "wrong engine" problem — it is four smaller mechanical problems stacked: a Bluetooth hands-free mic path that feeds Whisper telephone-grade audio, a fixed 15-second recording window with no silence detection, the oldest transcription model OpenAI still serves, and — the cheapest finding in this report — we never send Whisper its prompt bias parameter, so it has no idea "Frizwick" or "Sandpoint" are words. Recommendation: GO on four targeted upgrades to the existing cloud path (§4), DEFER self-hosted Whisper until the subscription model makes us the payer, NO-GO on local WASM Whisper — it is the one option that makes the car case worse. #77's read-back-confirm should ship after the upgrades, gated on a confidence signal Whisper already returns, so it interrupts only when suspicion is earned (§5).

1 · What we run today (the control)

stt.js has two fully separate paths:

  • Native — Web Speech API (webkitSpeechRecognition): Chrome/Edge desktop + Android Chrome. Free, streaming, no key. Not Firefox; not iOS Safari at all.
  • Cloud fallback — getUserMedia → MediaRecorder (audio/mp4 on iOS, webm/opus elsewhere) → hard 15s auto-stop → multipart POST to OpenAI /v1/audio/transcriptions with model=whisper-1 on the player's own OpenAI key → sttCorrectNames (deterministic roster-phonetic repair) → input box. This is the only path iPhone Safari / Car Mode has.

The key-ownership property (player pays for their own transcription) was decisive in declining LiveKit and remains a hard constraint worth keeping.

3 · The three options (#113's frame), costed

① Local WASM Whisper (whisper.cpp / transformers.js — the Piper #41 pattern) NO-GO

  • Only phone-feasible models are the worst ones. tiny/base (~75–145 MB) are the ceiling for browser WASM on a phone; their noisy-audio accuracy is far below API-side large models. The car case needs the most accuracy headroom; this option supplies the least.
  • Latency: WASM realtime factors of roughly 1–3× on mobile Safari mean a 12s utterance costs 10–30s of compute before the text exists — after the recording already ended. In-car that is unusable by construction.
  • Memory: a second ORT/wasm inference stack living beside Piper is exactly the iOS jetsam class the B9 arc spent weeks beating down (wasm linear memory grows and never shrinks; the r8 recycle exists because of it). The monotonic-resources rule says don't add a second ratchet to the same page.
  • Cost: $0/utterance, one ~100 MB download — but the car is an online context; offline STT solves a problem the car doesn't have.

② Self-hosted Whisper on the Fly box (the #90 tnd-tts pattern) DEFER

  • Viable: faster-whisper small/medium on CPU fits the existing warm-daemon + volume machinery; auth via the game session token is already built; it removes the OpenAI-key requirement for connected players and mirrors TTS_LADDER cleanly (native → server → cloud-on-player-key).
  • Costs (our box): small wants ~1–2 GB RAM, medium ~3–5 GB. On Fly that is roughly a $5–15/mo machine if it rides the auto-stop pattern (with a 2–5s cold-start on first utterance), $15–30/mo kept warm. Not painful, but it buys accuracy no better than the API's mini model while moving the bill from the player to us.
  • Why defer, not decline: under the subscription model we become the payer anyway and the endpoint slots into the same routing table. Until then, the player-key path costs us $0 and the player fractions of a cent (below). Revisit when the server-proxy work (#115's long-term half) happens.

③ Status quo + targeted upgrades GO

Keep the architecture (native where it exists, cloud on the player's key elsewhere) and fix the four mechanical failures — see §4.

4 · The recommended upgrades (all to the existing cloud path)

  • (a) Send the prompt bias — the biggest accuracy-per-line in the report. Build it from what the engine already knows: party + roster names, current location/sublocation, active quest titles ("Frizwick, Morwen, Ammut, Sandpoint, Thistletop, …"). This attacks the Frizwick→Physics class at decode time, where it is cheap, instead of after the fact. sttCorrectNames stays as the second net. One caution: the prompt biases — it can occasionally hallucinate a roster name into unrelated speech, which is exactly what the #77 confidence gate (§5) exists to catch.
  • (b) Model swap to gpt-4o-mini-transcribe (better noisy-audio WER, half the price), with whisper-1 as fallback on error — a PROVIDERS-style constant, not a hardcode.
  • (c) Silence endpointing (VAD-lite): a WebAudio AnalyserNode energy gate — stop the recorder after ~1.5s of sustained silence, and raise the hard cap from 15s to ~45s. No dependency, no wasm. The driver stops talking; the app stops listening. This also un-truncates long directives.
  • (d) Mic-path hygiene: audit getUserMedia constraints (echoCancellation/noiseSuppression/autoGainControl — defaults tuned for calls can hurt far-field dictation); log the active input device's sample rate into the #16 breadcrumbs so we can SEE the narrowband-BT case in field reports; add a Car Mode help note ("your car's hands-free mic is telephone-quality — the phone's own mic hears better"). We cannot fully control iOS audio routing; we can at least measure and say it.

5 · #77 — input proofreading / the read-back-confirm gate

The row's ask: a verification pass — the GM reads back what it heard and asks for confirmation before acting, toggleable, because in the car the player cannot see the input box. The row also assigns it the multiplayer voice-misattribution backstop (Q5/D13). Design findings:

  • Layer it under the upgrades, not instead of them. §4a+b should eliminate most of the garble class this row was filed about. Ship them first, measure (log sttCorrectNames hit rates + correction distances through the existing watch-log pattern), then tune how aggressive the confirm gate must be.
  • Confidence-gated, not always-on. The row itself worries the pass may irritate ("needs to be played a bit"). Whisper's verbose_json response already carries per-segment avg_logprob and no_speech_prob — a free suspicion signal. Confirm only when: confidence is low, OR sttCorrectNames had to make a far edit, OR the transcript contains an out-of-roster capitalized noun. High-confidence clean transcripts auto-send exactly as today.
  • The read-back needs no second model call. Speak the transcript itself through the existing TTS ladder ("I heard: Show Corynn the symbol — send it?") and accept spoken yes / no / again via the #78 spoken-pick vocabulary (parseCarCommand already owns this grammar). An LLM "nonsense filter" (Haiku-class, ~$0.0001/utterance) is a possible third layer but should wait for field evidence that the deterministic gates miss things.
  • Placement: File ▸ Admin toggle per the row; default ON in Car Mode, OFF elsewhere. The confirm moment is also the natural home for the multiplayer misattribution backstop — the spotlight player hears words they didn't say and declines — so no separate speaker-ID machinery is needed unless that ever proves insufficient.
