01 / Start with what already works

The existing hot-seat game is already multiplayer in its fiction and turn structure. mpQueuePush records each active PC’s action, mpAssembleRound orders the declarations, and the final submission goes through one GM call. Remote play should preserve that shared moment of resolution. It should not create four independent campaigns and attempt to merge their prose afterward.

Scope assumptions

Four total active players on desktop browsers, invited friends, synchronous sessions, one character per seat, one shared campaign, text as the reliable baseline. The inviter is also a player. If the intended limit is host plus four guests, use a five-seat configuration and rerun pacing, capacity, and ownership tests; the protocol should not encode four array slots. This remains an unresolved owner choice.

Public matchmaking, spectators, real-money trading, cross-campaign competitive progression, built-in voice chat, private whispers with secret canon, and offline multiplayer writes are excluded from the first release. These exclusions keep the pilot focused; they do not imply those experiences are impossible.

02 / Make four people feel like players

The main risk is waiting, not network latency. Passing one phone guarantees a single writer but makes everyone else a spectator. Remote PCs should allow parallel planning while still producing one agreed round.

  1. Create a private table. The owner chooses a campaign copy, announces who pays, sets an optional spend cap, and agrees with the group on tone, content boundaries, absence policy, and whether everyone may read every scene. No account or API key is shared.
  2. Join and claim a seat. An invitation admits a named guest to a waiting room. The owner confirms the person and assigns an unclaimed character. A connection is not consent to import a character, expose past campaign history, or spend their money.
  3. Read together; draft independently. Everyone sees the same committed scene, the four sheets they are allowed to inspect, and a small turn board. Each browser keeps its own spotlight and unsent draft. Looking at another sheet never changes who the next command belongs to.
  4. Post intentions, then agree. Posted declarations are visible to the table; unfinished typing is private. “Ready” acknowledges the current shared planRev. Editing a posted intention clears prior readiness. Players can discuss combinations, revise, help, or explicitly pass before any model call is bought.
  5. Resolve once. The facilitator can press Resolve only when every participating seat has acknowledged the same plan. The server atomically freezes its actor IDs, declarations, and revision. The last ready click does not unexpectedly spend money. No network request order becomes initiative.
  6. One result, four consequences. Show the common narration plus a concise per-PC outcome and resource receipt. Helping counts as an action; identical actions can cooperate without erasing their authors. Canon changes once, and the next board starts from that committed revision.
  7. Pause or finish cleanly. Any player can request a pause. The session ends with a factual recap, unfinished choices, the last committed revision, and export options. A round interrupted by disconnection resumes with its saved declarations, not reconstructed guesses.

Waiting, interruption, and social safety

No default countdown executes an absent player’s character. After a proposed 90-second idle interval, show “Waiting for Cora” with pause/reconnect options, not a punishment. Groups may pre-agree to a narrowly described defensive/pass policy; the affected player can revoke it. Without that consent the group pauses. Removing a disruptive member revokes access immediately, but does not authorize invented actions, retroactive history edits, or automatic redistribution of their items.

Text chat is a separate, bounded out-of-character channel and never automatically feeds the GM. A player can deliberately turn a message into their own action. Safety pause and content-boundary controls sit outside the model, apply to everyone, and do not require a player to explain a personal reason publicly. PvP, taking another PC’s possessions, or speaking for them requires explicit table rules and affected-player consent; a host checkbox alone cannot stand in for it.

Audio, accessibility, and short sessions

Use text-first PC play and an optional external group voice call for the pilot. In-game narration is opt-in on each computer, captioned, independently replayable, and never a condition for the next Ready. A shared event ID prevents replay on reconnect. Local speech-to-text requires an explicit mic action and a visible review before sending; it cannot infer which player spoke into a shared call. This avoids repeating the Safari permission and Bluetooth mic-routing problems as a required group-play loop.

A proposed 180-word group narration at 180 words/minute takes a full minute to hear. Add 30 seconds of parallel planning, 10 seconds of review and 12 seconds of model time: about 112 seconds per round, or roughly ten rounds in twenty minutes before setup. Those are illustrative inputs, not measured performance. Four separate 180-word monologues would consume four minutes in narration alone. Test short shared prose with distinct consequences, not equal word quotas.

Keep keyboard-only access, screen-reader announcements for readiness and reconnects, readable zoom, draft preservation, and a silent mode. A “twenty-minute table” needs a join target and a clear ending, not only fast inference.

03 / Method A — a hosted private table

A

The owner’s browser runs the game.

Guests join a dedicated room client. A relay admits seats, stores declarations and receipts, and distributes public results. The existing engine and model credentials stay with the owner.

Best fit

Friends who already trust one person to host a tabletop session, can schedule together, and accept that closing the host’s browser pauses the table.

Hard limit

The host can inspect or falsify the game’s private state. A relay cannot prove that a browser-owned engine behaved honestly.

↔

↔
GM providerOne frozen round becomes one candidate result

This is not screen sharing or remote desktop. Guests get their own sheets, drafts and ready controls; they never receive the owner’s login, keyboard access, API keys, raw prompt, memory archive, or whole save. A screen-share call remains a useful zero-build playtest, but offers poor independent reading and character control.

One round through the system

The relay authenticates every intent and binds it to a seat-owned pcId. On Resolve, it freezes an immutable batch and assigns roundId, baseStateRev, batchDigest and hostEpoch. The host adapter applies that batch to the existing multiplayer flow through one reviewed entry point. It must not loop over UI sendAction() calls: the last one currently triggers resolution and display-pointer state is not a secure actor binding.

The host computes a candidate from the last acknowledged checkpoint. It submits an owner-private checkpoint and an allowlisted public result together. In a short database transaction, the relay checks the exact base revision, frozen batch, current host epoch and unused round result, then stores checkpoint + public event + receipt atomically. Only then may clients display the result as committed. A timeout after upload means query the receipt, not call the GM again.

The relay validates envelope shape and authority, not the truth of the host’s game mutations. That distinction must appear in the product promise. A malicious guest should not control another PC; a malicious host remains capable of cheating. Do not use A for competitive rewards or claim private secrets are protected from the host.

Identity, persistence, and availability

A new room gets opaque room and PC IDs, separate from legacy account campaign IDs. An explicit import step maps each PC ID to the legacy hero/roster entity and rejects ambiguous names before starting. Renaming/importing/reassigning a participating PC is blocked during a frozen round. This adapter is a bridge to #202, not a replacement for the full entity-identity decision.

Only one host lease is valid. A second host tab is read-only until an explicit takeover increments the epoch; stale tabs cannot commit. Guest disconnects preserve posted declarations but do not imply consent for future rounds. Host loss pauses resolution, and guests may keep local unsent drafts. Reconnection reloads the relay’s last acknowledged private checkpoint and pending round. No automatic guest promotion: it would require handing over private canon and provider authority.

If a provider call’s outcome is unknown after a crash, display an “unresolved attempt” and reconcile the stored response/receipt if available. The owner may deliberately authorize a new attempt, acknowledging possible duplicate billing. Saving the host’s raw candidate before commit narrows this window but cannot eliminate a crash between provider completion and durable receipt.

Cost and implementation shape

The owner’s existing provider arrangement funds GM calls. Guests incur no inference charge merely by joining. The relay cannot enforce a hard budget against the owner’s direct provider key; its limits protect the room workflow, while provider-side key limits protect the bill. Paid narration is disabled by default for guests in the pilot; local/browser speech is an optional convenience with variable quality.

Build a small room client and host adapter, a relay service and durable room tables. Keep the solo client’s dependency-free delivery intact. The implementation still touches protected game/state seams and requires the project’s Fable review. “Reuse the engine” is not authorization to duplicate its parser or bypass its commit lifecycle.

04 / Method B — a durable server-run table

B

The server runs the game.

Browsers send commands, never authoritative saves. A room worker assembles prompts, calls the GM, validates the candidate and commits canonical state. All clients, including the owner’s, read projections.

Best fit

Groups that need another authorized facilitator to resume without the original owner’s PC, durable recovery, or stronger isolation between accounts.

Hard limit

This moves trust to the service operator and model provider. It is not end-to-end encrypted gameplay or immunity from prompt injection.

↔

One round through the system

The server freezes the agreed plan, reserves the maximum permitted spend, and creates a durable job with a unique result identity. A worker claims it with a fenced lease, builds the prompt against a pinned state/engine version, and calls the provider outside any database transaction. The raw response and usage are recorded. A reviewed reducer validates and applies the permitted game mutations to a copy, then atomically commits state, transcript entries, events, final usage and an outbox record. A separate broadcaster delivers the outbox; clients deduplicate by event ID.

A unique committed result per round prevents duplicate world changes even when network messages repeat. It does not guarantee exactly one paid upstream call. If the provider lacks a usable idempotency/retrieval mechanism and the worker crashes in the ambiguous window, pause and surface that ambiguity before another attempt. Do not hide it behind an unlimited retry loop.

What must move, and what must not fork

The canonical runner needs explicit inputs and outputs for prompt construction, tag parsing, memory, campaign clock, character identity and turn commit. The Node test loader demonstrates that portions can execute headlessly; it is not a production isolation boundary. Extract a versioned shared engine package or equivalent immutable source bundle, then prove browser/server parity on real transcripts, frozen prompt halves, mutation diffs and legacy saves. Do not maintain independent browser and server parsers.

Isolate concurrent rooms. Today’s engine globals must not be swapped in one shared context while asynchronous GM calls overlap. Use bounded, isolated room workers or a genuinely explicit state context with one canonical engine source. Test two simultaneous rooms with distinct private canaries through prompt assembly, memory, callbacks and errors. Uploaded campaigns remain data; an execution context is never permission to run uploaded JavaScript.

Fit the existing architecture decision. Server architecture §6 / Decision 7 already ratifies staged authority: shadow verification, canonical server turns, then multiplayer, while keeping local/BYOK play. B follows that direction. A is a proposed interim pilot that requires an explicit product choice; this exploration does not replace that decision or authorize a big-bang engine rewrite.

Take #202 seriously: stable IDs for campaign entities, explicit alias/name resolution, ownership by immutable PC ID, and migration checks for duplicate names and references. Per-client UI focus stays local. A server decision is not a client’s activePC. Rooms pin their engine version; upgrades happen at a committed round boundary with a checkpoint and rollback plan.

Use a canonical room namespace that legacy /api/state, campaign import, sync-modal writes, checkpoint restore and character-library writes cannot mutate. A downloaded campaign may become a separate solo fork; it cannot be uploaded as the authoritative room. Progression exported to a member’s library is a previewed snapshot with provenance, never an automatic overwrite of their personal character.

Service, credentials, and continuity

Start with a single room coordinator and a transactional store on the existing backend footprint if load tests support it. SQLite can serve this pilot with short transactions; WAL still has one writer at a time, so never hold a write transaction during inference. Multi-instance deployment requires a real shared authority and fencing, not independent SQLite files on different machines. SQLite WAL documentation.

B requires a deliberate funding decision. A pilot could vault an owner-supplied provider key, encrypted under a separately managed service key with access limited to the inference worker; keys are never returned to clients or included in prompts/logs. That changes the current local-BYOK trust promise and needs explicit owner consent. A service-funded allowance is a separate product/billing project, not assumed here. Reserve spend before dispatch and settle actual usage afterward; cap GM, suggestions, recaps, image and narration jobs together.

Durable membership binds each seat to an account; a room-scoped guest can be provisional during onboarding but must be claimed before reliable later re-entry is promised. Both GitHub and Google OAuth exist in the inspected backend. Reuse a guest’s own supported identity after hardening the handoff; verify deployed availability and test onboarding with nontechnical friends rather than assuming they need a developer account. Anonymous admission, if retained, needs a clear warning that an unclaimed seat is not a durable recovery identity.

The original owner can leave without losing the table only if another facilitator was authorized in advance and the funding policy remains valid. Service availability does not mean an unattended campaign advances by itself. The same consent, pause and absent-player rules still apply.

06 / Security is part of the table rules

Confirmed local prerequisite: repair campaign ownership on save. The current server checks existing rows using campaign ID + user ID, then performs an ON CONFLICT(id) DO UPDATE without the same owner restriction. An isolated in-memory SQLite test using the actual SQL and synthetic users confirmed that a different authenticated user can overwrite a known campaign ID while its owner field remains unchanged.

No production endpoint, real account, credential or campaign was tested. This is a verified local-code defect, not a claim about the deployed build. Fix and regression-test cross-account update refusal before issuing multiplayer invitations; audit sibling mutation routes at the same time. Opaque IDs reduce guessing but never substitute for authorization.

Assets: account/provider credentials; private GM canon; public transcript; PC inventory and progression; player identity and consent; availability; the payer’s budget. Adversaries: an uninvited link-holder, malicious admitted guest, compromised browser, malicious host (A), a stale host/worker, and an abusive client that bypasses the UI. Providers and the service operator remain explicit trust parties.

Credentials and origin: a concrete boundary

For A, owner login creates the room and exchanges into a narrowly scoped host capability; admitted guests get separate seat capabilities. HTTPS commands carry short-lived room authorization. WSS receives a one-use, short-lived connection ticket in its first authentication message, not the owner token or a query-string secret. Until authentication succeeds it sends no room data and closes after a short timeout. Each socket is tied to a live membership record, not merely a valid signature.

For B, prefer serving the dedicated multiplayer client and its API under one HTTPS origin, using a secure HttpOnly same-site session and explicit CSRF protections for changes. That needs routing/hosting work; it is not already provided by a static Pages frontend plus a cross-origin Fly API. Initial cross-origin deployment must retain the narrowly scoped token protocol instead of assuming cookies will work. Either way, the legacy file:// experience stays separate from remote-room permissions.

Ownership of characters and campaign history

The campaign has one declared owner and an explicit retention/export policy. Each player controls their own intent and consent to delegation; the authority applies game consequences. A guest cannot edit gold through a local sync screen. On joining an old campaign, the host previews which existing public history is shared. A player can export their character and the shared narrative they were entitled to see, but receives no private GM memory or other account’s library. Leaving never silently deletes or hands over the character.

08 / Panel of experts — nine grounded reviews

The review applied the project’s nine existing expert rubrics to both methods. These are simulated evaluations of documented principles, not statements, interviews, or endorsements by the named people. The numbered references below identify the source entries used; applying those principles to remote play is reviewer inference. “Primary” and “secondary” describe the evidence grade in the existing lens files.

Collective result: choose the authority model for operational needs, but make the table’s agency and resolution contract identical in both.

Gary Gygax lens · consistency and consequential procedure

Source: 1.1, 1.2, 2.4, 5.2, 5.3, 7.3 · primary.

A: One referee can give consistent adjudication, provided the group knowingly trusts the host. Rewriting a guest’s declaration defeats that arrangement. B: Central authority helps maintain one set of facts, but duplicate packets must never become extra fictional time, rewards, or consequences.

Required: Document when a round locks, how cooperation is adjudicated, and which action pays a cost. Advance the campaign clock once for the resolved fiction; time spent waiting for a network does not advance it.

Test: Repeat the final command and reconnect a player: one round, one clock change, one reward. Check that different classes contribute distinct actions.

Limit: the lens records reservations about computer storytelling (§0.1/§8). It cannot honestly be presented as blanket approval of either AI GM.

Robin D. Laws lens · attention and table needs

Source: 1.1, 4.3, 8.1–8.4 · primary; 6.1–6.2 · secondary.

A: Parallel drafts shorten the serial handoff, but host departure can still end everyone’s evening. Host approval of every individual draft would add another bottleneck. B: A durable queue preserves work; it does not make waiting entertaining.

Required: Let the group talk while planning, keep clarification separate from paid resolution, show who is ready, and offer a public factual recap on return. Do not put essential shared clues only in a disconnected person’s private channel.

Test: A quiet player and a slow typist join a casual group. Measure the first-ready person’s wait, whose choices matter, and whether a returner understands the scene.

Limit: these principles provide no sourced latency threshold or infrastructure preference.

John Harper lens · intent, stakes, and consent

Source: 1.2, 1.7, 5.1, 7.8, 7.9, 9.4 · primary.

A: Paying for the GM does not authorize the host to choose another player’s goal. B: A server can preserve a declaration exactly and still resolve a bargain the player never accepted.

Required: Everyone sees the posted plan and acknowledges that revision. Editing it resets readiness. Conflicting “negotiate” and “attack” intentions require clarification before locking, not a winner chosen by packet arrival. Help states what the helper actually does; any offered price is agreed before commitment.

Test: Opposed plans, a costly bargain, and a joint action preserve authorship and expose their costs.

Limit: this applies the lens’s agency principles; it does not import Blades’ stress, position, or flashback rules into this game.

Baker lens · play remains a conversation

Source: 2.3, 3.4, 4.3, 6.3, 7.1, 7.4 · primary. Apocalypse World principles credit coauthors Meguey and Vincent Baker.

A: A host can keep the conversation moving, but “disconnected” must not mean “passed.” B: Always-available infrastructure must not become permission to puppet an absent character.

Required: Distinguish drafting, posted, ready, passed, paused, and disconnected. Allow player-to-player answers without the GM inventing them. Record any narrow absence agreement and let the affected player revoke it.

Test: Disconnect before Ready, after Ready, and during generation. At each point, players can explain which choices were authorized and what will happen next.

Limit: the precise timeout and delegation protocol is a design inference, not a rule supplied by the lens.

Jenna K. Moran lens · room for different contributions

Source: 3.3, 5.3, 8.1 · primary; 2.6 · secondary.

A: Guests must be coprotagonists, not extra combat slots in the host’s story. B: Durable character history helps, but mandatory activity every round can turn participation into chores.

Required: Helping, listening, a personal goal, or explicitly yielding the spotlight can be meaningful choices. Avoid performance rankings, equal-prose quotas, and rewards for supplying the “correct” emotion.

Test: A quiet character supports another’s scene without disappearing from the fiction or being forced into busywork.

Limit: no change to this game’s XP economy is implied, and a player choosing to pass remains a player.

Ursula K. Le Guin lens · a readable ensemble

Source: 1.1, 1.2, 1.8 · primary; 4.1–4.5, 5.1, 6.1, 6.3 · secondary.

A and B: Neither transport earns a literary preference. Both need one coherent scene in which distinct acts remain legible. Four parallel monologues are likely to obscure relationships and rhythm.

Required: Keep the existing D12 third-person multiplayer narrator, attribute speakers/actions clearly, and allow caring, observing, or carrying something to matter. Put network and readiness notices outside the prose.

Test: Read and listen to a corpus of two- and four-PC scenes, including similar names. Check attribution, rhythm, and whether quiet contributions survive.

Limit: craft principles are not networking expertise. The multiplayer D12 decision stands; solo narration is unchanged.

Fritz Leiber lens · companionship with consequences

Source: 3.1–3.5, 4.1–4.2, 10.1–10.2 · secondary critical readings.

A: The host’s PC must not make guests into sidekicks. B: Saving everyone’s inventory does not itself preserve a developing relationship.

Required: Permit direct PC conversation, remember consequential cooperation and friction, and aim for a modest payoff and stopping beat within a session. The GM need not arbitrate every exchange between friends.

Test: The party disagrees, chooses a joint course, and later encounters a concrete callback to that choice.

Limit: this lens rests on critical interpretation of fiction; it is not an invented statement by Leiber about AI or online games.

Joe Abercrombie lens · distinct people, visible consequences

Source: 1.2, 1.5, 5.1, 5.5, 7.3, 8.1, 8.4 · primary.

A: One host-controlled narrative can flatten everyone into that host’s perspective. B: A server preserves identities only if narration also respects them.

Required: Keep speech and action attribution distinct. Never invent a silent player’s agreement, confession, or emotional reaction as a substitute for their input. Success, failure, and partial success should have legible consequences.

Test: Four contrasting PCs attempt the same scene; compare their accepted intentions with the resulting actions and costs.

Limit: novelist craft does not grant control over a human player’s inner life, and this review does not request darker or more graphic content.

N. K. Jemisin lens · discovery and meaningful agency

Source: 1.8, 7.1–7.4, 9.3–9.4, 10.1, 10.3 · primary.

A: State plainly that the host can see hidden canon. B: A filtered state projection is useful, but a recap or model-generated sentence can still spoil what players have not learned.

Required: Separate revealed knowledge from engine truth; disclose that initial split scenes are shared with the table. Choices must change something the group can observe, rather than merely decorate a predetermined path.

Test: Seed unrevealed facts, then inspect narration, recaps, maps, reconnects, and exports. Compare two materially different group decisions.

Limit: literary discovery principles motivate this test; they do not establish a technical secrecy guarantee.

Expert-panel synthesis

The strongest shared requirements are a written authority contract, an explicit interruption protocol, consequential participation for every seat, safe factual recovery, and actual-session evaluation. Tensions remain: procedure versus pace; space for quiet play versus pressure to finish; a unified narrator versus distinct identities; and central adjudication versus player agency. None is resolved by counting simulated votes. The engineering recommendation for A as a pilot is this document’s judgment, not an endorsement attributed to the panel.

Nan Oyelaran · a small session that actually finishes

Player-panel synthesis and missing voices

Short-session players may resist the review step that authorship-focused players need. Individual audio control helps Rosa but cannot set the whole table’s pace. 11 / Delivery, migration, and operating cost

Stage the work around evidence

  1. Security and play contract. Fix the save ownership bug with a two-user isolation test, audit mutation siblings, decide payer/owner/member roles, approve the room trust model, and design #22b/#202 migration boundaries. No invites before these pass.
  2. Four-browser prototype. Synthetic campaign, no real provider key, deterministic fake GM. Prove admission, independent drafts, plan revision, ready/resolve, pause, duplicate rejection and reconnect. Observe actual players before substantial engine migration.
  3. A private pilot. Add reviewed host adapter, durable commit/checkpoint, projection and bounded authenticated relay. Use disposable campaign copies and trusted invited groups. Test a 90-minute session plus host restart.
  4. Decision checkpoint. Continue A if people enjoy the table and accept host dependence. Choose B if required by measured interruptions, persistent membership, untrusted hosts or stronger private-view requirements. Do not market B guarantees on A.
  5. B migration, if chosen. Extract shared runner, stable entity IDs and idempotent commit core; shadow-run deterministic transitions and stored model responses against browser results; enable one isolated server-owned room only after parity and restore drills.

Effort estimates, not quotes: for one experienced engineer familiar with this codebase, A is plausibly 3–6 engineering weeks including hardening and four-client testing; B is plausibly 8–16+ weeks including runner extraction, identity migration, credential handling and operations. Discovery of existing defects, auth onboarding, secret scenes or integrated voice can exceed those ranges. A’s reusable room UI/protocol reduces some B work but does not make the canonical-engine migration free.

Model calls dominate the variable bill

Let R be rounds, Cg the measured cost of one full GM resolution, Ca the cost of auxiliary calls per round, and Ct narration cost per round. An approximate session model is R × (Cg + Ca + Ct) + room compute + storage/egress. Measure token/cache usage with real four-PC prompts. One shared GM call avoids multiplying the entire story call by four, but four action inputs, character sheets, suggestion requests and longer output can still increase costs materially.

For A, the owner directly bears provider cost and the service pays relay/storage. For B, the service must control reservations, provider timeouts, quota exhaustion and settlement. Cache a single licensed/generated narration asset for authorized listeners if later offering shared paid TTS; do not naively synthesize the same paragraph four times. Asset access expires with membership, and retained downloads cannot be recalled.

Start with operational measurements rather than a cloud price promise: concurrent rooms, messages/second, retained bytes, p95 command acknowledgement, GM latency, reconnect catch-up, failed/ambiguous provider attempts, per-room cost and rejected commands. Initial target: command acknowledgement under 500 ms at p95 on ordinary broadband, excluding the model; visible resolving time updated each second. Load-test 25 concurrent four-seat rooms as a pilot envelope, not a capacity claim.

Safe rollout and rollback

Remote play creates a new campaign copy with an explicit migration receipt and immutable checkpoint. Solo originals remain unchanged. Export before migration; test rename collisions, missing PCs, dead PCs, split parties, mature transcripts and corrupted input. Snapshot + committed event cursor + pinned engine version is the recovery unit. Feature-flag room creation independently of existing-room recovery. On rollback, stop new commands and preserve readable/exportable history; never downgrade a new save schema silently.

Implementation changes to prompt construction, tags, memory, state, clock and game commit touch the project’s protected drift surface. This document authorizes no such change. They require the specified Fable design/review workflow and regression evidence. Research itself does not require a game-version or cache bump.

Security findings

S1 · The ownership defect is live today, its honest trigger is save import, and the prescribed fix would break that workflow

§01 “Observed today” row 5 · §06 “Confirmed local prerequisite” · §13 review row 1 · Severity: high · Verified against server index.js and client source

What the document says. “Fix and regression-test cross-account update refusal before issuing multiplayer invitations … Opaque IDs reduce guessing but never substitute for authorization.” The defect is filed as a multiplayer prerequisite and framed as an attacker who knows a campaign ID.

Why that is wrong in three ways. First, the population that can reach the hole is not “invited guests” but anyone: index.js:184 gates every /api/* route on the existence of a session only, and a session is minted for any GitHub or Google identity with no allowlist. The exposure exists for the solo product now; invitations add nothing. Second, campaign IDs are neither opaque nor secret. state.js:955 mints them as camp_<timestamp>_<4 digits>, every .tnd export carries worldState.campId, and importSave (ui-files.js:562, “reuse the file’s own campId if present”) adopts it as the active campaign. The receiver’s next autosave posts that ID (storage-adapter.js:563) and the upsert at index.js:593–603 lands on the sender’s row. The “friends exchange files” workflow the pilot depends on is the exploit, with no malice and no guessing. Third, the turn-based CAS guard the §01 table presents as an existing protection cannot help: it runs only when the client sends a numeric baseTurn (index.js:566), and its lookup is owner-scoped (WHERE id = ? AND user_id = ?), so for a second account it finds no row and passes. Afterwards the original owner’s next sync gets a 409 “another device is ahead”, which disguises the overwrite as a benign device conflict.

Why the fix as written is incomplete. “Cross-account update refusal” alone turns the importing friend’s campaign into a zero-row write that still returns {ok:true}; the client’s _flushAcked clears its dirty marker on any 2xx, so the friend’s campaign silently never saves. The §12 Isolation gate as worded would pass either outcome.

Fix. Reclassify as a live solo-product security bug with its own TODO row and an immediate fix independent of #1. Fix in three parts: (1) the write itself carries the owner predicate — ON CONFLICT(id) DO UPDATE … WHERE campaigns.user_id = excluded.user_id; (2) zero rows changed returns 403 with a reason code, never {ok:true}; (3) importSave re-mints campId when the file’s ID is not one this account owns. Make the two-user isolation test send the forged ID both with and without baseTurn, and add the honest case: account B imports account A’s export, plays a turn, syncs; A’s row is unchanged and B’s campaign saves under a new ID.

S2 · The host page is inside A’s hostile-input boundary, and it has an unescaped model-text sink

§06 “Hostile input” · §12 Hostile-input gate · Severity: high · Verified against client source; the sink was reproduced

What the document says. The sanitization and CSP requirements are written for the room client (“A dedicated room CSP avoids third-party scripts”), and the §12 gate never names the page it runs against. Under A the host engine is the owner’s unmodified index.html, which holds the Anthropic key, per-provider keys, the fal key and the account bearer in localStorage (state.js:1, storage-adapter.js:17) and ships with no Content-Security-Policy in index.html, _headers or sw.js.

The concrete hole. Narration is escaped (escProse, helpers.js:6; game.js:2433) and the suggestion buttons are escaped, but diceTxt (api.js:2832) is not: for a [DICE:label|roll|note] tag it splices p[0] and p[2] — raw model text — straight into HTML that lands in the host DOM through innerHTML (game.js:2433 via addMsg, game.js:2680, ui-boot.js:390 on transcript replay). A model that emits [DICE:<img src=x onerror=…>|12|] runs script in the host origin. In A every guest declaration is prompt-injection input to that model, and the §06 prompt-injection row already concedes the model can be steered; the sink turns steering into credential exfiltration against the payer, the highest-value target in either method. The [CHECK:] branch of the same function escapes its label correctly, which shows the omission is accidental, not a design choice. L1 · Method A commits locally before the relay commits, and the host’s other mutation surfaces never touch the relay at all

What the document says. “The host computes a candidate from the last acknowledged checkpoint … In a short database transaction, the relay checks the exact base revision, frozen batch, current host epoch and unused round result, then stores checkpoint + public event + receipt atomically” and only then may clients display. For B the document says the worker “applies the permitted game mutations to a copy”; for A it never says the candidate is computed on a copy, and it tells the adapter to reuse “the existing multiplayer flow through one reviewed entry point”.

Why it cannot work as written. That entry point is the tail of sendAction: mpAssembleRound → callGM → commitGmTurn. commitGmTurn (game.js:2296–2420) is single-phase: turn++, transcript and sessionLog push, applyMuts, then the turn’s saveAll() — which is saveLocal plus syncToServer, a POST to the legacy /api/state row (state.js:340, storage-adapter.js:540–575) — all before any relay upload can happen, and its latch then forbids Retry. The §07 failure table has no row for a host-initiated retry or out-of-round edit.

Fix. Give A the same shape as B: the adapter computes the candidate on a cloned state (the tag-table clone-and-diff handler contract already supports state it does not own), persists an attempt record {roundId, attempt, rawResponse} before any mutation, uploads, and runs the live commit only after the relay’s accepted receipt, discarding the clone and rehydrating from the relay checkpoint on rejection. Define the checkpoint as the full save set (worldState, memory, sessionLog, transcript) plus the round record — the next prompt is built from sessionLog, so anything less desyncs it. In room mode route Retry, Rest, Sync-modal edits, reroll and level-up landings through an explicit hostMutation commit kind with its own receipt, or disable them while a room is open; suppress legacy /api/state sync for the marked campaign. Add a §12 Single-resolution case: “host presses Retry after a committed round → refused, local state equals relay checkpoint, no second charge without an explicit unresolved-attempt authorization”.

L3 · The round lifecycle has one exit from Locked, and every other outcome is undefined

What the document says. Locked/resolving → Committed. The failure table covers the ambiguous case (“outcome unknown after a crash … mark attempt uncertain”) and revocation (“suspend finalization”), and names “a finite job deadline” without a transition.

What is missing. (a) Definite failure. The commonest field failure is not a crash but a non-transient 4xx/5xx, credit exhaustion, the 240 s deadline abort (api.js:3552), or a model refusal — which today commits as a non-canon turn that still does turn++ and logs the pair (game.js:2325–2336). Add a phase × kind table with named reason codes (roundLocked, planRevStale, notParticipating): during Locked only pause and the administrative kinds are accepted, and a rejected declaration stays a local draft for the next round. State the presence rule: a Ready on the current planRev survives presence loss and Resolve may proceed, or Resolve rejects with a named code while any participating seat is absent — pick one. Define takeover during Locked as inheriting the attempt as ambiguous, rebinding the round to the new epoch, and requiring acknowledgement before re-dispatch. Record one attempt row per upstream call; set the lease TTL to the pipeline’s worst case with heartbeat renewal; add summarize and era compilation to the reserved-spend list; give rooms a job deadline shorter than the solo 3 × 240 s.

15.2 / The commit boundary A actually needs

  2. Compute an isolated candidate. Load the full acknowledged checkpoint: world state including transcript, memory, session log, canonical configuration and engine/schema identity. Credentials are not checkpoint fields. Record every upstream attempt and purpose; persist its response/usage before candidate mutations use it.   3. Accept once. Atomically verify phase, attempt, membership policy, epoch and base revision; store the complete next checkpoint, projections, receipt, usage attribution and broadcast outbox. The relay verifies the protocol envelope, not honest host adjudication.
