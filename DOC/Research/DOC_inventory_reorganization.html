Design and implementation plan · planning only

Item-bible-driven inventory organization

Traffic & Dragons · Sol · 2026-08-09 · character sheets and side panel · no game code or save data changed

Recommended design

Group every inventory row through one shared classifier, using the item bible as the authority and this fixed priority:

Weapons → Armor → Quest → Consumables → Tools → Treasure → Mundane.

Keep the existing singular category field for the item's primary mechanical type, and add inventoryCategories as a validated array for display membership. The first matching value in the global priority list wins. This supports a quest sword and a quest potion without converting the existing mechanics contract from a scalar into an array.

Unknown or invalid items must remain visible under a temporary final section named Unclassified. They must never be guessed from name fragments or silently treated as Mundane.

1. Scope and non-goals

In scopeSeven ordered inventory subsections; multi-category precedence; a shared view model for the side panel and all live character sheets; item-bible schema/editor support; explicit incomplete-bible handling; tests and visual verification.
Not in scopeNo inventory cleanup, item removal, save repair, equipment-slot system, encumbrance, drag-and-drop, automatic equipping, prompt rewrite, or conversion of character.inventory[] from strings to objects.

The implementation must be a view-only reorganization. It may change what order rows are displayed in, but it must not reorder, rewrite, merge, or migrate the underlying inventory array. The GM, save/export format, item gain/loss tags, stacking, and sync paths continue to see the same strings in the same stored order.

3. Design decisions

3.1 One ordered category registry

Define the order, internal ids, and display labels once. The classifier, item-bible editor, section renderer, validation, and tests all consume this registry rather than copying seven literals into several files.

var INVENTORY_CATEGORY_REGISTRY = [
  { id: "weapon",     label: "Weapons" },
  { id: "armor",      label: "Armor" },
  { id: "quest",      label: "Quest" },
  { id: "consumable", label: "Consumables" },
  { id: "tool",       label: "Tools" },
  { id: "treasure",   label: "Treasure" },
  { id: "mundane",    label: "Mundane" }
];

Array position is the priority. Do not store separate numeric ranks that could disagree with it.

3.2 Preserve the existing primary category

Do not change category from a string into an array. That scalar is already consumed by item-canon injection, tooltips, [ITEM_DEF:], the editor contract, and engine tests. Converting it would unnecessarily expand this UI task into the read-only drift-protection surface.

Instead, add a display-specific array:

"witchlight blade": {
  "category": "weapon",
  "inventoryCategories": ["weapon", "quest"],
  "aliases": [],
  "effect": "...",
  "uses": "at-will",
  "value": "N/A — not commonly sold"
}

The scalar remains the primary mechanical type. The array answers a different question: “Which inventory sections are applicable?” Existing entries and legacy campaign overlays without the array behave as though they contained [entry.category].

3.3 Global precedence, not array order

The registry order always wins; the order authored inside an entry is not meaningful.

Priority resultItem metadataDisplayed section
1["weapon", "quest"]Weapons
2["armor", "quest"]Armor
3["quest", "consumable"]Quest
4["consumable", "tool"]Consumables
5["tool", "treasure"]Tools
6["treasure", "mundane"]Treasure

Each stored row renders exactly once. Secondary categories remain visible in the item tooltip/editor, but never cause duplicate rows.

3.4 Unclassified is a safety state, not an eighth canon category

unclassified must not be accepted into ITEM_BIBLE. It is a UI fallback returned when there is no definition, identity resolution is ambiguous, or metadata fails validation. It renders last and only when non-empty.

This distinction matters: Mundane is a positive classification; Unclassified is missing knowledge. Treating them as synonyms would hide coverage defects and misfile current items such as a heavy crossbow, quest letters, keys, maps, and poisons.

3.5 Classification may precede mechanical definition

The editor should allow a classification-only entry whose effect, uses, or value is N/A, regardless of category. This is already safe at runtime because the item-canon prompt builder skips effect:"N/A". The editor should show a warning (“classified for inventory; not injected as mechanical canon”), not block the save.

Without this separation, classifying a quest letter or an ordinary suit of armor would force the curator to invent complete mechanics merely to put it under a heading. That would make organization hostage to the slower canon-writing pass.

3.6 No fuzzy classification

The current substring equipment guess must not be generalized into seven fuzzy guesses. “Cloak” is not always armor; “blade” can appear in a document title; “token” may be treasure, quest, tool, or mundane. A miss goes to Unclassified.

For known alternate names, the bible may add an explicit aliases array. Alias matching is exact after the existing itemBaseName() normalization. It is never substring, stemming, singularization, or model inference.

4. Proposed item-bible contract

{
  category:            "weapon" | "armor" | "quest" | "consumable" |
                       "tool" | "treasure" | "mundane",
  inventoryCategories: [one or more values from the same vocabulary],
  aliases:             [zero or more exact alternate TYPE names],
  effect:              string or "N/A",
  uses:                string or "N/A",
  value:               string or "N/A"
}

Validation rules

  1. category remains required and must be one registry id.
  2. inventoryCategories must be a non-empty array, contain unique valid ids, include category, and serialize in registry order.
  3. aliases must be an array of non-empty strings. Normalize each with itemBaseName().
  4. An alias may not collide with a canonical item key, another entry's alias, or a differently keyed campaign overlay. Collisions fail loudly; they never pick a winner by object order.
  5. Instance facts still do not belong in the bible: remaining charges, owner, provenance, current count, and one specific object's condition stay outside the TYPE definition.
  6. A classification-only entry may use N/A mechanics. It remains a valid organizer entry but stays out of the GM item-canon block.
  7. Legacy definitions with no new fields remain readable as inventoryCategories:[category] and aliases:[]. Static bible export should normalize them to the full shape.
Type-versus-instance limit. The current inventory model stacks and identifies items by normalized string type. It cannot represent “one ordinary longsword is quest-related but the other identical longsword is not.” A quest-specific copy must have a distinct canonical type/name, or the project needs a separate future structured-inventory design. This organizer should not pretend to solve per-copy identity.

Why aliases are on the table

The latest save contains surface forms such as Small corked vial, violet residue, while the bible contains corked vial. The current normalizer deliberately does not strip comma clauses, and broadening it heuristically could collapse genuinely different item types. Explicit aliases let the curator connect proven equivalents without weakening identity.

Alias resolution affects more than display if it is added to itemLookup(): tooltips and volatile item-canon injection will also begin resolving those names. That is desirable consistency, but it is drift-surface-adjacent. It should receive the same focused review as the current identity-hardening work before shipping. Do not create a UI-only alias resolver that disagrees with canonical lookup.

5. Shared resolution and grouping contract

Both renderers consume one pure view-model builder. They do not classify independently.

groupInventory(inventory) → [
  {
    id: "weapon",
    label: "Weapons",
    rows: [
      { raw: "Witchlight blade — ...", sourceIndex: 17,
        key: "witchlight blade", entry: {...}, categories: [...]} 
    ]
  },
  ...,
  { id: "unclassified", label: "Unclassified", rows: [...] }
]
StepRule
1 · IdentifyNormalize the raw row. Resolve an exact campaign-overlay key, exact static key, then an explicitly declared alias. Any ambiguous alias is a loud validation failure and resolves as Unclassified at runtime.
2 · ReadUse itemLookup() as the canonical definition source. Campaign overlay continues to beat the static base.
3 · CategoriesUse valid inventoryCategories; for legacy entries, derive [category]. Do not repair invalid metadata silently.
4 · SelectScan INVENTORY_CATEGORY_REGISTRY from first to last and choose the first category contained in the item metadata.
5 · PreserveAppend a row carrying its original array index. Preserve the source relative order within each section for the first release.
6 · ContainIf no valid match exists, append the row to Unclassified. Never omit it and never place it in Mundane by default.
7 · RenderOmit empty sections. Every source row must occur exactly once across the returned groups.

The builder should be O(inventory rows + bible/alias index construction), not “scan the whole bible for every row.” Build or cache one collision-checked alias index and invalidate it only when the item bible/overlay changes.

6. UI design

6.1 Shared presentation rules

  • Show only non-empty category sections, in the fixed priority order.
  • Use compact amber text headings with a subtle divider; no decorative pills/chips.
  • Keep the current item row rendering, quantity display, hover tooltip, and mobile long-press behavior.
  • Preserve existing relative order inside each category. Alphabetic sorting can be considered later, but it should not be bundled into the first grouping change.
  • Do not duplicate a multi-category item. Its tooltip may say, for example, Categories: Weapon, Quest · Filed under: Weapons.
  • Unclassified uses a restrained warning color and a tooltip explaining that the item needs bible classification. It is not an error toast on every render.

6.3 Character and companion sheets

  • The existing Inventory sheet section remains the parent. Inside it, render the same non-empty grouped sections.
  • Do not add nested collapse controls initially; the sheet already has a parent collapse and nested toggles would add interaction noise. Reassess only after visual testing with the 112-row save.
  • Every row object retains sourceIndex. The Drop button uses that original index, not the row's grouped position.
  • The same renderer covers the player, read-only previews, and companion sheets. Only live sheets get Drop buttons, as today.
  • After a drop, the sheet and side panel rebuild from state, so empty categories disappear and remaining rows keep correct indexes.

6.4 Empty inventory

If no rows exist, show the existing single “Empty” message. Do not render seven empty headings. If all rows are unclassified, show one Unclassified section rather than an empty-category scaffold.

7. Item-bible authoring and coverage workflow

7.1 Entry form

Retain the primary category dropdown. Add a checkbox row for all seven inventory categories in the registry order, seeded from the primary category. Selecting a primary category automatically selects its inventory checkbox; the user may add other checkboxes but may not remove the primary one.

Add an alias list editor with one normalized alias per row. Display collision errors before save. The list view should show the primary category plus a concise “files under” summary.

7.2 Classification-only entries

Replace the current hard rejection of effect:"N/A" for weapon/armor/quest/consumable/tool entries with a visible warning. The definition remains useful for organization and tooltip metadata, but the existing prompt builder will not inject it until mechanics are filled.

7.3 Campaign coverage audit

Add a read-only audit path—either a focused dev/item-bible-coverage.js tool or an “Audit .tnd” control in the item-bible editor—that reports:

  • total rows and unique normalized names;
  • direct key matches, explicit alias matches, invalid definitions, alias collisions, and misses;
  • chosen display section and all applicable categories;
  • misses grouped by character, with the exact raw inventory string;
  • coverage percentage without modifying the save or bible.

The t1593 save should become a regression corpus for this audit. The initial curation pass should classify each of its 156 rows or explicitly record why an item remains Unclassified before the grouped UI is enabled for normal play.

7.4 Player-confirmed emergent definitions

Do not expand the read-only [ITEM_DEF:] grammar merely for display. Its scalar category seeds the new array. In showItemDefConfirmModal(), present the same seven checkboxes so the player can mark a proposed potion as both Consumable and Quest before acceptance. Acceptance stores the validated array with the campaign overlay entry.

Legacy accepted entries without the field still work through scalar fallback. Closing the modal continues to leave the proposal pending.

9. Verification plan

9.1 Core logic tests

  1. Exact user examples: Weapon + Quest → Weapons; Consumable + Quest → Quest.
  2. Full precedence: an entry carrying all seven categories resolves to Weapons; adjacent pairs choose the earlier registry id.
  3. Legacy compatibility: an old entry with only category:"tool" resolves to Tools.
  4. Unknown containment: missing definition, invalid category, empty array, and alias ambiguity all resolve to Unclassified—not Mundane and not disappearance.
  5. Exactly once: concatenate all group rows and prove the same length, raw values, and source indexes as the input.
  6. Stable relative order: rows retain original order inside each selected section.
  7. Original-index drop: after visual grouping, dropping a row removes the exact source array element.
  8. Normalization: counts, dash provenance, and parentheses still resolve. Explicit aliases cover approved comma/prose variants without fuzzy matching.
  9. Collision refusal: duplicate aliases, alias-to-key collisions, and conflicting overlay aliases fail loudly.
  10. Editor round-trip: open/serialize/reopen preserves canonical field order, sorted category arrays, aliases, and every untouched mechanical value.
  11. Classification-only: effect:"N/A" groups correctly and remains absent from item-canon injection.
  12. Overlay compatibility: legacy accepted [ITEM_DEF:] entries derive one inventory category; new acceptance persists multiple selected categories.

9.2 UI integration tests

  • All seven categories plus Unclassified, with some categories empty.
  • Player sheet, companion sheet, read-only preview, and side panel.
  • Multiplayer spotlight switch: the side panel follows activePlayer() and re-groups the new inventory.
  • Item hover and long-press tooltip, stacked quantity display, category collapse, outer panel collapse, and gold placement.
  • Drop the last item in a category and confirm the now-empty heading disappears.
  • HTML escaping for apostrophes, quotes, ampersands, and GM-authored descriptions remains intact.

9.3 Visual ground truth

Use the t1593 save to capture the side panel and Ammut's full sheet at desktop and narrow/mobile widths. Verify with the rendered result, not only element measurements:

  • headings remain distinguishable while item text stays dominant;
  • long names ellipsize in the side panel without hiding headings or collapse controls;
  • the seven-category structure does not become more visually noisy than the flat list;
  • collapsed side-panel sections materially reduce scrolling;
  • the sheet's Drop button remains aligned with the correct row;
  • Unclassified is visible but not styled like a catastrophic error.

10. Acceptance criteria

  1. Both UI surfaces use the same grouping function and fixed priority registry.
  2. Weapons, Armor, Quest, Consumables, Tools, Treasure, and Mundane appear in that order when non-empty.
  3. Multi-category items render exactly once in the highest-priority applicable section.
  4. No name-fragment heuristic assigns a canonical category.
  5. Every inventory row remains visible. Unknown/invalid items appear under Unclassified.
  6. Stored inventory arrays, strings, order, quantities, exports, sync, and tag mutation behavior are unchanged.
  7. Drop actions still target the correct original row after visual grouping.
  8. The item-bible editor can author and validate primary category, inventory categories, aliases, and classification-only entries.
  9. Old saves and old campaign overlay definitions require no migration to render correctly.
  10. The t1593 audit has no unexplained misses or alias collisions before the feature is enabled for that campaign.
  11. All headless tests are green and both large-inventory surfaces pass screenshot review.

12. Quick sanity check — is this a good idea?

Yes—with two conditions, this is a good idea. The requested order matches the bible's existing seven-value taxonomy, the precedence rule is deterministic, and one shared grouping layer will make both inventory surfaces much easier to scan without changing campaign state.

The first condition is that classification must be allowed to mature independently of mechanical canon. Otherwise a simple organizational pass would force premature item rules. The second is that missing classifications must stay visibly Unclassified; with the current bible, pretending unknown means Mundane would make the interface tidy but untrustworthy.

The reservation is scale: grouping improves finding an item, but it does not reduce Ammut's 112 rows. Collapsible side-panel categories are therefore worth including. If the panel still feels painful after the grouped version is tested, the next improvement should be search/filter or a compact “show category” control—not more categories or automatic guessing.

Bottom line: proceed, but implement in the order schema and coverage → shared classifier → both renderers. Enabling seven headings against today's 84% miss rate would be premature; enabling them after the bible can classify without inventing mechanics should be a clear usability win.
