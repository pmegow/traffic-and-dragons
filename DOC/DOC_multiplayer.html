Vision

Everyone in the car is a character in the same story. The active player holds the phone, reads the scene, picks their action, and passes it to the next player. When everyone has moved, the GM resolves the whole round at once and narrates what happens. The outgoing player rotates into the party bar; the incoming player rises into the hero slot (the two-screenshot mock: Ammut's turn → Morwen's turn).

Alternatively, in Car Mode, everything is voice-activated. The current player's portrait is displayed in the center of the screen. When the player is ready with their action, the >> button is pressed on the car stereo (likely the steering wheel) or interface, and the player speaks their action.

Ephemeral — this is the current picture, not a commitment. Edit freely, then press 💾 Save changes (saves in this browser); tell me to absorb an edit to make it canonical.

First-pass scope

Hot-seat on one device. No networking, no per-device sync, no split-party. One phone passed around a car. This removes the entire multiplayer server problem from the first pass — it's a local turn manager plus a display/POV pointer, nothing more.

Networked co-op and per-player devices are explicitly later passes (Q7). Split-party (Q6) is different — it's a first-pass assumption, not a later feature: this flow holds only while the party stays together. Decide it early.

Turn flow

  1. Round starts. Pointer = first PC in party order. Hero slot shows them.
  2. Their 3 suggestions generate from their POV; input is bound to them.
  3. They submit an action → it's queued, not sent. Pointer advances to the next PC; hero slot + suggestions + input follow.
  4. Repeat until every active PC has queued an action.
  5. The queue is assembled into one labeled block and sent to the GM in a single callGM.
  6. GM resolves the whole round, narrates once. Round resets to the first PC.

An all-NPC round (no active PCs) skips straight to step 5 after the D2 confirm — the GM plays the whole party.

The activePlayer() migration

The core engineering task. Today the code reads worldState.character everywhere for both display ("show the hero's HP") and state writes ("apply [HP:-3]"). Multiplayer needs the display to follow the pointer while writes still land on the true owner. The accessor isolates that split.

The invariant that keeps it drift-neutral

With exactly one PC, activePlayer() must resolve to worldState.character — byte-identical behavior for every existing save. That's the safety anchor and the first engine test: single-PC campaigns notice nothing.

Process

  1. Add the pointer + accessor. A pointer on worldState (name or party index) and activePlayer() returning the pointed-at party member's sheet, defaulting to worldState.character when unset or single-PC.
  2. Classify the read sites. ~130 worldState.character refs in engine/UI code (ui.js ~43, game.js ~32, tag_table.js ~30, others). Split into two buckets: display/POV reads vs state writes.
  3. Migrate the display/POV subset only (~20–30 sites): HUD, party bar, character-sheet render, input association, suggestion-call context. These point at activePlayer().
  4. Leave every state write on the true owner. Tag application (HP/gold/inventory/conditions), level-up, save/load, migration — untouched this pass. A write following the display pointer would corrupt the wrong sheet.
  5. Guard it. Engine test for the single-PC byte-identity invariant; a grep-audit checklist so no write site is migrated by accident.

Estimate: an afternoon for the accessor + subset migration, because it's a curated ~25 sites, not all 130.

Core model: threads, not cameras

The primary thread is worldState.world.location — unchanged, and ALWAYS the hero's location. A party member "splits off" by gaining a location of their own; everyone else rides the primary thread. Schema: charSheet.splitLoc = null | {location, sublocation} (absent/null = with the party — every legacy save and every unsplit game is byte-identical, the P-series anchor). The HERO cannot split: the hero IS the primary thread (splitting the hero = the party bar's other thread is the split one — same fiction, one representation; avoids two "who is world.location" answers).

Effective location = splitLoc || world.location, via one helper (pcEffectiveLoc(sheetOrChar)) consumed by HUD, party chips, geo block, and suggestions — one derivation, no scattered conditionals.

Writes

  1. Bare [LOCATION:name] moves the PRIMARY thread only — the hero + everyone with splitLoc null. Split members are untouched. This is D8's bare-tag rule applied to geography: bare = the hero's context, always. (Fork F2 below.)
  2. Named split tag — ONE new TAG_TABLE entry (parse+strip+docs land together): [PARTY_SPLIT:Name|Location] sets splitLoc on that party member (PC or companion — both can split); [PARTY_SPLIT:Name|rejoin] clears it (they walk back into the primary thread). Name resolves via resolveNpcName; unknown name = loud no-op. The GM emits it when the fiction splits ("Morwen heads to the docks alone"); the doc line goes in the companion-tags section of STATE TAGS (stable half — bundled hash re-baseline, the #46-style batch).
  3. Sub-locations: [SUBLOCATION:] stays primary-thread. A split member's sublocation rides splitLoc.sublocation via [PARTY_SPLIT:Name|Location|Sub]'s optional third arg. Kept coarse on purpose — split threads are a temporary state, not a second full campaign.

Reads — geography, prompt, UI

  1. GEOGRAPHY block: primary thread renders exactly as today (byte-identical when no split exists — engine test). When splits exist, append a compact SPLIT THREADS section: per split location — who is there, the canonical [LOCATION_DESC:] if known, known sub-locations, connections. The GM narrates ALL threads in one D5 round, so it needs all occupied geographies every turn (not just the active PC's — "camera follows active" is a UI statement, not a prompt statement).
  2. Round rules addition (P4 block): one line — "party members listed under SPLIT THREADS are elsewhere: they cannot perceive, assist, or be assisted by the primary thread this round; give each thread its own beat."
  3. UI: HUD hud-loc shows the ACTIVE PC's effective location (camera follows the spotlight). Party cards + party panel rows get a dim "· Location" chip when a member's effective location differs from the active PC's. Suggestions (D4 POV line) name the sub-turn PC's effective location so options stay scene-local.

Map layer + NPC last-seen

Nodes/edges/visits/lastArrivalFrom stay PRIMARY-thread instruments (they exist for the hero's camera). A [PARTY_SPLIT:] move: files the destination node if unknown (first-visit stamped), records an edge from the member's previous effective location, stamps the member's lastSeenAt — but never touches lastArrivalFrom or primary visits. Rejoin stamps lastSeenAt back to the primary node. Cheap, additive, no rework of the graph.

Combat under splits — v1 keeps ONE tracker

worldState.combat remains global and belongs to the PRIMARY thread. Bare [LOCATION:] keeps clearing it (unchanged semantics); a [PARTY_SPLIT:] move never clears it (the primary fight continues without the departing member). A fight on a SPLIT thread is narrative-only in v1 — no tracker; the GM tracks it in prose exactly like any NPC-vs-NPC scuffle. If [COMBAT_START:] arrives in a response whose beats are split-thread — undetectable mechanically — the tracker binds to the primary thread anyway; accepted v1 limitation, documented. Per-thread combat instances are the v2 escalation IF real play demands them (fork F3).

Invariants + test plan (pre-review checklist)

  1. No splits ⇒ prompt (both halves), geo block, map writes, combat-clear all BYTE-IDENTICAL to v1.358 — the anchor test, written first (red on any leak).
  2. [PARTY_SPLIT:] round-trips: split → effective-loc changes, geo gains the thread, chips render; rejoin → all of it byte-reverts.
  3. Bare [LOCATION:] with a split active: primary thread + null-riders move, split member does not; combat clears; lastArrivalFrom updates.
  4. Death/demote/part-ways of a split member: splitLoc cleared (they stop being a thread), loud.
  5. Corpus replay (dev/diff-replay.js) byte-identical — no legacy transcript contains the tag, so end states must not move.
