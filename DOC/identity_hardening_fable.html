Identity Hardening

Implementation proposal · filed 2026-08-09 · Fable-tier (drift surface: applyMuts write paths, memory tiers, prompt injection, naming machinery) · absorbs TODO #152, #153, #155 into TODO #156 · design direction ruled by the user 2026-08-09: one standardized identity scheme, uniform across entity types — the fewer object types and actions, the better

1. The problem

The engine has no concept of identity. It has names.

Every canonical store in Traffic and Dragons is a dictionary whose primary key is a string the model produced while writing fiction: memory.npcs["Savah"], memory.map.nodes["Varisia - North Road"], questLog entries matched by title, factions by name, relationships by entity string, spell and item canon by normalized base name. The GM narrates; the engine promotes fragments of that narration to primary keys; every later read and write resolves through string equality. A campaign's canon is, structurally, a set of databases whose keys are improvised prose.

String-equality-as-identity fails in exactly two directions, and at campaign scale both are inevitable:

FailureMechanismDamage
Drift Many names accrete around one thing The model re-describes a known entity in fresh words — an honorific dropped, a region suffix added, a landmark renamed by its function — and the upsert mints a new record instead of finding the old one The entity's canon fragments: facts, visits, relationships and history split across records; recall serves a partial file; the roster and map overcount
Collision One name is reused for a new thing The model reaches for a familiar name when inventing — context gravity makes an established name the highest-probability token for "a shopkeeper," "the road north" — and the upsert finds the old record and writes into it Two entities' canon fuses into one file: the record becomes internally contradictory, and there is no clean way to split it after the fact

Both failures are silent — no error fires, because nothing is wrong at the string level. Both are cumulative — each summarize cycle files more facts under the wrong key. And both are self-reinforcing, which is the truly dangerous property: the system prompt is assembled from the keyed stores, so once a record fragments or fuses, the model is fed its own mistake as canon every turn. A fused record teaches the model that the armorer sells rings; a fragmented one hides the canonical name that would have anchored the next mention.

1.2 The engine already knows — five partial guards, grown independently

This is the strongest evidence that identity is one problem and not five: five stores have each sprouted a hand-rolled partial defense, each covering one direction in one store, none sharing code:

  1. NPCs: the #128 variant scan (drift), resolveNpcName + alias table, GM-confirmed [NPC_MERGE:]. Nothing for collision.
  2. Spells/abilities: capBaseName normalization (drift) + write-once [SPELL_DEF:] refusal (collision). The best-hardened store — and the proof the two-sided scheme works.
  3. Items (#81): itemBaseName strips counts/provenance (drift). Collision resolved by design ruling — TYPE vs INSTANCE: eleven iron keys correctly collapse to one type.
  4. futureEvents (#29): the feTokens near-duplicate dedupe — a fuzzy identity detector for event text.
  5. Quests: an archived-title re-creation block (one narrow collision guard). Nothing for title drift; [QUEST_STEP:] matches objectives by substring, so re-worded text silently orphans.

Factions have nothing at all — and [NPC_FACTION:] auto-registers unknown faction names, so a typo mints an organization. The standing audit rule ("second instance of a failure class → enumerate the class, don't ship a third point fix") tripped at instance five.

1.3 Why not stable IDs?

The textbook fix — opaque entity IDs with names as display attributes — is parked in SERVER_ARCHITECTURE.md as a design topic, and should stay parked. The GM speaks in names; tags arrive name-keyed no matter what the storage schema does, so IDs merely relocate the resolution problem to the tag boundary while forcing a total-store migration. The alias table is the pragmatic stable ID: one canonical key with many attached names. This proposal extends that idea to every store instead of rebuilding the schema.

2. The design — one identity scheme, per-domain adapters

User direction (2026-08-09): "the fewer object types and actions we have the better. If a standardized identity scheme is possible where locations, spells, items, whatever are dealt with more or less identically (like objects in OOP), all the better."

The house pattern already exists three times over: PROVIDERS (LLM adapters), BIBLE_TYPES (editor formats), TAG_TABLE (tag handlers). One table, uniform interface, dispatch through it, adding a variant = adding an entry. Identity gets the same treatment.

2.1 The registry: IDENTITY_DOMAINS

// identity.js (new engine file) — ONE table, one uniform adapter shape.
var IDENTITY_DOMAINS = {
  npc: {
    keys()                    — all canonical keys in the store
    aliases(key)              — registered alternate names
    tokens(key)               — distinctive-token set (npcCoreTokens generalized)
    resolve(name)             — name → canonical key (today's resolveNpcName)
    context(key)              — the disambiguation signal for collision checks
                                (npc: lastSeenAt; location: parent + node kind;
                                 quest: status; faction: member overlap)
    merge(canonical, dup)     — the ONLY genuinely store-specific code (see 2.4)
    registerAlias(canon, alias)
    namingRules               — domain lines for the shared prompt clause (2.6)
  },
  location: { ... }, quest: { ... }, faction: { ... },
  capability: { ... },  // already conforming — capBaseName/lookup wrap into the interface
  item: { ... }         // already conforming — itemBaseName/lookup, merge = N/A by TYPE ruling
};

Everything above the adapters is shared machinery, written once:

2.2 One resolver

resolveEntity(domain, name) — alias-aware canonicalization at every tag parse site. resolveNpcName becomes the npc adapter's resolve; tag_table call sites go through the shared entry point. Behavior for NPCs must be byte-identical (parity-tested) — this step is refactor, not change.

2.3 One detector, both directions

The #128 variant scan generalized, running over any domain via its adapter:

  • Drift scan: token-subset/overlap between keys ("Sandpoint, Varisia" ⊂ "Sandpoint" + suffix; "Residential Quarter, Sandpoint" ↔ "Sandpoint Residential Quarter"), plus the location-specific shadowing check (world node X coexisting with Parent|X).
  • Collision scan: at upsert time, an incoming name that resolves to an existing key whose context() disagrees with the scene (an NPC last seen in another city; a location whose parent differs) is a suspect — not an error, because entities legitimately travel and titles legitimately recur.

Every detection produces the same output: a GM-decides engine note, one-shot, through the established nudge channel. Nothing ever auto-merges and nothing ever auto-blocks — every prior ruling in this project (merge confirmations #57/#128, dead-status refusal B3, item-canon proposals #81) converges on engine detects, GM or player decides, and identity is the least reversible surface of all.

2.4 One action pair

Fewer actions, per the ruling — TWO generalized tags replace per-store families:

[ALIAS:domain|canonical|alias]     e.g. [ALIAS:location|Sandpoint|Sandpoint, Varisia]
[MERGE:domain|canonical|duplicate] e.g. [MERGE:npc|Savah|Savah (apothecary)]
  • Legacy [NPC_ALIAS:]/[NPC_MERGE:] remain valid — thin tag_table entries routing into the same handlers (the doc/strip registries keep them; the model has years of reinforcement on those names, and removing working vocabulary buys nothing).
  • merge() executors are the one place domain differences are real, and they are contained in the adapter:
    • npc: today's NPC_MERGE (events/knowledge/aliases fold, relationship cleanup) — moves, unchanged.
    • location: the hard one — re-key the duplicate's sublocation subtree (child keys embed parent names), merge node records (visits sum, canonical description wins, stateNotes/items concat under caps), re-point edges[], every memory.npcs[*].lastSeenAt, lastArrivalFrom, and any splitLoc.
    • quest: re-home objectives onto the canonical title, union-dedupe by objective text, archive the duplicate shell.
    • faction: fold member rosters and faction edges.
    • capability/item: merge = null — write-once overlay (spells) and the TYPE ruling (items) make merge meaningless; the adapters exist so the resolver and prompt clause cover them, not to add actions.
  • Reversibility is non-negotiable: every merge archives the complete pre-merge records to memory.archive.identityMerges (the P12 discipline) with a loud muts receipt. A wrong merge must be reconstructable by hand even if un-merge tooling never ships.

2.5 One prevention seam

The Savah collision entered through a suggestion-shaped gap: getNameSuggestions offers fresh names but nothing forbids reusing on-file ones, and the pool itself contains on-file names (it currently serves "Frizwick Coldwater" while Frizwick is in the party). Fix at the source: suggestion generation filters any candidate whose tokens collide with an on-file entity in any domain — one call into the registry.

2.6 One prompt clause

A single NAMING block (stable half — campaign-constant, cache-safe) stating the rule with the mechanism, because the model currently has no idea the stakes exist:

"The engine files everything by name: the same name IS the same entity, permanently. Never give a new character, place, or organization the name of one already on file (KNOWN NPCs, GEOGRAPHY). Name roads and passes by their endpoints ("North Road (Magnimar→Sandpoint)"), never bare. A place inside a known settlement is [SUBLOCATION:], never a new [LOCATION:] with the parent baked into the name."

Domain lines assemble from each adapter's namingRules — adding a domain extends the clause without editing prose elsewhere. Frozen doc-hash re-baseline required (deliberate, documented — the established discipline).

4. Phasing (each phase: critical review → failing tests first → sabotage-proven → live spot-check)

  1. Phase A — the spine + npc domain. identity.js registry, shared resolver/detector/nudge, generalized [ALIAS:]/[MERGE:] (legacy tags rerouted), #128 ported with byte-parity tests, npc collision scan (the Savah class), suggestion-pool filter. Risk contained: NPC behavior must be provably unchanged except the new collision nudge.
  2. Phase B — location domain. The subtree-re-keying merge executor (the hardest single function in this proposal — test battery over real t1593 fragments), drift + shadow scan, road naming rules, map_viewer gains an honest "suspected duplicates" overlay (read-only, dotted hulls — diagnosis surfaced, never display-folded).
  3. Phase C — quest + faction domains. Title-drift scan for quests, objective re-homing merge; faction dedupe + auto-registration tightening.

5. Constraints and non-goals

  • Drift-surface policy applies in full: Fable-only, review-before-code per phase, engine tests + stable-half byte-identity + prompt/mutation diffs against real transcripts.
  • ES5, no deps, tag_table discipline (parse+strip+doc land together; strip/doc frozen hashes re-baselined deliberately with documented deltas).
  • Never auto-merge, never auto-block, never silent — detection nudges, humans decide, receipts always.
  • Non-goal: stable opaque IDs (§1.3). Non-goal: display-side grouping that hides fragmentation (the map's honesty is load-bearing). Non-goal: retiring legacy NPC tags (working vocabulary stays).

6. Open questions for the user

Repair surface: when merges ship, is GM-confirmed-nudge repair enough for the Sandpoint cloud (~8 merges, one per nudge, spread over play), or do you want a one-time guided cleanup pass (a dev-mode "review suspected duplicates now" flow that walks the queue)?
