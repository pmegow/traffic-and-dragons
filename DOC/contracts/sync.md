## 3. State management (in `state.js`)

Three live objects, all persisted to `localStorage` via the `store` wrapper:

| Object | Storage key | Contents |
|---|---|---|
| `worldState` | `tnd_core_v10` | `character`, `world` (location/region/time/weather/threat), `npcs[]`, `questLog[]`, `eventHistory[]`, `combat`, `turn`, W2 `sceneRefs` / `canonTxns` / `identityConflicts` |
| `sessionLog` | `tnd_sess_v10` | Current-session messages sent to the API (`[{role, content}]`); cleared on summarization |
| `memory` | `tnd_mem_v10` | Long-term narrative memory: `npcs{}`, `locations{}`, `quests{}`, `lore[]`, `keyDecisions[]`, `futureEvents[]`, `chapters[]` |

`store` wraps `localStorage` with an in-memory fallback `_m`. Storage key constants (`WSK`, `SLK`, `MEM_KEY`, `AKK`, `RLK`) are defined in `state.js`.

**Transcript compression:** the append-only `worldState.transcript` is the dominant part of a mature save (it caused localStorage quota death on mobile; [history](DOC/CLAUDE_HISTORY.md#3-transcript-compression--the-t308-evidence-v1227)). `saveCore` writes via **`serializeWorldState()`**, which LZ-compresses ONLY the transcript inline (`transcript` → `{__lz:"…"}`); `loadState` reads via **`parseWorldState()`**, tolerant of plain-array transcripts (server blob, `.tnd` import, legacy save). **In-memory `worldState.transcript` is ALWAYS the plain array**; only the localStorage boundary carries the compressed form. Degrades safely to plain JSON if `LZ` is absent. Round-trip engine-tested against real save data — a compressor bug here would CAUSE data loss.

Campaign list metadata stored in `tnd_camps_v1` — array of lightweight campaign entries used by the campaign picker.

**Archive-key registry (JP0-5, v1.720):** `memory.archive` categories live in ONE list — **`MEMORY_ARCHIVE_KEYS`** (state.js) — with three derived helpers: `blankArchive()` (birth shape), `archiveHeal(arc)` (fill-only lazy init/heal, never drops or reshapes) and `archiveRebuild(src)` (untrusted-blob rebuild for the `.tnd` import). All four consumers derive from it: `blankMemory`, `healMemory`, `memArchive` (memory.js) and `importSave` (ui-files.js) — the hand-copied allowlists they used to carry had drifted apart and the import one destroyed a category on every round-trip FOUR times (attitudeSpec, eras, the #144A trio, `npcDeathCorrections`+`relDowngrades`). **The registry is not what closes the class — `archiveRebuild` carrying UNKNOWN categories through VERBATIM is**: a future category, or a dev repair tool's own (`retconRepairs`, `repairBundles`), round-trips with zero edits. Registering a category buys only the blank-shape default and an array type-guard (junk never becomes archive canon). The #144A ARCHIVE CARRY CONTRACT (run-tests.js) now derives from the registry and bans any `mm.archive.<key>` hand-enumeration in ui-files.js — the duplicated allowlist inside that contract is why each loss shipped green.

**The camp holder is CAMPAIGN-SCOPED, and a camp is gated before it is held (audit D1/D9, 2026-09-18).** `_checkpointMem` (state.js) was a module global scoped to nothing: a mid-session campaign switch left campaign A's camp in it, and dying in campaign B restored A's world re-stamped with B's `campId` — `saveAll()` then wrote A's state into B's keys and POSTed it at B's higher turn, so the CAS guard passed it. The snapshot has carried `campId` and `v` since #300 and nothing read either. Now: **`checkpointClear()` runs inside `setActiveCampId(id)` whenever the id actually changes** — the one funnel every path goes through (switch, new campaign, import, "play as", the wizard, the server adopt), so the clear rides the identity change instead of N call sites; `switchToCampaign` and `importSave` then re-run `restoreCheckpointHolder()` for the newly active campaign. **One pure gate, `checkpointAcceptable(snap)`, serves both consumers**: `checkpointHold` (the single door every transported snapshot comes through, IndexedDB or the server slot) and `checkpointRestore`. It refuses a snapshot whose `campId` is present and differs from the live campaign, and one whose `v` exceeds `CHECKPOINT_VER` (a missing `v` reads as 1, so legacy camps still load). Both refusals are `{ok:false,reason}` + `console.warn`, and `deathSceneChoose("back")` toasts the reason.

**A refused restore changes NOTHING (audit D2).** `checkpointRestore` used to degrade in place — `catch(e){sessionLog=[]}`, `catch(e){memory=blankMemory()}`, an empty catch around `healMemory` — and the caller's `saveAll()` one line later persisted the blank AND synced it, so an unreadable camp silently destroyed the campaign's long-term memory. This is the JP0-4 class at a second boundary. Now every part (`ws`, `sl`, `mem`) is parsed and type-checked **before any live object is touched**, the heal (the last thing that can throw) rolls the globals back, and the dead-branch `db` marking runs only once the restore can no longer refuse. Each refusal names the failing store on the console and in `reason`; the caller shows it, does not `saveAll`, and **leaves the death scene standing** so the player can still walk onward.

**Corrupt-store rescue (JP0-4, v1.719):** `loadState` parses each side key in its own try/catch (E73 — a corrupt session/memory key must NEVER discard a good worldState), and each catch now routes through **`rescueCorruptStore(tier,raw,err)`** before degrading: the unreadable bytes are preserved VERBATIM under `STORE_RESCUE_K + tier + "_" + campId` (one slot per store per campaign; a newer corruption OVERWRITES — the opposite of UA3, where the rescue is *prepended* to survivors so the oldest blob holds the longest record, whereas these stores are replaced wholesale), the degrade shouts on both channels naming the tier ("session log" / "long-term memory"), and only then does the store fall back to `[]`/`blankMemory()` so the campaign still loads. **No recovery UI ships in this pass by design** — nothing in the app deletes a rescue key (pinned by the JP0-4 CORRUPT-STORE RESCUE CONTRACT in run-tests.js), so the preserved bytes stay the only copy until a recovery flow is designed.

## 16. Campaign management

`showCampaignPicker()` reads `tnd_camps_v1` from localStorage. `saveAll()` calls `storageAdapter.syncToServer()` on every save — **debounced**: schedules a trailing 1.5s timer so a turn's multiple saveAll bursts coalesce into ONE `POST /api/state` built from the latest state. `storageAdapter.syncNow()` flushes immediately; wired to `beforeunload` and `visibilitychange(hidden)`. The payload no longer carries the story DOM (`narrativeHtml` is sent as `""`) — replay rebuilds from `worldState.transcript`.

**The boot push's turn probe (#377, v1.885, Fable adjudication 2026-09-10).** The dirty-flush boot push is the one path that POSTs before any GET; `load()` now probes the campaign list's turn first (`getServerCampaignTurn`, metadata only) and seeds `_lastAckTurn` when the server is not ahead, so the CAS POST carries a real base instead of drawing a 409 to heal. The probe adopts nothing and never touches the dirty marker; the push still precedes any `/api/state` GET; a server that is ahead leaves the base at -1 and the CAS/conflict path runs unchanged. JP0-11's "PUSHES before the reconcile GET" assertion allows exactly that one metadata GET ahead of the push and nothing else; `dev/sabotage-377-turn-probe.js` proves the ahead-server and never-adopt clauses.

**The page-hide flush is SIZE-BOUNDED (JP0-11, Fable f68 — the guarantee this line used to overstate).** The flush rides `fetch(keepalive:true)` (a plain fetch is abandoned on unload, audit E34), and the Fetch spec caps total in-flight keepalive request **bodies** at 64 KiB — over that the browser rejects the request outright, and that rejection landed in a swallowing `.catch`: no console line, no badge, no toast. It is not a mature-campaign edge case — the PC's base64 portrait rides **inline** by design (`_stripNpcPortraits` strips only NPC avatars), so a portrait-bearing character clears the cap from roughly turn 1. So: **under `FLUSH_KEEPALIVE_MAX` (56 KB, the margin under the cap, measured in BYTES via `TextEncoder` — `payload.length` is a character count and under-reports the multi-byte `{__lz}` transcript) the keepalive flush is unchanged; over it the doomed request is NOT attempted.** Instead the flush marks the campaign dirty in `tnd_sync_dirty_v1` (`{campId: turn}` through the `store` wrapper — the turn number, never the payload; the state is already saved locally; bounded at `SYNC_DIRTY_CAP`=8 campaigns) and says so in the console. The next `load()` for that campaign **pushes before `_reconcileFromServer` may adopt anything** — adopting a newer server copy over turns the server never saw is the silent cross-device loss — and the reconcile is only DEFERRED, never blocked, by a failed push. The **CAS turn guard is untouched**: a genuine two-device conflict still pauses loudly. The marker clears ONLY on a confirmed 2xx of our own payload at a turn ≥ the marked one (a 409 self-heal acks the *server's* turn, so its retry does the clearing), and a landed under-cap beacon clears it too. One toast per page load says the final turns synced. Tests: `dev/tests-jp011-flush-dirty.js` + the synchronous half in the suite; mutation proof `dev/sabotage-jp011-flush-dirty.js` (10 clauses).

After connecting to server, `syncCampaignList()` fetches the server campaign list and merges it into `tnd_camps_v1`, then the campaign picker opens automatically. **The list has ONE reader and ONE writer (audit D8):** the merge goes through `getCampMeta()`/`setCampMeta()` (state.js), never raw `localStorage` with a second copy of the key literal. The hand-rolled pair lost three things — getCampMeta's E72 corrupt-list backup (a corrupt list parsed to `[]` here, and the server-only merge then unlisted every local campaign), the `store` in-memory fallback that keeps the list alive on a quota-full device, and the `_mKeys` shadow that stops a stale disk copy being served. A failed persist is reported, not swallowed.

**The manual push is CAS-guarded (audit D4).** `campCloudPushSilent` (the picker's ☁↑, `campRemoveLocal`'s push-then-evict, and `campSaveRename` for a non-active campaign) probes **`getServerStateTurn`** — the state row the guard compares — not `getServerCampaignTurn`, whose value comes from the campaign LIST and which #377 measured as lagging. The probe alone was never enough, because another device can write between it and the POST, so the probed turn rides along as **`parts.baseTurn`** and the server's own CAS guard decides (`pushCampaignState` includes `baseTurn` only when it is a number, so the connect-time bulk upload of local-only campaigns is byte-identical to before). A **409 is announced on both channels naming the campaign** — `campSaveRename` pushes with a null callback, so the toast has to live in the push itself; a rename can no longer overwrite a newer cloud copy in silence.

**A missing memory slot is UNKNOWN, never empty (audit D5).** `store.get(campSlotKey(id,"mem"))||"{}"` pushed `memory:{}` with a real turn number, the adopt-side turn gate took it, and `saveAll()` persisted the wipe — the D3 half-slot becoming cross-device canon loss. The push now **refuses** a missing or unparseable memory (or session) slot with a console line and a toast. The download half had the same shape (`JSON.stringify(data.memory||{})` in `campLoad`/`campCloudPull`): `{}` is not an empty memory but a BROKEN one — `loadState` parses it as truthy and heals only the lazily-initialised fields, so `memory.npcs` stays undefined and the first reader throws. Both sites route through `_pulledMemory(data,id)` → `blankMemory()` plus a loud line.

**A campaign's sync markers die with the campaign (audit D10/D13).** `deleteCampaign` and the picker's "Remove local" (`removeCampaignLocalCopy(id,{teardown:true})`) call `forgetCampaignSyncMarkers(id)` → `storageAdapter.clearFlushDirty(id)` + `clearSyncSizeWarn(id)`. `SYNC_DIRTY_CAP` is 8 with oldest-first eviction, so a marker for a campaign that no longer exists pushed out a LIVE one and the JP0-11 boot push stopped covering a real campaign; `tnd_sync_size_warned_v1` appended a `|id|` segment per campaign and was never pruned. **The `teardown` flag is load-bearing**: `switchToCampaign` frees the incoming campaign's slot as part of the two-blob dance, and clearing its unsynced-flush marker there would drop the record of turns the server never saw for the campaign about to be played.

**Cloud rewind is confirmed, never silent (#424, v1.954, owner ask 2026-09-17).** The picker's two download paths — Load on a campaign this device holds, and ☁↓ Pull — decide through ONE pure policy, `planCloudAdopt(mode,serverTurn,localTurn,hasLocal)` (state.js): `adopt` (no local copy; the cloud is ahead; level on a pull), `keep-local` (load only: level, or the cloud turn unknown — say so, then play local), `confirm-rewind` (this device is AHEAD, or its copy is unreadable, or the cloud turn is unknown on a pull). Before #424 Load took the local slot without asking the server and ☁↓ Pull overwrote a local-ahead copy without asking the player. Load probes **`getServerStateTurn`** (turn-only — never a full blob for a comparison); Pull compares the fetched copy's own turn. A `confirm-rewind` opens `_cloudRewindModal` (modalShell, never `confirm()`): both turns, the turns that would be lost, and **Export this device's copy, then use the cloud copy** → `exportCampaignCopy(id)` (ui-files.js: the SLOT triple for a non-active campaign, the live triple for the active one, `_ensureFolderPerm` inside the click; a failed export ABORTS the rewind loudly), **Use the cloud copy anyway**, **Cancel** (a Load's cancel plays this device's copy). Every download lands through `_applyPulledCampaign`: the live keys for the active campaign (audit E3 — never switchToCampaign), the slot writer otherwise; then `storageAdapter.clearFlushDirty(id)` (the marker's turns were discarded by decision or superseded) and, when the campaign is active, **`storageAdapter.adoptServerTurn(turn)`** — the one path that LOWERS `_lastAckTurn` and clears a standing 409 pause; every other ack only raises it, and a rewind left on the old base would 409 the next save and count the discarded turns as unsynced. The boot reconcile is unchanged (adopts only a newer cloud copy; a device ahead of a dead host still wins). Pinned by the engine section "#424: cloud rewind", five source contracts in tests-audit-sync.js and `dev/sabotage-424-cloud-rewind.js`.

**Campaign switch under quota (#337, v1.821).** `switchToCampaign(id)` is sequenced for a TWO-blob peak: read the target slot into memory → free it (`removeCampaignLocalCopy`) → `snapshotActiveCamp(true)` (quiet — the switch owns the toast) → `writeLiveKeys` → `loadState`. The old order (snapshot, then unguarded live write) needed three blobs at once and let a `QuotaExceededError` escape as a half-switched store with no toast (owner report 2026-09-05). Every failure path — snapshot, live write, corrupt target (E35) — restores the exact start layout (outgoing snapshot copy removed, target slot re-written from memory, active id unmoved) and shows ONE toast naming the campaign, the KB the step needs and the KB the device holds (`storageUsedChars`). **The two guarded writers are the only way campaign transport writes storage:** `writeCampaignSlot(id,ws,sl,mem,label)` is all-or-nothing (a throw removes the partial keys AND their `_m` shadow, toasts, returns false) and `writeLiveKeys(ws,sl,mem)` restores the previous live triple on a throw (the caller toasts). The active-campaign cloud pull writes the live keys ONLY (no slot-then-dedupe double footprint). Pinned by the CAMPAIGN SLOT WRITER CONTRACT (run-tests: no raw `store.set` of a slot or live key in campLoad/campCloudPull/switchToCampaign **or snapshotActiveCamp**; free-before-snapshot order) and six engine tests against a capacity-limited localStorage fake; `dev/sabotage-337-campaign-switch.js` proves the guards. Known limit: a campaign larger than half the quota cannot be switched AWAY from (its backup needs its own size) — IndexedDB remains the escalation.

**`snapshotActiveCamp` writes through the same writer (audit D3).** Three raw `store.set(campSlotKey…)` calls survived #337 here — the contract's scan window stopped just above the function — so a quota throw mid-triple left `ws@N` beside `mem@N-k`: a slot that loads as a campaign whose world and memory disagree, and which the manual push then shipped to the cloud as canon (D5). It now calls `writeCampaignSlot(id,ws,sl,mem,label,quiet)`, and that writer gained two clauses: **`quiet`** (the caller owns the toast — snapshotActiveCamp's #395 cloud-proof branch turns a failed write into a non-failure) and **null-means-delete** (writeLiveKeys' rule: the live triple can legitimately lack a session or memory key, and leaving the previous slot's part beside a new world is the mismatched pair the writer exists to prevent).

**`snapshotActiveCamp(opts)` takes `{quiet}` / `{noSync}`** (a bare `true` is still `quiet`, the switchToCampaign contract). **`{noSync:true}` is the unload path (audit D11)**: `beforeunload` fired two POSTs of the same state — the snapshot's own debounced flush (a plain fetch, abandoned on unload by E34, which only double-counted `usage.syncPosts` and set `_syncing` on the way out) and then the keepalive beacon. The beacon is the one POST that can land; every other caller keeps the flush.

## 17. Sync modal

Direct editing of HP, max HP, gold, XP, level, sub-location, location, time, weather, inventory without going through the GM. **Level and place are NOT raw writes (audit E2, 2026-09-18):** the level goes through `syncLevelPatchPlan` → `checkLevelUp({land:true})` (a level-*down* is refused — no un-grant path exists), and the place is built as one engine-authored `[LOCATION:]`/`[SUBLOCATION:]`/`[SUBLOCATION_LEAVE]` tag by `syncLocationPatchTags` and applied through `applyMuts`, so resolution, the twin-conflict refusal, the node mint, the edge and `sublocation=null` all happen. The inventory assign is followed by `wornPrune` (audit E4).

## 22. Cloud sync (`storage-adapter.js`)

**Server:** `https://traffic-and-dragons-server.fly.dev`
**Auth:** GitHub OAuth popup → server postMessages `{type:"tnd-auth", sessionId, username}` back to opener → token stored in `tnd_server_tok_v1`.
**CORS:** Server uses `origin: function() { return "*"; }` to handle `null` origin from `file://` pages.
**Endpoints:** ~20 routes — full enumeration in [SERVER_ARCHITECTURE.md](DOC/SERVER_ARCHITECTURE.md) §1.2 (auth, state with the CAS turn guard on POST, campaigns, character/blueprint libraries, allowlisted `/api/prefs/:key` blobs, health). Auth flow is TICKET-based: the popup postMessages a one-shot ticket (or the opener polls it on file://), and the sessionId comes from the claim endpoint.
**Hygiene (#313, v1.770):** schema versioned via `PRAGMA user_version` (`MIGRATIONS` in db.js — roll forward only; a newer-stamped store refuses to boot); per-user quota (256 MB / 40 campaigns, env-tunable) refused as a 413 the client toasts verbatim; sessions slide 30 days but die 90 days after login; nightly off-Fly backup + quarterly restore drill are GitHub Actions in the server repo gated on `BACKUP_TOKEN`.
**Campaign ownership (#423, v1.953 / server 1.5.2, 2026-09-18 — research doc §14 finding S1):** campaign ids are neither opaque nor secret (`camp_<timestamp>_<4 digits>`, carried by every `.tnd` export), and `POST /api/state` used to upsert on `id` alone — any signed-in account posting a known id replaced the owner's row, and the everyday trigger was a friend importing an exported save. The server now decides ownership FIRST from one id-only lookup (**403 + `reason:"foreign_campaign"`, never `{ok:true}`** — the client acks any 2xx and would clear its JP0-11 unsynced marker on a zero-row write) and the upsert carries `WHERE campaigns.user_id = excluded.user_id` as the atomic backstop (`changes()===0` → 403); the CAS guard and the quota preflight read that same row, so their semantics are unchanged. Client side, **`importSaveData` (state.js) is the engine half of importSave** and decides the id through `resolveImportedCampaignId` — the file's id is reused only when this device already owns it (campaign list or local slot), otherwise RE-MINTED with a toast; `_syncNow` re-homes ONCE on a `foreign_campaign` 403 through **`rehomeCampaign`** (the one function that moves the slot, the list row minus `onServer`, the unsynced marker, the #365 stamp and the held checkpoint) and retries; any other 403 stays an ordinary sync failure. Pinned by the IMPORT OWNERSHIP CONTRACT (run-tests), `dev/tests-423-import-ownership.js` (a contract stub in CI; `TND_SERVER_DIR=…` runs the same scenarios against the real server) and, server-side, `test-state-ownership.mjs` + `sabotage-state-ownership.mjs`.
**Deploy:** `cd C:\Users\hannu\Projects\traffic-and-dragons-server && flyctl deploy --ha=false` — the server repo lives OUTSIDE the OneDrive-synced tree (DOC/todos_completed/PROJECT_ONE_DRIVE_EXODUS.html Phase 4); it is NOT a sibling of the game repo.
**TTS app (#90, M1):** `https://tnd-tts.fly.dev` — a SECOND Fly app in the same server repo (`tts/` subdir; deploy `cd tts && flyctl deploy --ha=false`). `POST /api/tts` {text, voiceId, rate} → audio/wav (warm piper daemons, LRU 3, 10min idle kill; voices HF→3GB volume on first use); auth = the game server's session token proxy-validated via `/auth/me` (10min memo); `/health` unauthenticated (the client's prewarm probe — wakes the auto-stopped machine). ## 23. Reload behavior

On `init()`, if a saved game is found, `rebuildNarrativeFromTranscript()` (ui-boot.js) repaints the last 20 `worldState.transcript` entries into `#story-narrative` (with an "earlier entries omitted" note when trimmed); the last response's suggested action buttons (`worldState.lastActions`) are live and clickable. The same rebuild serves campaign loads and the server reconcile (`clearFirst=true` there). Fallbacks for pre-transcript saves: last sessionLog exchange, else a "Previously:" chapter recap, else legacy `narrativeHtml` from old server blobs. Dice blocks and system messages are not replayed (the transcript stores story prose only, by design).

## 24. Character library (`storage-adapter.js` + server)

Server-side character storage separate from campaigns. Characters are portable snapshots — exporting Ammut at Lv3 stores a Lv3 version; campaigns have no dependency on this store.

**Server table:** `characters (user_id, slug, name, char_data, level, cls, ancestry, updated_at)` — composite PK `(user_id, slug)`. One slot per character name per user.

**Server endpoints:**
- `GET /api/characters` — list all characters for user (includes full char_data with portrait)
- `POST /api/characters` — upsert by name slug; body: `{character}`
- `DELETE /api/characters/:slug` — remove from library

**Client methods on `storageAdapter`:** `listCharacterLibrary(cb)`, `saveCharacterToLibrary(char, cb)`, `deleteCharacterFromLibrary(slug, cb)`

**The library is UPSTREAM (#427, owner rulings 2026-09-21).** The only road into the library is the manual Export Character → Save to library (the two branches in ui-browsers.js are the only `saveCharacterToLibrary` callers in the app — pinned by `#6A the library is UPSTREAM`). No campaign, adventure or village, ever writes a sheet to the library on its own: the #6 phase-A write-backs (the hero on a campaign switch, the demoted hero at a swap, the Hall line) are deleted, because a whole-sheet upsert by name from a village copy overwrote a newer export (last writer wins). Downstream, the village pulls: residents AND the hero being played refresh wholesale from a dated library copy newer than their move-in stamp (`npc.libraryAt` / `worldState.heroLibraryAt`, carried across a swap) on every entry; older, equal or undated copies are kept; the adventure kind never refreshes. Hall lines live in `worldState.hallLines` (village state), read through `villageHallLineOf`. Village-only changes since an export are lost on the next refresh by design (village saves are disposable).

**Replace from library (#428, owner rulings 2026-09-21):** the explicit WHOLE-sheet pull, beside the identity-only Update, on both sheet hosts (hero; companions where Export/Update already show), in every campaign kind, behind a confirm (`showLibraryReplaceModal`, ui-browsers.js: a before → after table from the pure `libReplaceSummary`, the copy's save time, "the name stays, cannot be undone"). The apply is `libReplaceApply(name, libCopy, updatedAt)` (game.js), which routes to ONE adopter per host — `adoptLibraryHero(c, at)` / `adoptLibraryCompanion(npc, c, at)` — the same adopters `villageRefreshFromLibrary` uses, so the button and the auto-refresh can never disagree: a wholesale COPY, the local name kept (the identity key), relationships through the axis adapter, item canon adopted, the v10 arrays ensured (`ensureV10Arrays`, shared with `startGame`), framing kept when the copy has none, voices reassigned, the stamp (`heroLibraryAt` / `libraryAt`) taken from the entry. The #161 identity-only rule stands: progression never flows through Update; it flows only through this explicit, confirmed Replace. Pinned by `#428 replace from library` + `dev/sabotage-428-replace-from-library.js`.

**Export flow:** "Export Character" button (char sheet + companion sheets) opens `_showCharExportOptions(char)` — offers "☁ Save to library" (grayed if not connected) and "⬇ Download .char file". If saving and character already exists in library at a different level, `_showCharOverwriteConfirm` asks before overwriting.

**Import flow:** the Import Character browser's **Library** tab (`showCharacterBrowser("library")`) — lists saved characters with portrait, Import (→ `showCharImportPreview`) and × delete buttons. *(The `showCharacterLibrary()` alias was deleted with zero callers — audit E8, 2026-09-18.)*

**Update from library (#161):** "⟳ Update from library" on player + companion sheet headers pulls the library copy's IDENTITY fields into the live sheet behind a per-field old→new preview — `LIB_UPDATE_FIELDS` registry + pure `libUpdateDiff`/`libUpdateApply` (helpers.js, engine-tested; apply recomputes the diff so preview and apply can never drift). Whitelist-only; **progression and play-earned state NEVER flow**; `name` is excluded (identity KEY — renames are #156 territory). Skip rules: lib-undefined skips, explicit `""` applies (deliberate clear), null/"" portrait skips. Modal: `showLibraryUpdateModal` (ui-browsers.js); companion apply mirrors `portraitOffset` onto `wsNpc`. The pull half of the future character-editor loop.

**"Play as X" flow:** all three import paths (file, campaign browser, library) route through `_startImportedCampaign(char)` — a campaign-setup modal asking campaign name, world tone, and starting location (options cloned from the wizard's Review-step select) before resetting state and calling `startGame()`. The character is played as-is; companions are added in-game via Import Character → Add as companion (intro instruction sent via `sendAction(intro,{silent:true})` so it never renders as a player message).

**Mid-game character swap:** `_switchPlayerCharacter(name)` (NPC sheet → "Play as this character") demotes the current PC to a companion NPC and promotes the chosen companion's `charSheet` to `worldState.character`. The POV-handoff fix is two-part: (1) a forceful out-of-character control directive sent `{silent:true}`; (2) `worldState.recentSwitch` makes `buildSysPrompt` re-inject a "CONTROL RECENTLY SWITCHED" block, auto-cleared after 2 turns — the re-injection is the load-bearing part (a single handoff line can't overpower many turns of old-POV history). **Portrait atomicity:** `syncToServer` must never null `character.portrait` — the current PC's portrait rides **inline in the main state blob**, atomic with the state turn. Only sheet-less NPC `n.portrait` is stripped to the separate `/portrait` store. (Desync history: [history](DOC/CLAUDE_HISTORY.md#19-portraits--the-sync-sagas).)
