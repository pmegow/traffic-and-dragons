# The bibles — capabilities, classes, skills, items

**Read this when** you touch a *_bible file, the bible editor, item canon, pricing or the wares economy.

Split out of CLAUDE.md on 2026-09-03 (#310); the map there links here. Version stamps and history links inside are the record as written — the contract lines are current unless a newer commit says otherwise.

## Files

### capability_bible.js

Status: ✅ Active

The unified `capability_bible` (#10) — `CAPABILITY_BIBLE` holds spells AND abilities (`kind` is cosmetic, `cost`+`isMagical` are the real axes). Keyed by base name (`capBaseName()`); schema `{kind:"spell"|"ability", tier, cost, isMagical, category, range, targets, duration, effect, dice?, save?}`. **`category`** is a LIST of traditions (`arcane`/`divine`/`primal`/`necromantic`/`martial`) — the gate for a rolled enemy caster's menu; `capabilitiesByCategory(cat)` returns the matching list. **Fixed attribute set:** every entry carries all of cost/range/targets/duration/save/dice, `"N/A"` where inapplicable — the card always shows the same 6 rows and injected canon can never be queried empty. `capBibleLine()` (api.js) renders one labeled injection line. **`capabilityLookup()`** — the ONE lookup for card, viewer, and injection: emergent `worldState.capabilityBible` overlay (write-once via `[SPELL_DEF:]`) wins over the static base; an ability that is really a spell resolves to its spell canon — no dup. Anti-drift injection: `buildSpellBibleBlock()` + `buildAbilityBibleBlock()` (api.js) re-inject canon for the player's known spells/abilities every turn (volatile half). Genuinely-different domains get their own `*_bible` files. **Renames (#221, v1.763):** `node dev/rename-capability.js "Old" "New"` rewrites every data-file site atomically and appends to `CAPABILITY_RENAMES` (data.js, transitional — a Clear-for-Release row); `migrateCapabilityRenames` (state.js) rewrites saved spell/ability names on load and at the .char/library import funnels, so a rename can never leave a sheet with a name that resolves to nothing

### class_bible.js

Status: ✅ Active (#72, engine-wired)

THE single definitive source for character progression. The engine reads it via classDef()/classDefs() + classFeaturesAt()/archFeaturesAt()/classXpLevels() (helpers.js); level-ups grant NAMED class rows (2/5/7/9/11/13/15/17) and the committed archetype's rows (3/6/10/14/18+20), player and companion alike; `CLASS_XP_LEVELS` runs 1–20 (L11 gate 85000). 9 classes, 27 archetypes, 234 level slots, C2 spellTiers, C5 skillSeeds ([history](../CLAUDE_HISTORY.md#class_biblejs--bible_editorhtml--the-72-build-out)). Machine-REGENERATED by bible_editor.html's exporter — canonical form `JSON.stringify(x,null,2)` between the `>>> CLASS BIBLE DATA` markers, byte-pinned by the BIBLE EDITOR CONTRACT (run-tests.js); content hand-edits in canonical form are legal, format drift fails the build. Coverage guard: every spell NAME in it must resolve via `capabilityLookup` (a new spell and its capability entry land in the SAME commit). In the SW app shell

**Class-ladder coverage (#339, v1.822).** Every class ability, level feature and archetype feature in `class_bible.js` resolves through `capabilityLookup()` — the class bible names a feature, the capability bible is its canon (effect, cost, magical flag, tradition), and the GM's per-turn ability injection reads the capability entry. Shared feature names (`fighting style`, `extra attack`, `consecrated ground`) get ONE class-neutral entry because the bible is keyed by base name. Pinned by the "class-bible coverage" engine test; `dev/sabotage-339-class-coverage.js` proves it bites. A new class-bible feature without a capability entry fails the suite — that is the design: the Cleric's "The Blessing Holds" reached a live character with no canon behind it before this guard existed (owner report 2026-09-05).

### item_bible.js

Status: ✅ Active (#81)

Curated canon for mechanics-bearing carried items — the spell-bible pattern for gear. `ITEM_BIBLE` keyed by `itemBaseName()` (helpers.js); fixed-attribute schema `{category: weapon/armor/consumable/tool/quest/treasure/mundane, effect, uses, value}` ("N/A" where inapplicable). **TYPE vs INSTANCE is a build contract**: definitions describe the TYPE; instance state (charges, provenance, counts) stays on the inventory string — an entry carrying extra fields fails the BIBLE EDITOR CONTRACT. Reads via `itemLookup()`: emergent overlay `worldState.itemBible` wins over the base. **Emergent items are PLAYER-CONFIRMED**: `[ITEM_DEF:]` is a PROPOSAL queued on `worldState.pendingItemDefs` (cap 5, dedupe) — the confirm modal (ui-modals.js; resurfaces on boot) is the only path to canon via `itemDefAccept`/`itemDefDecline` (accept = write-once PER REAL CANON — #294B: a classification-only overlay with no base may be replaced by an accepted proposal; `itemDefOverlayReplaceable` is the one predicate both the handler and `itemDefAccept` consult). **#294B (v1.762, owner: "ALL items need a description"):** `_itemDefCandidate` asks for EVERY canon-less `[ITEM_GAINED:]` (the mundane skip-list is gone; an inline "—" description exempts itself), once per item per campaign via the `worldState.itemDefAsked` latch (stamped at delivery, `ITEM_DEF_ASKED_CAP`=60, in NOTE_LATCH_FIELDS). **#481 D8 (v1.1049):** the slot was last-wins, so two new items in one reply asked only about the second; `itemDefCandidate` is now the NEXT ask, and later items wait in `worldState.itemDefQueue` (arrival order, `ITEM_DEF_QUEUE_CAP`=8, a registered latch — a dead turn restores it; overflow is a ⚠ summary line). The note stays one ask per turn: `buildUndefinedItemNudge` skips a head the GM defined or proposed meanwhile and promotes the next still-open item (`_itemDefPromote`), dropping one that waited more than `ITEM_DEF_QUEUE_STALE_TURNS`=10 turns, since the note says "just acquired". A sixth `[ITEM_DEF:]` proposal (the queue holds five) is refused with a ⚠ summary line and does NOT consume the item's ask latch. Proof: `dev/sabotage-481-d8-item-ask-queue.js` (7 clauses). Injection: `buildItemBibleBlock()` (api.js, volatile) — one line per carried resolvable item across player + party sheets; mundane/treasure/effect-N/A never inject. Tooltip: `itemTip()` (ui-panels.js). Machine-REGENERATED by bible_editor.html (byte-pinned `>>> ITEM BIBLE DATA` markers); read-only section in bible_study.html. **#157 (v1.583): two DISPLAY fields** — `inventoryCategories` (the FIRST match in `INVENTORY_CATEGORY_REGISTRY` (helpers.js) decides which inventory section an item files under) and `aliases` (exact alternate TYPE names, normalized, collision-refused; resolution is CANONICAL inside `itemLookup` — never substring/fuzzy). `effect:"N/A"` outside mundane/treasure = a legal classification-only entry (organizes + tooltips, never injects). Both inventory surfaces render through ONE pure `groupInventory()` view model (helpers.js — unknown/invalid items stay VISIBLE under Unclassified, never guessed). Coverage audit: `dev/item-bible-coverage.js`. Spec: [DOC/Research/DOC_inventory_reorganization.html](../Research/DOC_inventory_reorganization.html)

### skills_bible.js

Status: ✅ Active (#52)

The canonical skills reference. `SKILL_LEVEL_MECHANICS` = ONE global ladder (index-aligned with `SKILL_LEVELS`): flat check bonus per level (+1 Familiar … +5 Master, stacks with the stat mod) + auto-success bands (Trained+ through Master rolling progressively less) — data-only by design, a rebalance is a 6-line edit. `SKILLS_BIBLE` = per-skill canon keyed by EXACT `SKILLS` id: `def` (coverage + boundary vs confusable neighbors) + `untrained` (`yes`/`hard`/`no`; specialist lists derived by `skillsUntrained()`). Injection (api.js): `buildSkillMechanicsDoc()` — the constant ladder doc in the STABLE half (byte-identical, cache-safe) — and `buildSkillCanonBlock()` — VOLATILE, EARNED skills only, ""-clean at zero. Viewer: `skillCardHTML` (helpers.js) + a Skills section in bible_study.html. Engine-tested: bidirectional coverage guard (new skill + bible entry land in the SAME commit, sabotage-proven), ladder shape, stable/volatile injection

## Village shops (#6 F, v1.913)

**Read this when** you touch wares, prices or the Shop button in a campaign kind with `waresPerShop`/`tradeOnlyInShops` (the village). Wares and wants live on the SHOP sub-location node, never the settlement; a shop is decided by data (`isShopNode`: the kind's `shopWords`, a `node.shop` flag; a house with an `owner` and the Hall never are); each shop holds `WARES_CAP_SHOP` with a loud eviction; a ware with a bible value is recorded AT the bible value (`pinPrices`), a re-stated ware without canon keeps its first quote; expiry stays `WARES_RESTOCK_DAYS` on the campaign clock, per shop. Coin moves only in a shop with a present keeper (the GOLD trade gate, tags.md). **#501 (v1.1095, owner 2026-10-01) — the counter's two doors.** There is a counter to open exactly when `shopOpportunity()` (helpers.js) answers: the trade gate is open AND names a shop (`villageTradeContext`: a shop node, someone to trade with). Two doors read that ONE rule: the inventory panel's "⇆ Trade with <keeper>" row, and the narration's own **Shop** button (`syncShopButton`, ui-shell.js) — one button, on the Render row of the NEWEST scene (a narrator frame with a turn), at the panel's right edge. A new scene takes it from the one before; walking out, or the keeper leaving, turns it off. It is painted from the LIVE state on every repaint (`syncUI`) and whenever a narration lands (`addMsg`), never stored with a turn, and its click goes through the one click-time gate `invLedgerOpen`. In a shop the fourth suggestion button is the ladder's (rest / use / accept / the village rung): the #496 "Shop at <shop>." rung (v1.1085) was withdrawn a day later, with its opener table, because the fourth button is written once per turn and stored, so a reload repainted the old words. The village's "Buy the X (price) from Y." and "Sell your X to Y" rungs stay retired (#496: their choices are inside the counter), the `sellRung` kind flag is gone, and a `tradeOnlyInShops` kind never shows the adventure's Buy button. **#492 (v1.1082):** the adventure's buy rung names the first live ware the hero does NOT hold (`firstWareNotHeld`, helpers.js, compared by `itemBaseName`) and steps aside when every ware is held. Pinned by the `#6 the village — phase E/F` section, `dev/tests-501-shop-button-browser.js` (a real browser), `dev/sabotage-501-shop-button.js` (14 clauses), `dev/sabotage-492-buy-button.js` and `dev/sabotage-6-village-stash.js`.

**#481 D5 — one coin parser (v1.1045; audit 2026-09-29, Fable-approved).** `parseCoin(str[, lead])` (helpers.js) is the ONLY reader of a price.
- **What it reads:** gold, silver, copper, platinum (1 gp = 10 sp = 100 cp; 1 pp = 10 gp), thousands commas, and a bundle — "1 gp per 20" / "for 20" prices ONE of twenty; "each" prices one. It returns the unit price in gold (`unitGp`). A price without a coin ("N/A", "a handful of copper") is null.
- **Who reads it:** `itemValueGp` (canon); the counter (`shopTradeCatalog` sell, buy and wanted); price pinning (`fileWare` pins to canon's OWN words — "5 sp", "1 gp per 20" — compared by the unit price); the #303 price band (its receipt quotes canon's words); the [GOLD:] and quest-reward parses (tags.md).
- **The counter multiplies by quantity:** a bundle ware's row offers up to its bundle (`per`), and the line is unit price × count (`[ITEM_GAINED:Arrows x20]`). `shopFmtGp` says a sum under a gold piece in silver or copper.
- **The purse stays whole gold:** a single sub-gold buy still rounds up to 1 gp ("the keeper never gives a thing away"); a sub-half-gold SALE is #481 D7.
- **Proof:** `dev/sabotage-481-d5-coin.js` (14 clauses).

**#481 D4 — the keeper's offer, and a want that retires (v1.1047; ruled 2026-09-29, amends #407 ruling ①).** A WANTED item sells at the keeper's STATED offer (parsed by `parseCoin`), for ONE unit (the row's max is 1), and the want retires when met (tags.md ▸ WANTED). An offer in words is no counter price: the row is off with the reason quoting the offer ("Wanted, but the offer is in words (“a fair price”) — ask <keeper>"). The offer is paid as stated even below half canon (Gazz's 40 gp for a 200 gp ring pays 40; the second ring, unwanted, 100) — the ruling as written; `max(offer, half canon)` would be a one-line change. Proof: `dev/sabotage-481-d4-want-met.js` (6 clauses; a seventh guarded the fourth button's sell rung and retired with it, #496).

**#481 D7 — the sale floor (v1.1046; ruled 2026-09-29).** `shopTradePlan` floors the LINE total (count × unit price): a sale line worth under half a gold piece would round to 0 gp while the item left the pack, so it is refused. The plan names it (`plan.under`, the reason "the keeper pays nothing for 1 Carved whistle (3 sp) — under half a gold piece; mark more of it, or keep it"), holds the WHOLE plan (a partial trade would leave the mark silently unsold), and nothing moves. Two 3 sp whistles (6 sp) sell for 1 gp. The counter shows the reason while only a refused line is marked. Proof: `dev/sabotage-481-d7-sale-floor.js` (4 clauses); browser QA `dev/qa-481-d5-d7-counter.js` (manual, CDP, no server).

## Item canon travels with the sheet (#81b, v1.916)

**Read this when** you touch a character export, the library save, or any import of a sheet (the village write-back was deleted in #427, 2026-09-21 — the library is upstream and the player's manual saves are the only roads in — see sync.md §24). A campaign's `[ITEM_DEF:]` overlays live on `worldState.itemBible` and a sheet is only item names, so an exported hero's runeforged blade arrived Unclassified (owner, 2026-09-13). `portableSheet(sheet)` (helpers.js) returns a copy with `itemDefs` — the origin campaign's definitions for the items the sheet carries — and every export goes through it (`_doExportChar`, both library-save branches). `adoptSheetItemDefs(sheet)` merges them into the destination campaign's canon, missing keys only (write-once, #81), and every import calls it (`startGame`, `importVillageResidents`, `_addImportedCompanion`). Pinned by the `#81b item canon` section and `dev/sabotage-81b-item-canon-travels.js`.
