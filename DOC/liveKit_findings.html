⚔ LiveKit — findings and verdict

Should Traffic and Dragons adopt LiveKit for realtime audio? Investigation for TODO #84.
Written 2026-07-21 · engine v1.415 · sources: five supervisor research lanes (A–E, aggregated web research) cross-checked against the repo itself (stt.js, tts.js, TODO.md, DOC/DOC_multiplayer.html) · design-only, no code written
Verdict

Do not adopt LiveKit. Close TODO #84 as investigated and declined, with one narrow re-open trigger (see §8). LiveKit is a competent, well-funded realtime-media platform that solves a problem this project does not have, at a cost model that inverts the project's economics, by way of an architecture change (server + build pipeline + a second runtime) that is larger than the entire feature it would buy.

DO NOT ADOPT Confidence: very high under current constraints · high even if a server and build pipeline are accepted

The single strongest argument against this recommendation: if networked co-op (#1 Q7 — separate devices, live sync) is ever built and it wants live player-to-player voice, LiveKit is genuinely the right tool and a solo developer should not hand-write an SFU. Declining now means re-litigating it later, possibly with sunk-cost bias toward whatever half-measure got built in the meantime. I accept that risk because Q7 is unscoped, because the multiplayer spec's own primary use case is one phone passed around a car (which needs no network at all), and because nothing about declining today forecloses adopting later — there is no partial commitment to strand.

1 · The two readings, kept separate

TLDR: under today's architecture LiveKit is not adoptable at all — this is not a close call and all five lanes agreed on it. Under a hypothetical server-plus-build architecture it becomes possible, but still loses.

Reading A — current constraints

No build step, no npm, ES5.1, static hosting on Cloudflare Pages, one small Fly.dev REST sync service, keys in localStorage, browser calls provider directly.

  • LiveKit performs no speech recognition itself. It is a media router (SFU). STT/TTS live in the Agents framework.
  • Agents requires a persistent server-side worker process (Python or Node) that registers with LiveKit and receives job assignments. There is no documented browser-only or client-only mode.
  • Access tokens are JWTs that must be signed server-side with an API secret that can never reach the browser. Even the "just connect a client" path needs a backend.
  • Therefore: zero benefits are available under this reading. Not "few" — zero. Every one of the 25 benefits returned across five lanes is tagged with-server-and-build or collapses to it.
NOT ADOPTABLE — STRUCTURAL

Reading B — server + build accepted

Hypothetical: the project takes on a bundler, npm dependencies, and an always-on media/agent backend.

  • The capabilities become real: cross-browser mic capture over WebRTC, server-side STT with swappable providers, model-based turn detection, barge-in handling, room/participant primitives.
  • But the decision is no longer "LiveKit or not." It is "accept a server-and-build architecture" first, and only then "is LiveKit the best vendor inside it" — and inside that new architecture, a direct Deepgram/AssemblyAI/Whisper integration behind your own token endpoint is cheaper per minute and skips LiveKit's agent-session fee entirely.
  • Keeping Claude as GM inside a LiveKit agent needs the Python runtime — the Anthropic plugin is Python-only; the Node/TypeScript agents SDK omits Anthropic. The project's one existing server is Node. That is a second, unrelated runtime to operate.
POSSIBLE, STILL LOSES

Why Reading A's finding carries so much weight: the five lanes were deliberately framed differently — Lane A was pitched as "drop-in replacement: capabilities" (a positive framing), Lane E as adversarial risk analysis. They still converged, independently, on the same structural fact. Lane A's own supervisor wrote that the "drop-in replacement" framing "is itself not supported by the research." When a favourably-framed lane refutes its own premise, that is the highest-quality signal in the dataset.

2 · What the repo already does that the research did not know

TLDR: I checked the codebase, and the two problems every lane offered LiveKit to solve are already solved in-repo, at zero cost, without a server — which is the finding that actually decides this.

All five lanes worked from the project summary they were given. That summary described stt.js as "a thin module over the browser Web Speech API… not Firefox, flaky on iOS." That description is out of date. Reading the file changes the analysis materially.

① The iOS Safari / Firefox dictation gap is already closed — shipped, no server, no build

stt.js lines ~281–433 contain a complete cloud fallback: when native SpeechRecognition is absent, it captures audio with getUserMedia + MediaRecorder (mp4 on Safari, webm/opus elsewhere), and POSTs the blob straight to api.openai.com/v1/audio/transcriptions with whisper-1, using the player's own OpenAI key from providerKeys. It is ~150 lines of ES5, dispatches only when native is missing so the native path stays byte-identical, and isSupported() already reports true on iOS when a key is on file.

This is precisely the "cheap point-fix alternative" Lane E proposed as the reason to reject LiveKit — and it was built and shipped before the question was asked. The single most-repeated benefit across all five lanes ("closes the Firefox/iOS Car Mode gap") is therefore not a benefit. It is a re-solve.

Honest caveats, because this is the load-bearing fact: the path is marked EXPERIMENTAL (todo_carplay rank 7); it needs an OpenAI key, so a player carrying only an Anthropic key still gets no iOS dictation; there is a 15-second recording cap; and there is no auto-endpoint — it is tap-to-start, tap-when-done, versus native's automatic speech-end. Those are real seams, and §8 targets them.

② Fantasy proper nouns already have a better answer than keyterm prompting

Lane A's strongest genuine capability claim was custom vocabulary — Deepgram Nova-3 Keyterm Prompting, up to 100 terms, to bias recognition toward invented names. The project shipped sttCorrectNames() / sttWordScore() / sttNameRoster() (helpers.js, v1.330, commit b8fea0f, titled "phonetic name correction — 'Frizwick becomes Physics'") — post-hoc phonetic correction against the live campaign roster, with an explicit tie-guard that refuses to substitute when two roster names score equally ("never guess between people").

That is better targeted than a static 100-term list, because it draws from the actual NPCs in this save, not a vocabulary configured at request time. It costs nothing, runs on both the native and cloud paths, and needs no vendor.

And TODO #77 (confirm-before-send read-back) is the designed follow-up. Note what #77 solves that no STT engine can: speaker misattribution — in a car with four people, a second player speaking during another's spotlight is silently filed as the spotlight PC's action. A more accurate recognizer transcribes the wrong person's words more accurately. Only a confirmation gate fixes that. The project's own roadmap is aimed at the right layer.

③ Multiplayer shipped as hot-seat on one device — the room model has nothing to route

Three lanes (A, C, D) offered "LiveKit rooms are a natural substrate for PARTY_MAX 4." DOC/DOC_multiplayer.html locked the opposite: "Hot-seat on one device. No networking, no per-device sync… This removes the entire multiplayer server problem from the first pass." D13 (2026-07-20) records the multi-human session and the user's verdict, "it works." Phases P1–P5 are built; the hot-seat build is closed. Only Q7 (networked co-op, separate devices) remains, explicitly deferred and unscoped.

Even for Q7, the problem shape is turn-based text state sync — a labeled action block, a quest log, per-PC location threads — which is the existing Fly.dev REST service's shape, not media routing. Lane D's own top drawback says this plainly, and adds the sharper point: LiveKit data-channel packets are never buffered for a disconnected participant. For a game played in cars, where signal drops, a transport that silently discards state for whoever was in a tunnel is the wrong primitive.

④ The cloud-TTS question was decided against, two days before this row was raised

TODO #9 (direction change, user call 2026-07-20): remove Cartesia entirely — "too expensive to be viable" — and make Piper THE engine, with native kept only as a silent fallback. Lane C offered "Cartesia already integrated in tts.js could carry over into a LiveKit pipeline" as a benefit. That integration is being deleted, on exactly the cost grounds that LiveKit would reintroduce at a higher rate. Meanwhile the community Piper plugin for LiveKit is unofficial, absent from LiveKit's own 40+ provider list, has no confirmed maintenance history, and disables streaming synthesis — and adopting it would move Piper from client WASM to a server process, trading away the offline, $0, zero-network property the project just spent #9 committing to.

3 · Consolidated benefits, ranked by weight to this game

TLDR: after deduplication and after checking each against the repo, exactly one claimed benefit survives as a real capability this project lacks — and it is the one with a documented open defect.

#BenefitLanesWeight here
1 Coordinated turn-taking: barge-in, interruption handling, model-based semantic turn detection, automatic gain control. Car Mode today stitches tts.js and stt.js as two independent modules with no shared turn contract — the player cannot interrupt narration to speak, and the cloud path has no auto-endpoint at all. LiveKit ships these as first-class pipeline features (AudioTurnDetector, ~300ms min_delay vs ~500–800ms flat VAD). A, C REAL GAP, POISONED
The only benefit naming something the project genuinely lacks. But Lane E found LiveKit's own tracker documenting a barge-in bug that drops the start of a user's utterance specifically when interrupting agent speech — closed "not planned." The one thing LiveKit uniquely offers has an unfixed defect in the exact mechanic Car Mode needs.
2 Provider-swappable STT behind one interface — string descriptors like deepgram/nova-3:en, no call-site branching. Architecturally the same idea as the project's own PROVIDERS and TTS_PROVIDERS tables. A, B, C TRUE, NOT NEEDED
Three lanes agreed, and the agreement is fair — it is a good fit for how this codebase likes to be built. But the project already demonstrated it can build that table itself, twice, in ES5, in an afternoon. Buying a server to obtain a pattern you already own is not a benefit.
3 Cross-browser mic capture via WebRTC, removing dependence on whichever speech engine the browser ships. A, B, C, D, E ALREADY SHIPPED
Unanimous across all five lanes — and superseded by §2①. The project reaches iOS with getUserMedia + MediaRecorder + Whisper, no server, no build, on the player's key. Note the irony: Lane C flagged that no researcher actually tested WebRTC mic capture on iOS Safari. The repo has empirically answered the adjacent question already.
4 Custom vocabulary / keyterm prompting for invented fantasy proper nouns — a capability class Web Speech API structurally lacks. A OUT-DESIGNED IN-REPO
See §2②. Roster-driven phonetic correction beats a static term list for this use case, and #77's read-back also covers misattribution, which no recognizer can. Lane A itself conceded the accuracy premise is unproven — see §6.
5 Rooms/participants as multiplayer substrate, plus granular publish/subscribe permissions matching one-speaker-at-a-time table play. A, C, D WRONG PROBLEM
See §2③. Multiplayer shipped hot-seat; Q7 is a state-sync problem; data channels do not buffer for disconnected players. Lane D's own drawback contradicts its own benefit here — the internal conflict is genuine and it resolves against LiveKit.
6 Apache-2.0 core, self-hostable, low transport lock-in; well-funded ($100M Series C, Jan 2026); repos active within days of the survey. E RISK-REDUCER, NOT A REASON
Correctly scoped by Lane E itself: portability covers Cloud↔self-host only. The Agents/orchestration layer has no drop-in equivalent, so exiting LiveKit entirely is not cheap. This lowers the downside of adopting; it is not an argument for adopting.

Dropped in deduplication: free Build tier (1,000 agent minutes/mo) and pre-connect audio buffering are real but trivial at this scale; multilingual coverage (up to 190 languages) has no stated demand in this project; built-in STT/TTS/LLM failover exists only in the Python SDK — Lane E found the open issue confirming agents-js lacks it, in the language this project actually uses.

4 · Consolidated drawbacks, ranked by weight to this game

TLDR: one drawback is unconditional and gating; the rest only bite after you have already accepted the gating one.

#DrawbackLanesWeight here
1 There is no incremental path. LiveKit does no STT itself; STT lives in Agents; Agents requires an always-on server-side worker; tokens require server-side JWT signing with a secret. Adopting it means a bundler, npm dependency management, ESM, an always-on media backend, and — to keep Claude as GM — a Python runtime alongside the existing Node one. Against 16 plain <script src> ES5.1 files on static hosting. A, B, C, D, E GATING — DECIDE THIS ALONE
Unanimous, and Lane E is right that it should be weighted above everything else because it is unconditional: true before a dollar is spent or an outage occurs. This is the whole decision.
2 It inverts who pays. The project's economics are BYOK end to end — players pay Anthropic, players pay OpenAI for the Whisper fallback, Piper costs nobody anything. LiveKit bills the developer per connected minute (agent session + WebRTC participant minutes + inference), not per minute of speech. B, C, E BREAKS THE MODEL
This is the same unit-economics trap DOC/app_vs_browser.html already reasoned through and rejected for the App Store conversion: "converting doesn't create a business; it creates a billing obligation." The reasoning transfers exactly. See §5.
3 Regresses the offline/local-first posture the project deliberately built. Piper is WASM in the browser, OPFS-cached, offline, $0 — a decision re-ratified 2026-07-20 by deleting Cartesia on cost. Native STT is on-device. Routing voice through a remote room + worker + third-party vendor means the STT and TTS halves end up with opposite connectivity and privacy models. B, C, E AGAINST A FRESH DECISION
4 Breaking-change churn on exactly the layers this would touch — Agents v0→v1, client-sdk-js v1→v2, server-sdk-js CommonJS→ESM-only, three migrations in roughly two years, with no published LTS or deprecation policy found. E ONGOING TAX
For a solo maintainer already carrying a 57-handler tag parser, a prompt-cache split, and a nightly ship cadence, each major bump is unplanned work with no user-facing payoff.
5 Multi-speaker transcription for a 4-person table has open bugs. Diarization operates on a single mixed track by design; GitHub #3657 reports the STT agent transcribing only one participant when several speak; #4567 reports a no-op diarization toggle. No provider publishes accuracy at 3–4 simultaneous speakers. D HITS THE CAR CASE
Downweighted for a reason Lane D flagged honestly: these are dated observations with no confirmed-current status. Downweighted further because hot-seat multiplayer has one mic and one speaker at a time by design — so this only bites in a networked-co-op future that does not exist.
6 Self-hosting to escape the fees is a worse trade for a solo dev — TURN relay config with its own certs and bandwidth, 20–40% of users behind symmetric NAT needing it, Redis-coordinated multi-node Go SFU, break-even only around ~500 concurrent sessions. B, D, E ESCAPE HATCH IS SHUT
Three lanes agreed. It closes the obvious "just self-host it for free" rebuttal.
7 Cloud reliability is imperfect and the failures land on Car Mode's pattern — status page showing 97.22% trailing-30-day uptime against a 99.9% target; the barge-in drop and phantom interrupted-speech events; EU-region latency reported doubling when deployed. D, E SPECIFIC, THINLY SOURCED
Real signal, but see §6 — the aggregate outage counts come from automated monitors with undisclosed methodology.

Where the lanes conflicted

  • Is LiveKit STT cheap or expensive? Lane B modelled STT-only at ~$0.044–0.058/player-hour and called it small; Lane E modelled a fully-loaded stack at ~$4,614/month for one continuously-open session. Both are right about different things, and the resolution is the important part: the transcription is cheap and the connection is not. Agent-session and participant minutes accrue for the whole time a player is connected, while actual speech is a few minutes per hour. Lane B's own numbers show the overhead dominating the STT by roughly 10×.
  • Does a script-tag-loadable build exist? Lane E asserted npm/ESM-only as verified; Lane B explicitly labelled its own version of this an unverified inference and named it the one item it most wanted checked; Lane D's researcher flagged ES5 compatibility as unaddressed by the docs. This, the most-contested fact in the whole dataset, is decision-irrelevant — a perfect UMD bundle would still buy nothing, because the client SDK alone cannot transcribe anything without a room and an agent worker that do not exist. Worth stating plainly so nobody spends an evening checking it.
  • Lane D internally. Its Topics 1–4 described LiveKit on its own terms and read favourably; only Topic 5 was asked to compare against alternatives, and that framing flipped the verdict to "overkill and cost-inefficient." Lane D's supervisor flagged this honestly. It is a structural bias worth naming: four of five lanes were never asked what the cheaper option was.

6 · Evidence quality

TLDR: the one fact the verdict rests on is the best-evidenced thing in the dataset; almost everything favourable to LiveKit is thinner than it reads.

Verified, and load-bearing

  • LiveKit performs no STT itself; the Agents framework requires a server-side worker; there is no browser-only mode. All five lanes, from official docs. This is the finding the verdict rests on, and it is the strongest evidence present.
  • Tokens are server-signed JWTs; the API secret must never reach the browser. Official docs, two lanes.
  • Anthropic plugin is Python-only; agents-js omits it and also lacks the fallback adapters. Official docs + an open GitHub issue.
  • Published per-minute rates for LiveKit tiers and for Deepgram/AssemblyAI/OpenAI, from vendor pricing pages.
  • Repo-side facts in §2 — I read stt.js, helpers.js, TODO.md and DOC/DOC_multiplayer.html directly rather than relying on the project summary the lanes were given.

Vendor claim or single-blog — do not treat as fact

  • The ~$0.077/min fully-loaded figure and the ~$4,614/mo derivation both trace to trtc.io, a competitor's blog. Flagged as vendor-claim by Lanes C and E.
  • "568+ outages" and third-party incident counts come from automated status aggregators (statusgator, isdown.app) whose definition of "outage" is not disclosed. Lane E said so itself.
  • Self-hosting break-even points (~500 concurrent sessions, 500K–1M participant-min/mo) and the $16K–30K/yr opportunity-cost figure come from consultancy blogs with an interest in the answer.
  • Migration cost figures ($72K, 4–6 weeks, two senior engineers) are enterprise customer-support-agent case studies with telephony and CRM tool-use. Lane C used them only qualitatively and said so; the literal numbers do not transfer to a solo hobbyist.
  • Latency figures (sub-1s cascade, 320–800ms realtime) are from LiveKit's own docs and blog. "Verified" there means "present in official documentation," not independently benchmarked — and no lane found any published latency benchmark using Claude in a LiveKit pipeline.

Unverified, and it matters

  • Nobody has ever benchmarked STT accuracy on invented fantasy vocabulary — not for LiveKit's providers, not for Web Speech API. Lane A said this outright and it undercuts Lane A's own headline benefit. Worse, Web Speech API has no published WER at all, so every comparison in this dataset is qualitative on one side and quantitative-but-shaky on the other.
  • Even the best providers do badly on proper nouns generally: AssemblyAI Universal-3.5 Pro reports a 24.08% missed-entity rate on names despite 4.35% overall WER; a Pipecat benchmark puts Deepgram Flux at 50.50% entity error rate. Deepgram's own 5.26% WER claim is possibly contradicted by Artificial Analysis at 7–10%.
  • No lane tested WebRTC mic capture on iOS Safari; Lane C explicitly labelled its own iOS benefit an architectural inference.
  • No lane evaluated multi-human-plus-agent rooms for a game party. Lane C called this an extrapolation.
  • The multi-speaker transcription bugs (#3657, #4567) have no confirmed current status; the Node/Anthropic plugin gap may be temporary — Lane C explicitly asked that it not be used to rule LiveKit out permanently, and I have not.
  • No case study of a team migrating off LiveKit exists, so "low lock-in" is architectural reasoning, not observation.

7 · Alternatives considered

TLDR: the do-nothing baseline is genuinely strong here, and the best improvement available is hardening what already ships — not buying infrastructure.

OptionOutcomeWhy
Do nothing — native Web Speech + shipped Whisper fallback + roster name correction + Piper TTS BASELINE — WINS TODAY $0 to the developer, works on every target platform including iOS, no server, no build, no npm, no new runtime, no vendor. The bar LiveKit had to clear, and did not.
Harden the shipped cloud path — lift the 15s cap, add an endpoint heuristic or VAD so it is not tap-when-done, ship #77's read-back, then #78's numbered read-back for Car Mode RECOMMENDED NEXT MOVE Targets the actual remaining seams (no auto-endpoint, garbled names, misattribution) in ES5, in-repo, at zero recurring cost. #77 also solves misattribution, which no STT vendor can.
Whisper.cpp / Moonshine WASM in-browser TRACK AS AN IDEA The most architecturally aligned option in the entire dataset: OPFS-cached, offline, $0, no key at all — precisely the Piper pattern the project already runs and just re-committed to in #9. Would close the iOS gap for key-less players too. Loses today only on effort and model size, not on principle. If the voice stack is ever revisited, this is the shape to revisit it in.
Deepgram / AssemblyAI streaming direct from the browser FALLBACK IF WHISPER FAILS Keeps BYOK and needs no server, gets streaming interim results and keyterm prompting. Caveat: lanes disagreed on whether browser-direct keys are sanctioned, and AssemblyAI reportedly requires backend token minting. The general "never ship a key to the browser" objection is weaker here than elsewhere, since this project already ships player-owned keys in localStorage by explicit design — but it is not zero.
Colyseus / PartyKit / plain WebSockets for networked co-op (#1 Q7) RIGHT COMPARISON SET FOR Q7 Assessed 5–10× cheaper and architecturally closer to a turn-based text game's state-sync problem. When Q7 is scoped, this is the field to evaluate — LiveKit belongs in it only if live voice presence between remote players is a stated requirement.
LiveKit LOSES Requires the largest architecture change of any option, to deliver two benefits already shipped, one benefit aimed at a decision already made in the opposite direction, and one real capability (turn-taking) with a documented unfixed defect — while inverting who pays.

8 · Smallest next step, and the re-open triggers

TLDR: my recommendation rests on one assumption I have not personally tested, so test that — for the price of one evening and about a cent.

The riskiest assumption in this document

That the shipped Whisper fallback is actually good enough on iPhone Safari in Car Mode. I verified it exists and read every line of it; I have not seen it run on a phone in a car. TODO #84 itself names "the iPhone Safari + Car Mode path" as the primary use case. If that path is in practice unusable — permission prompts, mp4 recording quirks, the 15-second cap truncating actions, tap-when-done being impossible while driving, latency after upload — then the "gap is already closed" finding weakens, and §7's ranking shifts (though still not toward LiveKit; toward hardening or toward WASM Whisper).

The test

  1. One iPhone, Safari, an OpenAI key on file, Car Mode, a real campaign with a few awkward NPC names on the roster.
  2. Dictate 10 actions containing campaign proper nouns. Record for each: did the mic button appear (isSupported() true?), tap-to-text latency, raw Whisper output, output after sttCorrectNames, and whether the 15s cap ever truncated.
  3. Note explicitly whether tap-when-done is workable one-handed while driving, since that is the seam LiveKit's turn detection would nominally fix.

Cost: one evening and roughly $0.01 of Whisper. Decides: whether §2① holds, and which of the three §7 improvement paths to take. Does not require: any code, any server, any dependency, or any commitment.

Re-open TODO #84 only if all three become true

  1. Networked co-op (#1 Q7) is greenlit — separate devices, live sync, explicitly scoped, not the hot-seat build.
  2. Live voice presence between remote players is a stated requirement, not an assumed one. A turn-based text RPG can be networked co-op with no audio transport whatsoever.
  3. The project has already accepted a build pipeline and an always-on server for other reasons. LiveKit must never be the thing that forces that decision; it can only ride one already made.

Absent all three, this file is the answer, and #84 closes. If they do become true, re-check two things that may have moved: whether agents-js has gained Anthropic support (so a second Python runtime is unnecessary), and whether GitHub #3657 multi-participant transcription is fixed.

Bottom line

LiveKit is a good product aimed at a different problem. It exists to route live media between many participants and orchestrate voice agents. Traffic and Dragons is a turn-based text game where one person at a time dictates one sentence into a text field, played on one phone passed around a car, funded by every player bringing their own API key.

The research was unanimous on the structural point and was, in places, thinner than it read on everything favourable. But the finding that actually settles it did not come from the research at all — it came from reading the repo: the iOS dictation gap that every lane offered LiveKit to close was closed months ago in about 150 lines of ES5, and the fantasy-name problem has a roster-driven correction pass that a generic vendor could not match. The project solved its own voice problems with the architecture it already has, twice.

The correct next move is not to buy infrastructure. It is to spend one evening confirming the iOS path works in a car, then ship #77 — because the read-back gate fixes the one failure mode (a second player's words filed as yours, silently) that no amount of transcription accuracy can ever touch.
