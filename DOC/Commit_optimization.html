Commit optimization

Five plans for shortening the time from a finished change to a pushed one. Measured 2026-11-18 on the owner's desktop at commit 3980b657, plus the last 30 CI runs of "Engine tests".

The sweep is not a hook. It is a rule sessions follow (the 4-to-40-minute figures are the project's own earlier measurements, not re-timed today). CI then runs the same sweep again on the pushed range.

CI, last 30 runs: median 40 minutes, shortest 13, longest 141. About 14 minutes are fixed (engine suite 2.5, focused battery 2.8, browser suites 9.5). The sabotage sweep takes the rest: between 0 and 127 minutes, and 75% of all CI minutes. CI does not block a push or a deploy.

What a battery proves. A battery proves that a test would catch a specific break. It does not prove the code is right; the green engine suite does that. A missed clause therefore means a weak guard, not a broken game. This matters for plans 1 and 3.

Found while measuring. The full local browser run was red twice: tests-771-place-sheet-browser.js exits in 0.5 s with no output when it runs inside the whole 40-suite run. It passes alone, passes under --only 771, and is green in CI. The cause is not diagnosed. While it stands, the pre-push hook blocks a push from this machine.

The five plans

1. Push first, prove in CI

Stop running the range sweep at the desk. CI already runs the identical sweep on every push.

Change
The local rule becomes: the applicability scan (5 s), plus only the batteries the change itself added or edited. The range sweep is CI's job. A red CI run already reaches the next session through dev/ci-status.js; add a phone notification so it reaches the owner sooner.
Saves
4 to 40 minutes per push. A core change goes from about 48 minutes to about 8.
Cost
Small. A protocol and documentation change, no new code beyond the notification.
Risk
Master and the deployed site can run for up to two hours with a guard that is not yet re-proven. The game itself is still covered by the engine and browser suites before the push. A clause that only CI's Linux runner can miss is already found only there.

2. A landing queue

The session ends at the commit. An unattended lander does the proving and the push.

Change
A session commits to a landing branch and stops. A lander script, in its own clean worktree, takes each queued branch in turn, runs the sweep and the browser suites, pushes to master when green, and reports when red. Proof still comes before master.
Saves
The owner's wait drops to the 2-minute commit. The 40 minutes still happen, without anyone watching.
Cost
Medium. The lander, a queue, a report channel, and a rule for the version marker (two queued landings cannot both hand-bump APP_VERSION; the lander would stamp it).
Risk
A red landing is found after the owner has left, so the fix waits for the next session. The desktop must stay awake, or the lander runs in the cloud.

3. Run only the clauses the change can reach

Today one changed line in helpers.js re-proves 1,894 clauses. Most of them guard code the change never went near.

Change
Select by clause, not by file. A clause is due when the diff touches the function that holds its anchor, or the test it names, or the battery itself. Everything else is left to the weekly full sweep (run-sabotage-all), which becomes the backstop.
Saves
Estimated: a 200-battery sweep becomes 10 to 20 batteries, so about 40 minutes becomes 3 to 5. Speeds up CI by the same factor. Not measured; needs a trial on last month's commits.
Cost
Medium. Dev tooling only, but it loosens a gate, so it is Fable-tier work with its own sabotage proof.
Risk
Not sound in principle: a change in one function can weaken a guard on another through a shared helper. The weekly sweep catches that up to a week late. The trial would count how often it happens.

4. Mutate in memory

Make each clause cost a fraction of what it does now, so the full sweep stays but shrinks.

Change
Each clause currently resets a scratch git clone, writes the mutated file, and starts a new node process. The project's own notes name those two steps as the ceiling. A new harness would mutate the source string in memory, load the engine into a fresh VM context, and run the one guarded test, all inside one process.
Saves
Unknown until tried. A one-battery spike would give the real number in an afternoon. Chrome-driven batteries gain nothing.
Cost
Large. The harness is the root of trust for every guard, so the rewrite must itself be proven against the old one, battery by battery.
Risk
An in-memory load that differs from the real load order would produce false proofs. Tests that read files from disk would not see the mutation.

5. Trim the fixed costs

Shorten the parts every commit and push pays, whatever it touched.

Change
Three independent pieces. (a) Run the browser suites four at a time, as the battery pool already does. (b) Run the standalone suites inside run-tests side by side, not in sequence. They are 129 of the pre-commit's 135 seconds, and each is already its own process. (c) Let a commit that stages only documentation skip the engine suite, keeping the TODO and link checks.
Saves
Estimated: every commit from 2.3 minutes to about 25 seconds; the push hook from 5.4 minutes to about 1.5; a documentation commit to 5 seconds. The same change takes about 9 minutes off every CI run.
Cost
Small. Dev tooling, a day or less.
Risk
Chrome suites were flaky when run 16 wide beside batteries; four wide alone needs a check. Piece (c) needs a strict definition of "documentation only", since CLAUDE.md facts are tested against the code.

Recommendation

Do plan 1 and plan 5 together. They are both small, and together a 20-minute window can hold a core change and its push. Then trial plan 3 on last month's commits, because it is the only plan that also shortens CI's two-hour runs, which is the wait plan 1 leans on. Choose plan 2 over plan 1 if "proven before master" must stay absolute. Plan 4 is worth a one-battery spike and nothing more until that number is known.

Splitting the project into more modules is not among the plans. It would not remove any of these gates, and the portable parts are already separate.

Plans 1, 3 and 5(c) change what a gate requires and need the owner's ruling before any work.
